## 開場（主持人 鄭然）

大家看到了很多智能體技術，包括剛才幾位專家做的分享。智能體其實往往還處在比較早期，在個人、在企業裡（很多還停留在）demo（演示）（階段）。今天想跟各位專家進一步討論的話題是：因為剛才幾位專家已經講了很多「怎麼做」這個問題，那接下來我們一起討論——怎麼樣讓智能體真正在我們的生產環境裡面落地？在生產環境落地需要解決哪些問題？

因為剛才也講了，其實落地還是有很多技術問題需要解決。那我今天就和三位專家一起討論「Agent 落地的真實代價」。首先，軟件的行為——大家都知道，我們原來做軟件，軟件的行為、我們的程序、我們的架構設計，其實都是「確定性」的。但是大模型 / AI 帶來了「不確定性」：整個大語言模型本身是一個概率性的技術，最終輸出的是一堆概率。早時候可能大家都不相信、不覺得這樣一個技術能對我們整個世界（帶來改變），也不覺得「概率」（能靠得住）——概率總會出錯，事實上大模型也確實有幻覺。那在傳統的架構上，我們做了幾個假設：整個行為是確定的、整個架構的調用過程是確定的、整個的狀態是（確定）的。在這種情況下，我們設計的系統是面向確定性的系統。所以在 AI（Agent）出來之後，這些行為發生了巨大的變化。那我們就要考慮：面向 Agent、面向大模型這種「有一定不確定概率」的場（景），我們應該怎麼去設計？

**第一個問題**，請各位老師依次回答：在大家的實踐裡面，你們是如何設計「面向 Agent 友好」的基礎架構的？什麼樣的基礎架構能更好地去幫助 Agent、幫助 Agent 程序（運行）？因為原來的基礎（設施）是傳統的（面向確定性的）。

## Q1：如何設計面向 Agent 友好的基礎架構？

**陶宇田（阿里巴巴）：** 那我先開始。我覺得這個問題可以從兩個角度來看。第一個點是：今天（模型）能力越來越強，然後我們給它——其實今天我們講很多話題，其中一個很重要的點是「給 Agent 提供合適的工具」。這些工具，一方面我覺得是從 Agent 執行環境的內部來看：可能 Agent 隨（著模型）能力越來越強，它只需要一些基礎的部分，比如一些 bash、一些文件操作，它可能就能組合出很強的（自主）性和進化性，這是它能力範圍可以觸（及）的。另外一層是：今天我們談很多場景，是希望 Agent 能夠成為人的一個數字（分身）。所以在這個視角上，Agent 很多時候會去嘗試做以前「人在（做）」的事情；那在這個層面上，很多外圍的系統是 Agent 自己可能觸碰不到的、或者不能被它隨便改的，那對它友好的這種設計，就是你要給它提供更友好的工具。

今天我們在（阿里）內部也會經歷很多這種變革：去年的時候我們開始提 MCP（走這個工具化路線），今年——我不知道其他公司有沒有，像阿里、華為有非常強的（推動），很多應用會提供對應的（工具/MCP）。因為這相對於 Agent 不僅僅是（工具）友好，也是對它的上下文（更）友好的一種（供給）方式。這些可能都是從不同角度去讓系統的設計更適合 Agent 去（使用）。

**晁岳攀（鳥窩，百度）：** 我其實對這個（很有）體會，因為去年做智能體也遇到了各種困難，然後做了很多（工程）化的處理。我可以給大家分享兩個經典場景。

第一個：怎麼讓智能體獲得充足的知識。比如我們一開始做網絡監控——做整個物理網絡監控的一個「（網絡監控）智能體」產品的時候，我們去把告警、流量、以及變更等等這些各類信息抽取出來，提供給智能體，讓智能體有充足的「後備資源」可以去查找。另外一個例子：我現在做高性能網絡庫這個方向的時候，我們要做（某網絡）庫（大家做虛擬化時比較熟悉的那個庫）的一些故障定位。我們自己（總結）了 20 幾條、27 條最常見的場景讓它去處理，但這個（覆蓋）不夠；後來我們想辦法去拉取這個庫在（GitHub）上的 issue——它的 issue 大概有兩千多條，上面的信息都非常全。我們通過工具把它拉下來，讓大模型去做整理、清理，裡面的圖讓它去（視覺）識別出來、轉成文字，整理之後再餵給大模型，讓大模型去做一個知識庫，放在（RAG/文件）裡。這樣我們這個智能體就能充分利用（這些）資源，我們就可以為大模型提供一個現成的知識庫資源。這是我們做的一個（工程）化的處理。

還有一些小的處理，比如怎麼去解決「幻覺」的問題。因為經常有用戶吐槽：我們做（問答）的時候反复問答，給出的結果貌似有證據、實際沒有任何價值信息。我們怎麼解決？比如像剛才（提到）的「雙 Agent」概念：讓一個模型得到一個結論之後，再交給另外一個模型（做交叉驗證）。比如我用 Qwen（通義千問）去得到一個結論，然後我再讓 DeepSeek-3.2 去做一個 review，讓它倆之間做一個互動的校驗，把這個結果做一個互動的 review，然後找到一個（更可靠的答案）。我覺得整個在利用 AI 技術做產品的時候，還有很多值得去挖掘和探索的方向。

**季旭（字節跳動）：** 這個問題，因為我們最近正好在做一個 memory 產品，其實本質上就是 **Mem0**。（更多的是）因為我們 Claude（這類）是一個通用（Agent），但我們 memory 其實是一個垂直的、只做一件事的（Agent）——把自己這件事給你做好，但它本質上也有 Agent、也有 LLM 的能力在裡面，其實它就是一個 Agent。

在這個過程中我有一些體會：就是「從玩（demo）到生產」這個階段，我們應該怎麼做。首先，比如現在的 Agent 其實（還）不能（直接）用於生產：如果我們真正嚴肅地處理一個系統，我們是不敢就讓 Agent 去碰我們這些線上、直接在生產上去跑的，因為它有特別多的長尾（corner case）問題，而且它的（執行）效率可能沒那麼高，我直接做一次（工具/skill 調用）也比較貴——比如我提取一個記憶、一段代碼路徑，可能就耗（掉不少 token）。所以我一直的想法是：隨著模型能力不斷提升（scaling），我們的長尾問題確實會越來越少，然後真正到大部分（場景）都 OK 以前——（也就是）確實可以用於生產的（那條）路，才能在生產環境裡面真正（放開）。

現在我們（只）敢去做一些簡單的、只讀的工作，我們會嚴格限制這條線——只讓它做非常簡單的事，讀一些什麼系統、讀一些（數據）。而對於所有確定性的（環節），其實我們有點像 OpenClaw：我們用 hook 的方式，就相當於我們在 Agent 裡有各種各樣的 hook 點。比如在（做）記憶（提取）的時候，本質上它要（調用模型），但我直接把它 hook 掉，我就把這個 Agent 用一種確定性的邏輯去（執行）。但更多的是——我們為什麼還要保留（模型能力）？還是為了未來去留一個口子。不過現在在我看來可能還是比較難的。所以我的答案就是：用 plugin / hook 來控制確定性的（部分），（讓 Agent 只做）那種少量、輕量、對系統影響最少（的事）。

## Q2：在不確定性裡，哪些行為 / 技術 / 平台 / 信息可以依賴為「確定性」的？

**主持人 鄭然：** 謝謝三位老師。我順著這個話題再問一下：不管是面對智能體，還是說 AI，都帶來了不確定性——因為它（本質上）就是不確定性。那在大家的實踐過程中，有哪些因素、哪些行為你認為還能依賴、是「確定性」的？能依賴哪些技術、哪些平台、哪些信息，你認為是一個確定性的信息？

**陶宇田（阿里巴巴）：** 我覺得今天（模型）背後最底層的原理其實就是「隨機性」，所以我們很難去假設它是一個確定的行為（模型的生成）。今天我們設計系統、以及像剛剛（季旭）說的「在生產（環境）也不敢相信」，其實就是因為在目前模型的實現原理下，我們沒辦法抹掉這種隨機性。那當前，比如我們今天去做沙箱或者類似的一些基礎（設施），本質上還是希望能夠在一個特定的環境下，把它自身的能力做一定的限制。因為在特定場景下，如果完全不限制地放開這個能力，很多時候可能就會出現「不受控」的情況，而不受控的結果在很多時候我們都不能接受。

**晁岳攀（鳥窩，百度）：** 大模型的不確定性是現在客觀存在的一種事實。就像前段時間，Facebook 的副總裁去用 OpenClaw 整理他的郵件，結果把郵件刪了——所以會出現這種（意外）情況。所以有的關鍵場景下，我們對這種（風險）考慮以後，就可以通過一些工程性的方法去做處理。比如「一（步一）步」模式（剛才說的）：每一步你要做一個校驗，對這個結果你要（充分）地做一個審核；第二，可以（用雙模型讓）它（互相驗證）結果；第三，就是利用文件（沙箱）——沙箱技術能在一些安全的環境裡去做執行，讓數據在這個安全穩定的環境裡去（跑）。

**季旭（字節跳動）：** 這塊前面兩位老師都說了，可能更多的是在「安全容器」或者控制它的「行為」上。我可能補充一點：因為本身我原來是做（存儲）的，對於（存儲）來說——我們怎麼樣去解決這種意外？比如我一個（存儲）盤，我的可靠性是 99.9%，那我想把它提到「五個 9」或者「六個 9」，我們經常（批）（量）（提升）（可靠性），其實我們做的是「冗餘」。這個其實可能也是（一個思路）。

包括我自己也是——比如我做 PPT，好多 PPT 都是（AI）（做）出來的。我自己是怎麼做的？它確實一個東西做不好，那我怎麼做？我同時用一個 prompt 給它發五遍，最後可能是讓 LLM 判斷它的好壞、或者是我來判斷它的好壞，然後把這個東西的好壞（比較一下），我選擇一個可用的。這是第一點。

第二個點：除了（可以）在一個容器裡面去做（存儲）（隔離），還有一個東西是我們經常做的——「控制爆炸半徑」。就是說我要把這個東西用（沙箱）完全隔離，它必須得在（隔離的）（環境）上跑；我們完全不能做一個特別好的（防護）的時候，那你就要（承擔）不確定性，你就要（做好）「爆炸半徑」（的控制）。我去為我自己的（例子）——我用 OpenClaw（做了個嘗試）：你看到好多亂七八糟的這種（廣告），（有個交易）（工具）說「我們幫你賺了多少錢」，在（某個交易/預測）市場上（很火）。我當時也試了一下，然後發現其實完全不像（宣傳的）——第二（點）我發現它可能就是想賺我錢。然後它幫我做了一件事，還搞錯了：我說「你給我平倉」，它把方向完全買反了，結果變成 double（加倉）了。但為什麼這事沒有對我造成任何損失呢？因為我的賬號裡根本沒什麼錢，我就是玩一玩。所以如果你真的能控制好那種爆炸半徑，也許在某種情況下你就能接受這種長尾或不確定性的事。（至少我自己也沒有通過它賺到一分錢——如果他（能）賺錢，可以教我一下。）

**主持人 鄭然：** 確實，三位老師舉的例子都講了如何去應對不確定性：包括重試、包括在一個隔離的環境裡面做交叉驗證。其實我自己在實現的時候也應用了一些類似的技術——用多個 Agent 去做（驗證），讓一個 Agent 去寫代碼、讓另一個（Agent 去 review）。既然不確定性無法消除，那我們就把這些不確定性的行為做一個隔離，然後在一些合理的邏輯裡面去解決確定性的問題。

## Q3：怎麼控制 Agent 的行為？（可控性）

**主持人 鄭然：** 那我們討論下一個問題——可控性。因為它既有不確定性，那 Agent 在這個不確定性裡面，除了剛才這些「從結果上驗證」之外，我們怎麼樣去控制 Agent 的行為？或者說 Agent 的行為我們還能不能控制？因為傳統的邏輯裡面，我們的代碼是非常嚴謹的：有輸入、有執行算法、有執行邏輯、產生輸出。但是 Agent 本身又有不確定性，很多行為又不可控。所以我想和三位老師討論：第一，我們能不能控制 Agent？我們怎麼能控制 Agent，讓它的行為在我們可控的（範圍裡）？

**陶宇田（阿里巴巴）：** 這個問題剛剛我們討論的也很重要：今天它的行為從底層原理上就有很多不確定，所以「控制」——我們在（發）揮很多工程手段的時候，比如我們說的沙箱可能只是其中一個方向。這個方向是說，我們會給整個 AI 的運行環境添加一些適當的約束：不管是它運行在安全容器（容器級別的強度），還是說我們在網絡層面上加了一些強制隔離的因素、或者一些 DNS 的（限制），本質上這些都是在給整個系統增加約束，去防止一個你控制不了的 Agent——它一旦（因為）外（部）的提示注入、還是說它自己內部的模型「抽風」了，然後去做出一些行為的時候——把這個（風險）（兜）（住）。

另外一方面，其實像今天很多工程上的想法，比如今天很多場景都會給 Agent 注入不同的 skill：skill 其實就是在對一些傳統工作、甚至個人經驗的一些總結、抽象的方式。然後我發現一些特別經典的（做法）是，除了用自然（語言）描述一些流程之外，還有一種特別典型的——它可能會有 scripts 這種文件。其實這個就是特別典型的「用固定的、傳統的語言（編程語言）或者程序的固定性 / 確定性，來對抗 Agent 或模型的隨機性」的一個手段。就是說在這種（做法）下，我們除了「讓 Agent 不去浪費更多的 token 去生成一些比較隨機的結果」之外，還有一個特別重要的、（值得）考慮的點：當它執行這個特定任務的過程，其實我們已經通過程序的形式把這件事情（固）（化）了。那這種情況就是「用確定性去對抗（不確定性）」。

**晁岳攀（鳥窩，百度）：** 其實從大模型的原理來說，它是通過概率性的方式去計算，所以我個人認為不確定性是無法（完全）避免的。但我怎麼去解決這個問題呢？我給大家舉個例子：因為我們（這個）部門經常會做「網絡變更」這種東西。網絡變更——大家知道，現在 15% 以上的網絡（故障）就是因為人為的變更去導致（的）。原來都是我們人工去做變更：之前把整個變更步驟人工寫出來，然後經過（嚴）（格）的審計，最終去執行。現在我們的同學去做一些應用（來）接（管）、去做（編排），但最終還是要交給人去做一個最終的審核才去執行。我覺得如果你實在無法避免、確實在一些關鍵步驟上需要特別重視的話，我們（引）入一個叫 **HITL（Human-in-the-Loop）** 的機制：人必須去做最後一關。畢竟 AI（出了問題）它自己不能（負責），還要找一個人來（負）（責）。

## Q4：如何平衡 AI 的「天馬行空」與給它的約束？方案要詳細到什麼程度？
