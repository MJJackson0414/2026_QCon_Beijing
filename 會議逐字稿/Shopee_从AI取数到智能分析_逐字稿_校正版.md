OK，先说背景与挑战。

## 一、背景与挑战：从 BI 演进到 AI 原生数据消费

数据消费呢，一般来说我们都认为它经历了四个阶段。**1.0** 呢是传统 BI，这个是以静态报表为代表，报表的交付呢主要是依赖数据（IT）团队通过写 SQL 的方式去交付。**2.0** 呢是进入了自助式 BI 的时代，这个是以平台拖拽配置为代表——以我们公司为例，我们公司的（BI 平台）差不多现在月活有两万多，但是这两万多人里边只有不到 10% 是数据的生产者，也就是报表的编辑者，说明大部分人的这个数据消费还是要「指着」少数的报表编辑同学的手（去操作）。**3.0** 时代呢是增强分析时代，开始引入 ML 辅助的数据分析，但是主要的分析流程依然是由人驱动。那我们现在呢正式地进入的是 **4.0，AI 原生（Agent）的时代**：数据消费者可以通过自然语言提交它的数据分析需求，然后呢可以自主地从取数、完成从取数到智能分析（的全流程）。

其实我们做 AI 取数这件事情，最早是从 24 年的时候就开始。那时候呢我们对 **Text2SQL** 这件事情是非常有信心的。为什么有信心呢？因为我们看了学术界的 benchmark，像 **Spider** 上（SOTA）的一些骚（操作）的解决方案，它的准确率可以做到 85% 到 91%，这已经跟人的准确率差不多。基于这份信息呢，我们设计了我们第一版的 **Text2SQL** 的一个 demo 架构。这个架构一个周就做出来，就是上面（这个）架构就做（成）的：我们把我们平台上近 30 天有访问的差不多 100 万张表做了 **embedding** 索引，然后用户问题过来之后的话，可以基于相似（度）检索的方式去召回一些相关的表，用这些表来构造一个 prompt，然后交给大模型一步生成 SQL——这是一个典型的 RAG。

但是这个 RAG 它的效果是非常差的。我们第一版我们造了一个评测集（这个评测集还是一个简单版的评测集），在这个评测集上，**找表的 MRR@10 只能达到 56 左右**，**Text2SQL 的执行准确率差不多只有不到 40%**，更有甚者，即使只看语法准确的语法准确率也就（60%）的样子。差不多在同时间，我们这个版本在用的时候，**Spider 发布了它的 2.0 版本的 benchmark**，这个 benchmark 呢号称是基于企业真实场景构造的一个测定集；这个 benchmark 上，当时比较先进的商业化模型，就是 **GPT-4o**，达到的准确率也只有 **10% 左右**。（我们第一版的 LLM 用的是 GPT-4o-mini。）

所以结合这个数据和我们第一个版本的实践，我们可以得出一个结论：**企业级的 OLAP 场景的 Text2SQL 是一个非常难的事情**。（基于 RAG 的 Workflow 在企业级 OLAP 场景下效果不佳。）

但是（面对）前面的这个难点，我们开始了 Text2SQL 的一个技术演进之路。首先我们分析了一下我们第一个单网（单链路）的版本，以及我们试用的（种子）用户的一些负反馈，总结了五大问题吧：

第一个问题是「**找表不准**」。我们知道，我们的数据数仓都是有分层的，每一层之间、和数仓每层的内部会有很多相似的表——它有一些细微的区别，但是整体上还是相似的。尤其对于这个 embedding 模型来说、做相似检索的模型来说，它其实很难区分这些表之间微弱的不同。所以说如果我问了一个问题，只用 embedding 的方式去召回的话，那通常会召回一些「看起来语义相关、但是不正确」的一些表，这个是找表不准。

第二个是「**SQL 语义的错误**」。我们第一版的架构只用了 Hive 元数据，严重缺少一些业务规则和数据口径，这样导致它生成的 SQL 虽然能跑、能有数据结果，但这个计算逻辑和结果都是不对的。

第三个呢就是「**SQL 的语法错误**」。我们发现大模型生成 SQL 经常会「会」（混用）一些像 MySQL 等里边的专有语法，但是我们引擎是 Presto 或者 SparkSQL，它写的一个 SQL 在引擎上跑的时候就会报错，这是一个问题。（第二个）问题就是模型的幻觉，它经常会「觉」（生成）一些表里面不存在的 column，甚至会引用其他表里面的 column 来生成 SQL，所以就导致我刚才说的、我们这个语法方面的准确率只有 60% 左右。

第四个问题呢就是「**交互体验差**」。我们做的这个版本其实是一个完整的链路，但是里面其实有几个功能点——像「找数」、「取数」，其实最后还有一个「数据的可视化」，但我没有列出来——这几个功能的入口是相互割裂的。用户要进行一个连续、流畅的分析的过程中，需要在各个入口切来切去，这个体验感非常隔离，等待时间也会比较长。

第五个问题呢就是「**评测缺失**」。我们这个版本只构造了一个非常简单的、有 50 多个数据的一个评测集，这个评测集也脱离了实际的生产环境。我们即使在这个评测集上把这个 Agent 的（分数）调得非常高，我们也不敢把它交给业务去使用。

所以这五大核心问题呢，就开启了整个我们 Text2SQL 的演进之路。我们整个 Text2SQL 的这个演进之路可以分成五次关键的**跃迁**吧，每次跃迁都是由真实的一个生产的痛点来驱动的，这五次跃迁也是我这次分享的一个主题：

- **跃迁 1**：我们从这个单链路的 RAG，变成了一个 **Multi-Agent + 元数据渐进式披露（Progressive Disclosure）**的解决方案，主要是解决找数及（体验）割裂的问题；
- **跃迁 2**：我们引入了用户画像和持久化记忆，从千人一面到个性化，实现了一个跨 session 的上下文共享；
- **跃迁 3**：我们引入了**语义建模**、引入了语义模型和辅助建模的 Agent，主要是为了突破纯大模型生成 Text2SQL 的这个准确率的天花板；
- **跃迁 4**：我们设计了包含文件系统上下文、Sandbox 等工具在内的一系列复杂 Agent 的一个**工程底座**，主要是为了支持一些复杂分析、多步分析，以及长时间执行 Agent 的稳定运行；
- **跃迁 5**：我们引入了 **Skill 机制**，通过 Skill 机制允许用户自己定义一些多步骤的、复杂的、流程化的一些分析主题，实现了从取数走向场景化分析的一个转变。

## 二、Text2SQL 技术演进

### 跃迁 1：Multi-Agent 架构 + 元数据渐进式披露

第一次跃迁里边我们最核心的一个设计，就是这个 **Data Agent 的架构**。整个系统是分了两层的架构。左边这部分呢是我们的 **Supervisor**（背景层），它主要负责背景知识的加载、意图的识别，和任务的拆解、编排和调度；任务拆解之后，它会把对应的任务交接给专业的一个子 Agent。然后右侧呢是我们的专业 Agent 层，分为三个角色：

1. **Data Scope Clarity Agent**（业务域澄清 / 定位）：主要是帮助用户确认数据域（百万表 → 域内数百表）；
2. **Data Discovery Agent**（域内表发现）：主要是在数据域内找到相关的表、或者满足用户需求的表（数百表 → 候选表）；
3. **Generate SQL Agent**（生成 SQL）：它是基于已经找到的数据表的元数据和里面的业务知识，来生成最终的 SQL（候选表 → 最终 SQL）。

这里边还有一个设计，就是我们（加入）的 **Human-in-the-Loop** 机制：在 Data Scope Clarity 找到了相关业务域之后，我们不着急走下一步，而是引入用户确认的环节；在 Data Discovery 找到了相似的表之后，也引入用户的确认，这个用户确认之后我们才会走到第三步。这里边的两层用户确认体系，会确保整个生成的过程（是可控的）。

我们那个第一次跃迁里面第二个重点的设计，是**元数据的渐进式披露（Progressive Disclosure）**。大家知道，RAG 系统的那个数据召回通常是一次性的、相似性向量的方式召回。假设我们一次性召回有十几张表，每张表都有上（百）个字段，那它的这个表描述、表（名）和列描述加在一起，差不多会占用 100K 左右的上下文（token）；但其实在其中真正有用的表可能只有一到三张。这样我们就导致了上下文的严重浪费，更严重的一点是：**大模型在长上下文情况下会出现严重的上下文腐化（degradation）问题**，导致它的效果一个严重的退步。

为了解决这个问题呢，我们利用了那个「**金字塔漏斗**」的原则，引入了三层的元数据披露的这样一个逻辑：

- **L1 业务域定位**：我们会基于用户的意图识别和用户的背景信息，结合公司已有的所有业务域的基础（元）数据，在百万级表中先定位用户的问题所（在）的数据域。定位到数据域的话，我们就会从百万级表的数据范围之内缩小到预（估）的数百张表；
- **L2 域内表发现**：这个主要基于语义检索和热度排名，再结合数据表的一些（业务）规则和表的基础元数据，从数百张表中挑选出一些候选表，然后交由用户确认。只有用户确认之后的候选表，我们才会展开它完整的 schema、完整的字段关联的业务（规则）；
- **L3 深度知识展开**：（候选表 → 完整字段 + 业务规则。）

举个例子说，比如「顾问东南亚地区的昨天的 GMV 是多少」这样一个问题，我们在 L1 阶段会基于刚才说的意图识别和用户背景，定位到我们公司内部的 **marketplace order** 这个业务域；找到业务域之后，我们会在域内进行表的发掘，然后表的检索通常会定位到我们内部的（订单）明细表和每日的 GMV 增量表等一到三张表；这几张表拿出来之后，我们会交给（用户）确认。比方说此时用户选中了「每日 GMV 增量」这张表，我会把这张表的完整的业务规则加载到上下文里面，这样最后传导到 SQL 生成阶段的这个上下文即可控又（准确）。

OK，找到了正确表之后，就会进入我们的 **SQL 的生成阶段**。这里边有两点需要讲。第一个是我们整个 SQL 生成的一个 **workflow**，这个 workflow 呢主要是分四个步骤：

1. **前置分析**：在我们拿到了用户问题及候选表上下文之后，我们首先会引入一些（歧义/缺失检查）。比方说我们候选表里面有多个 GMV 相关的指标，那么我们不会直接把这个（上下文）拋给下一步去生成 SQL，而是通过 Human-in-the-loop 的方式与用户确认，让用户选择他关（注）的 GMV 的口径。只有所有（歧义）都消除之后，我们才会走到下一步；
2. **多路并行生成**：这个是我们参考了很多业界的优秀实践总结出来的方案，我们一共有三路会并行地生成候选 SQL——**路径 1** 是自校正模式，就是生成、反思、然后自己修正，最后交出一个（内定）的 SQL；**路径 2** 是任务分治模式，将一个复杂的任务拆成各个子任务，每个子任务会生成自己的结果，然后最终合成一个 SQL；**路径 3** 就是简单的直接生成；
3. **选优**：这三路生成的 SQL 呢，我们会（有一个）选优环节，从中挑选一个（整理）最优的一个 SQL，然后进入到第四步；
4. **验证与修复**：这一步的话，我们会首先用 SQL 的编译去验证，（看）SQL 是否有语法错误。如果有语法错误呢，我们就会开启一个「修复和再验证」的一个循环。这个修复阶段也是大模型在做的，我们会在（上下文）里面放入一些专用的语法知识，来提升它修复的效果。修复没问题之后，我们会交出最后的 SQL。

这个是整个生成链路的一个过程。

第二个 SQL 生成中相关的，就是它的**上下文**。这个上下文我们分成了四层：

- **L1**：最基础的 **Hive 表元数据**，包含了表名、表描述、字段名、字段描述等等这些基础信息（基础层）；
- **L2**：我们业务域的知识文档，我们内部叫做 **Mart**。这些知识文档呢包含了 Mart 里边的（数仓）建模的一些介绍文档，以及数据的使用、用户帮助文档、一些 FAQ 等等的知识。我们对这部分的知识做了一些语义的压缩和结构化的提（取），最终形成了我们的一个（优质）的专业知识文（档）层（文档层）；
- **L3**：**Topic 运营知识**。我们允许（用户）在这个基础上再去补充一些他们想使用的、或者他们认为要用的一些业务（规则）、术语（映射），形成一个 Topic 维度的一个运营知识（业务层）。Topic 这块后面会讲，我们还可以在 Topic 绑定一些专有的、少量的一些表，或者绑定一些语义模型，这样来规避一些找表阶段引入的一些不确定性；
- **L4**：一些技术类的元数据（**Sample SQL & Data**，样例层），主要包含三类。第一类是我们一些高质量的 SQL 样例，主要是从线上执行的日志里面找到的、基于打分机制挑选出来的一些高质（量样例）；第二呢是用到表的一些 **sample data** 的数据；第三呢是用到表的一些统计数据。统计数据这部分呢主要来源于两个渠道：一个是 Mart 里面的（table status）的一些数据，主要包括数据的（函数）和某些列的一些分布的情况，这个数据不是（每张表）总有的；第二个呢是我们的一个**枚举值挖掘**的一个链路挖掘出来的——我们会扫描现在有热（度）的所有的表，然后去识别哪些字段可能是枚举列、或者（离散）列（世间离赛），然后识别它可能的可有的值，把这个做成一层的知识的一个（沉淀），在 SQL 的生成的过程中提供给大模型去参考。这个知识是非常重要的，它能够帮助（准确生成）。

### 跃迁 2：双层个性化体系

OK，有了这个 Multi-Agent 之后的话，我们整体上的这个效果和体验割裂的问题，是有了很大的改进。但我们接着又遇到一个（新）的问题，就是 **AI 的回答是千篇一（面）的，但是实际使用的场景（因人而异）**。比方说「GMV 为什么下跌」这样一个问题，如果是一个 SG（新加坡）的一个运营，那他其实真正关注的是 SG Marketplace 订单表里面的这个数据，他只关注他自己的数据；如果是一个 global 的一个财务（当然财务可能不会问「为什么下跌」这种数据，只是举一个比方），那他关注的数据应该是一个全局的、财务会（口径）汇总的一个（规范）的数据。其实不同的人问同样的问题，他们的关注点差别（很大）。

如何解决这个问题呢？我们引入了双层的个性化体系。第一层呢是**用户画像（静态）**。我们会从我们的权（限）平台、或者说数据平台的其他位置，拉取用户的一个组织架构、用户的角色、Region、还有数据权（限）等等各种偏静态的数据，让 Agent 能在对话前就加载到上下文里面，这样开口之前就能「认识」用户。举个例子说，我们在线上发现的一个现象：假设这个用户是 SG 的一个运营同学，我们把它放到上下文之后，那 Agent 会倾向于推荐给这个用户来自 SG Marketplace 的相关的数据、相关的表，然后在回答、或者生成 SQL 的过程中，也倾向于在过滤条件里面加上 `Region = SG` 这样的一些过滤条件——这个其实是符合用户预期的。

第二层的个性化体系就是**用户记忆（动态）**，主要是实现一个跨 session 的、持久化的偏好的记忆。我们主要是把用户在我们平台上的一些交互行为，比方说点赞、经常搜索的表、或者曾经做过的口径确认、曾经配置的数据映射等等，持续地持久化到我们的存储里面；然后在用户的新一轮对话过程中，基于一些相似性等的规则给它加载到上下文里面，能够实现它「越用越懂用户」。

### 跃迁 3：语义建模——突破 Text2SQL 准确率天花板

前面有了个性化和我们多路生成 SQL 这（部分），但是我们最终还是发现，**纯大模型来生成 SQL，它的准确率一直很难过我们的预期**。我们分析了一下原因，纯大模型生成 Text2SQL 的话，现在主要有三种挑战：

- 第一个是**业务语义的理解**。比方说，要生成一个正确的 SQL，用户问的是一个 GMV 相关的问题，他要推（断）GMV 该用哪个口径、活跃用户应该怎么定义；但是通常我们的（上下文）里面、表描述里面、或者我们业务的知识里面，是缺少这些业务规则的，或者他在（利用）这个业务规则做（推理）加工的过程中，本身就会累加它的（幻觉），所以这个生成 SQL 的语（义）错误会（频发）；
- 第二个是**表关联推理**。场景里很多数据加工的过程中需要多张表的（Join），那这个 Join 的链路——因为数仓本身复杂、数仓的层级也比较多——那这个 Join 的链路的推导也是一个难点；
- 第三个呢就是 **SQL 物理的实现**。比如说分区怎么选，是一个（Daily）的表或者（DF）的表，那我应该选择查询的分区范围是什么，那函数语法是否正确、多方言的过程中语法错误率很高的问题，都很难（处理）。

这三层（复杂度）叠（加）呢，就是纯大模型生成 SQL 的准确率很难提升的主要原因。基于这个呢，我们也是跟前面分享（的）老师一样，我们引入了**语义模型**作为一个数据抽象层，作为（大）模型和底层的物理数据之间的一层桥梁。这里边主要做了三件事情：

- 第一件事情就是**业务语义映射到物理表字段**（的逻辑）——将业务术语（GMV、活跃用户）映射到物理表字段和计算逻辑；
- 第二个就是**预定义一些标准的指标、维度、过滤条件**，（让 LLM）不再是从零去推理业务逻辑；
- 第三（件）呢就是让语义模型来**封装复杂（性）**——语义模型对外呈现更像是一个 cube、一个统一的宽表的概念，它会封装一些底层的多个表之间的一些（Join）或者过滤条件等，然后它看到的是一个业务的概念，而不是原始的物理（表）。

这样，大模型整个的生成任务的难度大（幅）降低，然后整体上基于（语义）模型的最终的生成的准确率也有了很大（提升）。

举一个例子来说吧，还是以「计算昨天 SG 区域的 GMV 是多少」这样的一个简单的问题来说。如果是纯 Text2SQL 的过程，它需要推很多问题，而且都是串（行）的过程：首先它需要知道 GMV 统计的口径应该是哪一个，然后这个统计的口径对应到哪张物理的表、哪张物理的（字段），然后查询的过程中我们应该（限）定哪些过滤条件、我究竟是应该按下单计算、按成交计算、按支付计算、还是按（缴）付计算等等，这些都是需要大（模型）去推断的，这个过程中任何一步出错，那它生成的（SQL 结果）和取出来的数据就是错了。那如果是基于（语义）模型去做这件事情的话，它只需要生成一个非常简单的 **DSL**，告诉它「我要统计最近一周、或者昨天的 GMV」就是，这样的话整个 DSL 到 SQL 的过程不再由大模型去生成，而是由后边的**语义引擎经过工程的方式**把它翻译成一个（可执行的 SQL）。

OK，刚才我看有的嘉宾也问过类似的问题——那我们现在有了语义模型、我们也有了 **Text-to-DSL**，那么后续所有的 Text2SQL 的生成过程中，是不是都要交给 Text-to-DSL 决定了？这是一个工程的问题。我们最终选择的是一个**混合 Workflow** 的方式。用户的问题过来之后，我们会有一个「意图识别和复杂度评估」，这个地方呢其实是分了两个维度：可以让大（模型）自主地评估，用户也可以配置一些策略去做自主的一些路由。比如说我配置一个「我个人的（这）套数据域里边就一直走语义模型」、或者「一直走（Text2SQL）」，这些都是（可以的）。那如果走我们的 AI 评估呢，会基于用户问题的这个（复杂）度、和我们当前的平台里面建模里面绑定的语义模型去做一个路由：如果它觉得用户的问题是比较简单的、是一个偏探索性的问题，那我们还会走之前的 Text2SQL 的内容；如果它觉得用户问题是一个复杂的计算逻辑，而且恰此时正好有可用的语义模型的话，就会记（录、走）我们的 **Text-to-DSL** 的（路径）。这两条链路最终生成的都是一个物理可执行的 SQL，然后交付给下一步去做 SQL 的取数和可（视化）分析等的过程。

OK，前面是有了我们的语义模型，能够大（幅）提升（Text2SQL）的准确率。但是呢，因为语义模型的构建过程呢是一个非常复杂的、传统的方式呢通常要由数据专家人工地去建，既周期非常长、也非常的费力。我们为了缩（减）这部分工作量，我们设计了一个**辅助语义建模的 Agent**。这个语义建模的 Agent 现在还是（Demo）阶段，它的输入呢主要有三类的元数据：

- 第一类还是我们（表）级别的表结构、字段描述和数仓层级等这些基础的元（数据）；
- 第二类呢是我们现（场/线上）历（史）的一些 SQL，主要是让（它）去学习这些 SQL 的查询模式、一些字（段）（共现）的一些逻辑、一些指标和过滤条件的一个绑定关系、一些常用的聚合方式等；
- 第三（类）呢是我们现在有报表平台已经配置好的一些数据集、看板，可以从看板的定义里面学习一些维度和指标的配置，从数据集里边可以学习一些指标的计算口径等等。

有了这些信息的话，我们基于用户的意图、或者建（模）的意图，语义建模 Agent 呢会做四件事情：第一件事情呢是**指标推（荐）**，第二个是一些**维度的识别**，第三个呢是**关联路径的发现**，最后呢是一些（术）语关系的识别和（映射）的补（全）。语义建模 Agent 呢生成的是一个语义模型的**草案**，这个草案是不能直接上线的，我们会把它交给（擅长）建模的数据专家，由他来审核、修改、确认；确认没有问题之后，我们（再）上到线上，上到线上之后再绑定到我们的 Agent，来支持这个基于（语义）模型的 Text-to-DSL。整体上的思路就是：我们通过一个辅助建模的工具来降低整个建模的复杂度，但是最终语义模型的这个质量还是有数据专家来把控。

OK，前面讲的是语义（建模）的过程，这一（部）讲的是我们在生产上这个语义模型是如何持续优化的过程。我们做 Data Agent 的过程中，应该很（多）同学也有相似的（体会）：我们很难一步把它做成一个非常完美的一个（版本）、或者是一个非常完美的语义模型，（如果）现在它的准确率一直（不）很高，它更像是一个（实习生）、或者是一个刚（招）过来的、（过）了试用期的员工，它需要我们在（试用）期阶段呢需要 mentor 不断地去辅助和优化，优化到一定程度之后才能达到（线上）可用、或者准确率能达到一定的指标。所以我们建了这样一个四步的一个循环：

1. 第一步是刚才讲的 **AI 辅助建模**；
2. 第二步呢是 AI 这个建好的模型放到线上支持 DSL 的查询，但是我们会打上一些（beta）的一些标签；
3. 第三步呢，线上用户的 AI 输出的结果、以及线上用户的一些反馈信息会回流回来，找到数据专家手里，由专家 review 和审核。在 review 和审核过程中，它会发现语义模型存在的一些缺陷和问题，从而去优化语义模型；
4. 优化后的模型重新上线，上线之后的话，这样就形成一个「**建模 → 查询 → 验证 → 优化**」的一个反馈（循环）。

整个反馈机制运营起来之后，可以保证我们的模型在线上持续的正常（运行）。

## 三、Data Agent 工程体系

OK，这是语义模型和循环优化部分。前面的 Multi-Agent、语义模型、个性化等都是为了解决 AI 的准确性的问题。AI 的准确性解决了之后的话，第三章是我们的 **Data Agent 的工程体系**，这个主要是保证我们的 AI Agent 能够在线上的三四千人在用的一个生产环境中稳定运行，又有（完整的）评测和运营闭环的这样一个工程体系。

这个是我们（的）Data Agent 工程体系的全貌，整体上是分成三个大部分，分别是**技术体系、评测体系和运营体系**。技术体系呢我们分成了六大块：有知识管理、有文件系统上下文、有隔离环境、Agent 工具箱、还有 Agent Skills 和个性化。这里我挑两个重点的讲一下。

第一个是**文件系统的上下文**。为什么要做文件系统上下文？因为 Data Agent 的场景下，模型的上下文是比一般的 Text2SQL Agent 要大得多的——我们有表的基础的元（数据）、（表的）schema、表的（业务）规则，还有个性化的数据、以及用户补充的（等级）（那个）语义（模型）（Topic）里的一些口径等等数据。这些数据如果一（股）脑都放到大模型的上下文里面，很容易（撑爆）上下文，也很容易再次触发这个「上下文（腐）化」的问题。我们的做法是（引入）文件系统。这个文件系统可能是一个抽象的文件系统，你可以理解成是一个文件系统的接口，那后面的存储可以是（对象存储）、也可以是分（布式）文件系统。但是我们把知识是按照一种层级的方式、（树）级的（树）的方式去分层地去组织，比方说我们前面讲过的这个金字塔漏斗（式披露）跟这点是相辅相成的：我们在最开始的阶段会加载最上层的一些元数据，比方说用户的用户画像信息；然后在确定数据域的过程中呢，我们会加载 L1 的数据域的、所有数据域的业务知识；然后呢在找到真正的、用户确认表之后，才会展开表的最详细的信息以及它的一些（业务）规（则）。这中间呢，找（表）之后呢，那些上下文里面呢——比方说数据域的一些信息和其他的一些不需要的信息，我们会（择机）地从窗口中 **offload** 下来。

对，这个是文件系统上下文（的）一（个用途）；另外一点呢，就是文件系统上下文呢可以帮我们去（承）（接）多步分析的一些中间结（果）。比方说我们做场景分析或（归因）分析，通常第一步是取数，取到数据之后，后期的 3、4、5、6 这些步骤都会依赖我们取到的数据。这个数据能不能一直存在母星（上下文）里边？如果一直存在（母星/上下文）上，它的窗口会被严重地占用。我们现在的做法是：我们取到的数据以一个标准的 **DataFrame** 的方式把它存到文件（系统）里面，（模型）能看到的只是这个 DataFrame 的一个 **reference**、一个 path（是虚拟（文件）系统里面一个 path）。下面每一步、每（个）工具需要使用的时候，大模型不需要传递这种复杂的、超级大的一个 DataFrame，只需要（传）这个 reference。对，这个是文件系统。

另外一个是**隔离环境**，隔离环境也就是 **Sandbox**。这个主要是给每个（子）Agent 提供一个权（限）隔离和资源隔离的一个（沙）箱，保证整体运行的过程中呢是安全可控的。同时呢，我们给模型提供的两个杀手级的工具——像（SQL）执行和 Python 执行——这些工具都是在沙箱（里）运（行），防止模型、或者防止一些恶意的（人）利用这种强大的工具做一些破坏的事情。

OK，这是技术体系。**评测体系**呢，这块包含了评测集的建设、结果评分和评估执行这三部分。测评集的建设上呢，我们也踩了不少的坑。刚才介绍我们最早的一版评估集，其实是 QA 帮忙做的，只有五六条数据，然后也脱离业务场景，然后我们没法基于这个评测集得出的数据去优化一个面向生产的一个（模型）。所以最后（我们走了很多弯路），我们想到了一个很好的方法，就是**基于线上真实（经）常使用的 SQL 来构造（评测）集**。首先我们会面向我们的分析主题、或者面向我们重点优化的一些主题去做表的选择；选择了表之后，我们会去线上去搜索——通过线上日志去搜索在线上执行成功的、以及在线上（频繁）执行的一系列的 SQL（已经来源于是一些（要）成熟稳定的报表平台的一些 SQL）；这些 SQL 呢，我们让大模型生成它的自然语言的问题，这个生成的问题呢就交给人去（审核），通过之后我们（收进）到我们的（评测集）里面。经过这个（阶）段呢，我们最后积累了数千条（三四千条）数据吧，（涵盖）不同的分析主题，也有不同的分析（难）度，我们以这个作为我们的（基线）评测集。这是评测（集）部分。

**结果比较**这一部分呢，我们也做了很多的探索。首先我们尝试了通过（语法树 AST）的比较来比较两（个）SQL（是否）（等价），后来我们发现，其实同样的语（义）逻辑，它的表达方式是多种多样的，不同的表达方式对应了不同的语法树，所以这个比较的效果会很差。第二个呢，我们选择了基于大模型的一个**准确性比较**，这个准确性比较呢在一些简单的 SQL、或者是（逻辑）比较（简）（洁）的 SQL 下是效果比较好的，但是在一些复杂的场景、或者有多种表达方式的一些 SQL 的话，它的分数比较差（主要是通过人工比较和 LLM 比较的交叉对比，我们发现的这个现象）。所以最终我们还是决定以**执行准确性比较**为主。这（种）（比较）我们要解决一些问题，比方说：AI 生成的 SQL 可能会取一个别名，然后用户的问题中可能没有特别细的描述、我的时间字段（时间列）应该用（什么）format，那我生成的 SQL 的时间字段的格式是灵活的、不同的格式也都是对的，所以我们去解决这些问题——我们做了一个**时间字段的规（整）**，我们也做了一个不同列之间通过类似**编辑距离**的那种方式去计算它列的（相似）性的问题；第二个是针对一些浮点类型的数据、或者是经过类型转（换）类的数据，做了一个基于**容差**的一个比较策略。对，最终的话我们会把我们的结果比较做成工具，然后放在我们整个评估的 pipeline 里面，平台的包括知识库、包括 Agent、包括模型的任何改动，我们都可以很容易地触发一个线（上）的评估，来比较改动前后的效果。对，这是评测体系。

**运营体系**这块的话我们后（面）会有一个章节专门地（讲）整个运营（闭环）体系。这个图最下面呢放了两个（模块），是 **LLM 基座**和（容器）平台。我们公司现在的 Data Agent LLM 呢是混用了商业模型的，主要是像 **OpenAI 和 Gemini** 都会在用；然后未来呢，我们会考虑去替（换）成一些自己训练、或（微调）的一些模型。

OK，在讲运营体系之前，再插一（讲）我们之前也做的一个非常重要的事情，就是**元数据治理**。这部分呢，首先我们在开始做 Text2SQL 的过程中，我们就发现了公司平台上的大量的 Hive 表其实是完全没有表描述和列描述的。那时候我们就想，大模型在这种完全没有知识、只有表名的情况下，是很难找到一个符合他要求、或者符合用户语（义）的这个正确的一个表结果，所以我们就同步启动了这个元数据治理的过程。但平台上百万级别的表，这个人工治理的成本是非常高的，所以我们设计了这种 **AI 和人工配合的四步**：

1. 第一步呢是按照业务过程和一些数仓层（级）对一些表进行**分组（Table Group）**，比方说相同业务语（义）的 D（Daily）表和 DF 表会放到一起，相同业务语（义）的、拆分的一些表我们也会放到一起，这同一个 Group 的表会共享相似的（业务）语（义）；
2. 然后我们在生成——我们会以表组为基础交给 AI 去**生成描述**。生成描述的阶段，我们会依赖于表自身的一些名字（信）息，但我们更多的会依赖于这个业务（域）内的一些建模相关的知识、和用户帮助相关的文档及一些 FAQ 的知识，然后一起生成一个 candidate 的表描述和列描述；
3. 这里的表描述和列描述不能直接上线，我们会交给**业务方的人、或者表的（Owner）去 review**，他们会（逐）条地审查生（成）的表（描）述结果，选择采纳、修改或补充。只有经过人工（确认）之后的这些（产）出，我们才会上（到）线上；
4. 第四点呢是我们做过的一个非常重要的一个动作，就是**血缘扩散**：我们已经治理好的一些核心表，通过血缘关系、和血缘之间的一个计算逻辑（就 SQL 之间的这个计算逻辑），会自动地扩散到下游，自动地为下游生（成）一些表描述。这个表描述也会需要经过业务方的 review 和修改、确认。

对，这个是整个（治理的过程）。下面呢是我们整个治理前后的一个效果的比较，首先看几组数字吧：第一，**AI 生成语（义）描述直接被业务方采纳、没有（修改）的比例有 70%**，说明我们设计的这个链路还是有正向收益的；第二个呢是对于一个中规模的表（像 40 列的表），它的治理时间会从 30 分钟缩小到 10 分钟左右，这个**时间成本节省了 67%**；第三个呢是人工治理——这就是血缘扩散机制了——**人工治理了 2000 张表，通过这个血缘扩散机制扩散治理了 15 万张表以上**（效率提升 642%）；第四点呢是我们治理前后找表阶段的一个准确度的提升，**最大能提升 15 个百分点左右**。这个数据也充分地说明了：**在元数据的质量、或者元数据的丰富程度，对于我们找（表）阶段这个 Agent 是有很大的帮助的**。

所以这里边可以总结出一个经验：我们做 Data Agent，这个 Data Agent 是一个更广的概念，不能只考虑这个模型好不好、不能只考虑我们的工程是什么样，像**数据的质量这一部分也是非常重要的**。通常数据质量的（这）（块）优化是一个脏活累活，这个（活）也是要做的。

OK，下面就是**运营闭环**这部分。运营闭环（之）（前），我们首先发现了一个事实吧，就是「**线上的效果 ≠ 线下（评测）的效果**」。线下的评测集的构建，虽然也是基于线上数据去构建的，但是呢，随着不断迭代，这个分数总会越来越高的；但是上到线上之后，（分数的问题）（是）前面（忘化了）（——线上运行的效果）它通常跟（线下）评估的（结果）会越来越（有差距）。我们运营（闭环）是这样做的，我们做了三步：

1. 第一个是基于线上反馈采集和人工标注相结合的**准确率评估**。线上反馈采集包含了两部分：一部分是**隐式反馈**，比方说用户在平台上拷贝执行的（SQL）、追问、纠正等等行为；另外一个就是**显式反馈**，就是用户（点赞点踩）的数据。第三（部分）呢是我们数据（同学）在后台的一个对结果的标注。这三项结合，能够提升这个（线上）准确率（评估）的效率，同时能够（收敛）这个准（确率）；
2. 第二部分呢是**知识管理和 Topic 运营**。Topic 运营刚才也提了一遍，但是因为我们刚才没有讲（Topic）建（模）这部分，所以这里重点说一下。我们的 **Topic** 相当（于）是一个私（域）的（优质）的概念：BI 同学、或者是有数据分析需求的同学，可以把它经常使用的、他认为这些数据能解决他问题的这些表，放到一个独立的 Topic 里面，形成面向他自己的一个私（域）的一个数据组。这样的话我们会绕开整个找表的问题；同时你通过语义建模方式建（的）模型也可以绑定到一个 Topic，那这样的话所有的数据查询是走（语义）模型、不会再走（找表），也避免了 Text2SQL 的一个准确率的一些干扰；
3. 第三步呢是**效果验证和数据回流**。我们做了后台，后台有一个 **Test Session**，能快速验证用户在 Topic 里面补充的业务知识、业务规则的效果，如果效果好的话就可以直接上线；效果的话（整体的效果）我们提供了看板和监控。另外一点呢就是标注数据和用户的这些记忆，我们会回（流）到我们的算法平台那边，算法的同学现在正在帮我们训练一个我们自（有）数据的一个自（有）模型。

## 四、基于 Skill 的场景化分析

前面讲到的是运行稳不稳的问题、以及最前面讲到的是取（数）准不准的问题。第四部（分）我会讲**基于 Skill 的场景化分析**的一个支持，这个是将我们的这个 Data Agent 从取（数）工具变成一个支持复杂分析场景的 Agent 的一个关键的步骤。

首先我们做了一个「让 Agent 做自由（不规定）、自由分析探索」的一个实验。我们发现在做自由分析探索的过程中，它会有很大的问题：首先它经常会（跳）过一些关键维度的下（钻）和关键维度的交叉分析，直接去给结论。有时候这个结论它是对的，但是很多情况这个结论是不对的。我们（去）问一下我们专业的 BI 的（同学），这个结论无论对还是不对，他们都是不敢用的——因为整个过程他们不知道这个数据是怎么做出来的，数据不可验证的话，那整个结论（即使）是对的，他们也不敢用。

**第一个是 Agent Harness 的演进。** 我现在理解 Harness 其实是 Agent 的一个操作系统。怎么去形象地理解 Harness？**Agent = LLM + Harness**，所以 Agent 减去 LLM，所有的东西都是 Harness。那是不是「新（瓶）（装）（旧）（酒）」呢？（答案）是、也不是。「是」的部分是——我们之前做的很多工程工作，其实都是 Harness 的范畴；但是这个范畴里面又分成两部分：有一部分工作呢，它的边际效益会越来越低，比方说我们调 prompt、我们优化那个工具的调用的一些逻辑和（链路），这个随着模型自身能力的进化，它的（收）益会越来越低；但是有一部分工作的话，随着模型（无论）（怎么）进化都是要做的、要（携带）的，而且未来可能会引发出更好的一些方案，比方说 **State（状态）或（Context）（管理）**。另外一个就是一些工具的**「个性化到通用化」的一个转变**：我们以前给大（模）型做工具是这样，比如说大（模）型它需要一个做加法的能力，我们会给它做一个加法工具绑定（能）（挂载）；另一个呢是假如它需要做减法，我们又给它做了一个做减法的工具，放（到）我们的（上下文）；那未来的大模型的工具应该是一个通用的（场景），比如说我们给他一台电脑、给它一个可以操作、可以反馈的环境，这一个电脑和一个环境是它的一个（工具），那通过电脑的标准化接口可以自由地排列组合去解决很多很多的问题。这个是现在像（某厂商）的最新的模型从 **4.5、4.6** 开始已经明显地看出它有这个能力。对，就是这部分。
