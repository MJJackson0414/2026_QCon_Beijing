## Harness 的兩種定義（狹義與廣義）

## Spec：什麼是真正的 Spec？

然後我們回頭會去講：如果我們要用好 AI Coding 這件事情，我們會想從「提示詞管理」到「上下文管理」到各種各樣的 Spec……但回過頭來說，是不是說 Harness 時代了、所以提示（詞）不重要了？其實回過頭來說絕對不是這樣。

那 Spec 這個東西——我認為 **Spec 其實是所謂 Harness 的基礎**：你連 Spec 都做不好的話，那你又怎麼做好 Harness 呢？你只是靠你的 programming 嘛。因為有那麼多的東西的話，其實你不論如何還是從 Spec 去做的。但是有一個點我覺得大家又沒（認）（真）（想）：（誰）可以很好地回答出來「什麼是真正意義上的 Spec」？Spec 是需求文檔嘛？是不是我把一個需求文檔寫得足夠細，然後我產生的代碼質量一定會更高？或者說 Spec 是不是「我把它寫成了一個很複雜很複雜的、（跟）代碼基本上平（行）的東西」——我代碼有幾十萬行，然後我的 Spec 也基本上把這東西描述清楚了，才能夠去做好一件事情？其實我相信在做這麼多的同學，對 Spec 的理解肯定都是有很大不一樣的地方。

那麼回過頭來，我想問第一個問題：什麼是 Spec？其實我的答案是——**Spec 其實是「和 AI 交流」的一個工具**。我舉個比較有意思的故事：我跟一個做（獨立/出海）（App）的同學交流，他說他三個月寫了 150 個 App。我想想看，在這種場景裡面，無論是什麼東西可能對他來說都不重要的——因為無論是代碼也好、Spec 也好、甚至他運行時候的那個 App 也好，他自己都沒怎麼（用）（（，因為在這種場景裡面其實是沒有辦法去真正用 Spec 的。那麼 Spec，你想想看：如果我們去讓 AI 寫個代碼，它其實在寫自己的「執行規劃」——那這個執行規劃，到後面的（複）現性、或者（歸）人的理解，很多時候是沒有意義的。它會寫「我先寫 DAO、再寫 Service、再寫 Controller、再寫什麼東西」，它這個其實是自己把這個長程任務做了一個拆分——我認為這種東西還不（足）（以）成為 Spec。真正意義上的 Spec 其實是一種 **Harness 的模式**：就是「如何讓人可以更好地去管理到這個 AI」。

那麼第二個問題：為什麼需要 Spec？回頭想「軟件跟腳本的區別」就能大概理解為什麼我們是需要（Spec）的。如果你只是寫一個腳本，大概率其實你就是「我把需求扔進去、（跑）（了）之後、測完了 TDD 的模式做完（就行）」；但如果你需要「長期維護它、多人協作它、你過了半年之後你還要（改）它」的時候，這個時候 Spec 就比較重要了。

## AI Coding 是低門檻的，Spec Coding 卻未必

那麼回過頭來說，我們會得出一個結論：**AI Coding 的門檻一定是很低的**。現在 AI Coding 已經不是程序員的（專屬）能力了，已經基本上是包括業務人員也好、或者是一些甚至一行代碼都（不）（會）（（的）（（（（同學也好，所有人的一個工具。但是 **Spec Coding 我相信要做好的話，還是要有很強的一個工（程）基礎**。這裡面就會有好多問題：

第一，剛才說到的——**怎麼定義 Spec**？如果你自身對於「結構、設計」這個東西的理解都是比較淺的話，其實你很難去跟 AI 共創出一個「你這個軟件開發中比較適合的整體方向」，你其實如果被它帶著走的話，某種程度上說是很難去做好這件事情的（需要本身對架構知識有一定了解，而不只是被動接受 AI 輸出）。

第二，**如何維護好 Spec**？傳統的 Spec 一定是一個「以文字/文本驅動」的東西，那文本其實肯定是有「語（義）不（清）的地方、有定義混亂的地方、有前後不一致的地方」。（長）遠來說，如果你（的 Spec）跟你的代碼越來越「漂移」的時候，然後你的上下文其實還多了一個——你原來給 AI 的上下文只是你的代碼，然後你再加上了一個所謂的「這種帶有歧義的 Spec」，那麼你給 AI 其實是兩個東西，那到底 AI 在這種情況下如何去抉擇？某種程度上說，很有可能「一個不好的 Spec 反而會毀掉了你的 Spec Coding」（現實業務的持續變更會導致規約迅速熵增，保持長期的邏輯自洽、（比）修補代碼補丁更難）。

第三，**如何協作 Spec**？剛才上來的時候我跟我前同事就在聊：現在很多 AI Coding 的情況是「一個人提（效）10 倍、十個人提（效）一倍、然後 100 個人可能就提（效）（（（」。第一，它一定是提效的，這個沒有人去爭議；第二，但是我畢竟（（（很多的軟件開發其實不是一個人開發、也不是在一個生命週期內開發，那麼我如何去協作這個 Spec？兩個人會不會同時改到同一個東西？那後面我們難道要去 merge 一下我們的這個文本？（除了 Merge 代碼，還需要 Merge Spec 麼？）這裡面有很多細節問題，在你真實的使用中就會碰到。

第四，**如何驗證 Spec**？你的 Spec 本身的邏輯完整性是不是好的？第二個，你的代碼寫出來之後，你的 Spec 跟你的代碼之間的映射關係又是怎麼樣的？我相信雖然說現在 Opus 4.7 出來，但大家用過也知道，並不是說它可以真正意義上完全地還原到你想要做的一件事情（規約層缺乏像編譯器一樣的硬性物理反饋，導致 Spec 本身會慢慢變得矛盾重重）。

## Spec 的發展階段與 DSL

那麼 Spec 其實在業內有三個所謂的發展階段。第一個階段是「**Spec-for-（prompt）**」——這種東西相對來說比較容易理解，就是「我通過寫一個比較複雜的 Spec 然後給 AI，而不是純粹的 Vibe 模式（只給一個含糊的指令）」。然後「**Spec-anchor**」——這個可能跟 **Kiro** 會有點（關係）：去年 8 月份 Kiro 發布的時候，其實在整個業內引起了蠻大的反響，就是它希望「以 Spec 作為一種 driven（驅動），可以保證這個 Spec 和（代碼）之間的映射關係、存在著一種軟約束的模式，可以不斷地去改進代碼」。

那麼 Spec 是不是到這裡就結束了呢？其實（長）遠來說，很多人說「以後代碼就沒那麼重要了」——這句話是對的還是錯的呢？其實我們回到我們第一頁 PPT 你就看到了：這個觀點其實是有一定道理的。我剛才講的「左移」，對吧，又有人講「右移」——你看左邊移一點、右邊移一點，（中）（間）（就）（把）（（（（給壓縮掉了，那後面的代碼這件事情的確就沒那麼重要了。但是回過頭來說，那麼真正能承載這個軟件的東西是什麼呢？除了一開始的業務需求文檔之外，我認為這個 **Spec** 其實某種程度上說就可以去做「跟代碼（映射）關係的一種描述」的東西。

那麼我們當時的思路是什麼樣的呢？就是在所有的行業裡面，你基本上都可以看到一個現實：我要去描述一個東西——一開始可能就是在傳統的比如建築行業裡面，我要去建房子，那麼每個人建房子的時候去描述這個房子的模（型），但（大家）會發現這件事情其實是不太利於（房）（子）（的）交流的。比如我這個建築隊建完了之後，B 建築隊來維護的時候，他要去看之前的設計圖（紙）的時候就會有很大的困擾，對吧？那這個問題在所有的工業領域裡面要解決的方案其實非常簡單——他們就是去做 **DSL**（domain-specific language），就是「我在某一個領域裡面，通過一個嚴格約束的表達」。如果我們能找到這個東西的話，那其實我們就應該用這個東西來表達我們整個想要去做的事情。我相信今天無論是我們去做鞋子的（模）（具）、還是去建一個房子，其實它肯定都是有他們領域內的一個「通用語言」的。

那麼回過頭來說，軟件開發這件事情是不是某種程度上說也有這種東西呢？其實你可以看到，我們整個軟件開發（（（（其實有一點「復古朝回來」的——我們在很早期、其實是在 90 多年代的時候，其實就已經在提 **MDD** 也好、或者建模驅動也好，它這種時候就已經開始有一定的「通過建模來驅動標準化、建模來驅動開發」這個東西。但是當時的問題其實也很簡單：**你建模的產物和你的代碼之間的映射關係，其實是非常難以維（護）的**，所以基本上這個東西到了後面慢慢的就沒人用了。回過頭來說，是不是因為這條路完全走死掉了？其實不是——那個時代提出來的觀點，和現在的軟件工程的本源問題其實是沒有發生本質性變化的，那麼那個時（代）提出來的觀點在 AI 時代很有可能就被很好地解決了、或者被很大程度上去緩解掉它裡面一些不太好的東西。這其實就是（剛才）黃東旭提到的這種「UNIX 時代回歸」也好、或者是「上古（時代）回歸」——歷史一致（是）（螺旋）發展，只是說在不同的新技術下面，它可能會（煥）發出不同（層面）的東西。

我們可以舉一個簡單的例子。首先，這個東西非常簡單，在服務端應該都能看到：我就是（傳）（回）一個對象。你在需求文檔裡面會怎麼描述這件事情？你可以說「我有一個用戶、加了一個公司信息、還要把他的設（備）設定信息返回來」，或者需求文檔根本就不寫這句話、「我就是要一個東西你自己（（（吧」。但這種東西你想想看，如果這是個「多層嵌套」的、如果它同一個實體還有不同的（（（（的話，你用語言描述起來其實都很痛。那個時候為什麼大家不回頭想「我有沒有一個更簡潔的、行業裡面都可以公認的一種模式」，我就用這種東西來描述一個對象的組成？這種組成裡面既包含了（（（——你看這樣描述的話有很多好（處）：一旦你熟悉這種東西，你去看這個對象的時候，很多含義它是非常非常清晰的。它某種程度上說跟代碼又不太一樣：如果只是代碼的話，你可能會看到一個數據結構；但如果你把它定義為「在某個領域的一個特定（DSL）語言」的話，它會把你的數據來源、數據的關聯關係全部都帶進去描述。那麼這種東西其實一定是「超越代碼」的——因為代碼要描述這件事情的話，一定是在多個文件裡面（有些是數據組裝的文件、有些是數據填充的文件、有些是數據格式表達的文件）去做這件事情。

那麼我覺得在這種模式下面，我們可以用一種很嚴格的模式去共同約束我們某一個領域去做的事情——很有可能其實是「代（碼）（（（語言的體系的一次提升」，而不是（（（。自然語言它有它的靈活性所在（就跟我引用的 Dijkstra 提到的東西一樣），但是對於我們去做專業的——我如果是專業做（前）（端）、或是專業做後端、或專業去做 BI 的時候，我們還是希望形成一個「無歧義的、你可以準確表達的、容易看的」一套（東西）。

比如我舉了一個例子：原來在（網易）雲音樂裡面有一些「分頁」——分頁可能有比如「是不是可以去加載更多」這麼一個東西，然後它有個 `hasNext`。那麼寫代碼怎麼寫呢？寫（代）碼是「你這頁顯示 n 個、我就取 n+1 個，如果那個 n+1 （存在），（（（（，然後再一層層包出來」。其實你看到一個組織裡面、或者一個行業裡面，一定有很多類似的一套模式，它其實是有「標準化表達」的。你要描述這個東西的時候，它可能會有一些「自由度」，這些自由度很有可能就可以變成你所謂那條 DSL 的一些參數。如果大家都可以在這種語（境）下去描述的時候，你就會發現「不再是散亂的」——因為（（（你只要越到上層去描述這個東西的話，你會發現「每個人的實現代碼邏輯自由度都不太一樣」的時候，你這個代碼就變得難以維護、而且難以理解。它缺少掉了一個信息：就是說「我只有最後的 How，但是沒有 What」。那麼 DSL 這個東西，它其實很大的作用是在「把你的 How 和 What 之間進行了一個粘合」，而且是用一個標準化的模式（粘合）。

我們可以看一下它的一些好（處）。第一，DSL 是一個「含義明確、（可）讀性很強」的東西——這個東西是不是沒有任何的（歧義）？而且如果你稍微去研究一下，有句話叫「一圖勝萬（言）」，某種程度上說你看到這個東西了、大家就沒有任何的分歧了，只有「對和錯」的問題了，而不是說上來可能大家理解上面就已經錯掉（了）。然後它的細節和可維護性其實相對來說也會比較高。然後你可以在裡面把你剛才我說的 What 和 How 相結合的東西認真地理解出來，而不是「要麼 What、要麼 How，然後兩者之間的 gap 到底誰來連接」存在的一個問題。**所謂的「設計」，其實本質上來說就是把 What 和 How 給你做了一個中間的橋樑，這個就是我說的所謂的 DSL。** 我剛才問的另外一個問題——我對 Spec 的一個理解，就是說它既不是單純的描述 What、也不是單純的描述 How。這種東西（原始需求）都有更適合的東西描述：需求一定（（（（——資（然）語言（（，其實也可以（用）DSL（（，但是它原始的、最原始的動機肯定不太可能是一個 DSL，而是說「我想做一個更好的房子」；但是我除了那個「磚塊」（那個代碼）是我最終的產物之外，其實那個「設計圖紙」就是把我最開始想（的）一個大房子、和我最後做的那個比較好的房子之間給它聯合起來。

還有一個點，其實是當年做（網易）雲音樂的時候我一直在提的一件事情：我們做複雜系統，大家都知道 CI/CD 這件事情——我整個東西，比如我的環境管理、我的 API 管理、我的測試管理……那其實（現在）大家都在提 **Ontology（本體論）**。我想問一個問題：**研發系統的「本體」到底在哪裡？** 這個問題大家有沒有人想過——是需求文檔嗎？是代碼嗎？是測試用（例）嗎？我覺得很有可能都不（是），因為這些東西都是一個 **IaC**（infrastructure as code）的東西，它很有可能都是一些發散的、或者是一些不可約束、很難傳承、很難比對的東西。我認為 **DSL-Spec 很有可能可以去組合成我們想要的、在整個研發領域裡面的這一套 Ontology**——就是你以這個東西為「（真）（正）的中心」去做你的 CI/CD 也好、或者什麼東西也好，這種是在一個比較大型的公司裡面很容易、比較適合的一套落地。

## Programming：Harness 的最佳範式（Agent + Programming）

那麼我們講的 Harness，其實可以講到第二點——剛才講的是「如何通過這種 Spec 或語言模式去控制 AI」，那麼回過頭來說，我們希望怎麼樣去使用（AI）。

那麼研發這件事情是不是本質上也是一個「長程」的東西？我認為裡面的 programming 成分還是比較（（（（。如果說我們的 DSL-Spec 是成立的話，如果 AI 幫我們去生成 DSL-Spec 的話，那麼其實對於一個組織、或者對一個社區而言，通過「DSL-Spec 去預定義這套 Spec 的一個外框型的代碼」，這個可以大量節省掉你去 review 代碼、和你跟 AI 交互的一些不確定性的問題。那麼我們去做這些事情——就是我們做了一個建模相關的 DDD 也好、或者這些理論相關也好的一個引擎，然後我們去把那個「框架型的結構」做出來了，這個東西是通過 programming 去做的。某種程度上說，我認為這個是（我們）去區別於其他產品的一個比較有意思的 Harness 的實現——因為傳統的 AI Coding 大部分並不會關心到你中間的某套東西，而我們（（（去做一套領域內的 AI Coding 的話，其實我們很容易想到往這個方向去走。

那麼這個東西其實又回到了我剛才說的點：**它是一種「設計時的固化」。** 大家有沒有理解？就是原來我們有「運行時」的東西，然後我們通過（加）（上）一些類型把它變成一種「編譯時」的東西、可以進行編譯時的（校）驗；然後我們又再往前走了——我們的團隊對某些東西是有共識的前提下面，我們就在「設計」的時候去保證了大家做出來的那個代碼又是相對一致的。就是「編譯時保證了運行時的 code 可能是正確的」，同樣的「設計時就保證了你的編譯時的代碼寫出來那個東西是可以長時間維護的」。這個是我們想說的一個比較有意思的實現方案。

## Human-in-the-loop：人什麼時候介入

## DSL-Spec 的缺陷

當然我們回過頭來說，那 DSL-Spec 這個事情有沒有缺陷？首先第一個肯定（有）缺陷，沒有缺陷都去做了。第一個，它最大的缺陷就是它是一個所謂 domain（領域）的——在一個 domain 裡面才有用的東西。其實我看了一下，海外有一個叫 **Tessl** 的產品，他也是想去做一些 DSL、或者一些結構化的驅動的東西，但是感覺它其實在社區裡面影響也不是特別好，因為（我覺得）他想去做「DSL 通用（（（」，但其實軟件開發有沒有「通用（（（」呢？因為我原來比如 7800 名研發裡面有多少種分類，對吧？光是這種職能分類就非常多，每個領域裡面能描述的軟件模式、甚至每個組織裡面可能都存在一些差異性。但這並不代表說「DSL 這個方向是有問題的」，只是說「有沒有可以某一部分是行業裡面公認的一種建模方式，然後某一部分可能是我這個企業裡面自身的一些描述模式」——你只有不斷地去建立這種「分層的 DSL 模式」、大家（共）建這套東西的話，才有可能可以讓這個事情繼續往前走。

第二個東西，其實提到了 **Programming**——Programming 有沒有問題呢？其實它同樣出現了問題。Programming 它增加的（是）它的 Harness 能力，它生成的代碼的約束性和質量的確會變高；但同樣碰到一個問題：這個生成的代碼結構也好、或者裡面的有些習慣也好，是不是符合所有人的需求？這裡面同樣是打問號的，可以很坦誠地講。那麼回過頭想，我們為什麼會在開篇的時候就講「設計時」——其實你想想看，現在 AI 這麼強了，他為什麼不能把這種 Programming 的描述維護在「最前面」、通過 AI 來維護這種 Programming 的（遷）（移）？那這樣的話，其實就是說「我讓 AI 的能力不是只在最後一刻」——不是每個程序員在最後才寫到最後一（趟）代碼的時候去發揮他的（泛）（化）、或者他很強的（（（能力，而是說「我在設計的時候就讓他去做這件事情」。這樣的話，我可以嘗試著去快速地定義出「我真正在這個組織裡面、或者在這個領域裡面固化下來的這種軟件結構」，這種（遷）（移）的話很有可能才是一個技術領域裡面比較好的實現。所以我們會去嘗試把我們這套東西去開源，也希望大家有興趣的同學可以一起去共建、或者互相討論一下這個問題的發展方向。

## 未來觀點（CTO 十年的思考）

我再簡單講一下。因為我也是做了所謂十年的 CTO，所以現在很多技術同學問我對這個東西的一些未來的看法。首先第一個，我個人不是做基（礎）（模）（型）的，我不去預測 AGI 什麼時候到來，我只預測一下我能看到的。
