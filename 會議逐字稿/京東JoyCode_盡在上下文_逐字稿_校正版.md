## 一、企業在編碼場景面臨的核心挑戰

京東主要是——我們內部會有大量的不同業務，我們有零售、有物流、有健康等等，所以我們的**業務場景是非常複雜的**：內部會有各種各樣不同的項目，有大有小，所以我們對「知識的來源」、也就是 coding 知識的來源會有一個很高的要求。

第二個，我們的**用戶畫像是非常豐富的**：從用戶畫像數據來分析，我們有普通的開發者，再到（資深）架構師、再到算法（工程師），甚至非開發的同學也會去用我們的 JoyCode，比如像財務同學、法務同學等。

第三個，我們的**複雜（長）任務會比較多**：因為剛才提到我們大型的項目會（涉及）非常多（文件/服務），所以我們在面臨這種複雜任務的時候，很容易造成「上下文爆炸」、然後頻繁地去壓縮這種問題。

第四個，就是**超大（代）（碼）（倉）的（理解）**：我們如何在這種超大（代碼倉）裡面快速地、精準地定位、塞入有效的上下（文），其實也是我們面臨的一個主要問題。

## 二、JoyCode 的創新解決方案

### 2.1 提供豐富的企業知識增強來源

那我們怎麼去解決呢？第一個就是我們提供豐富的企業知識增強來源，主要有這四個方面（我們還有其他的，就不重點說了）：第一個是非常常見的 **JoySpace** 在線企業文檔的知識增強；第二個是我們**多模態的、結構化的知識增強（JoyContext）**；第三個是我們的**代碼知識增強（CodeWiki）**；第四個是我們**面向前端的「設計稿 → 企業組件」這條通路的（知識）增（強，即 D2C）**。

**（JoySpace 在線文檔）：** 這裡給大家演示的就是我們在 JoySpace 如何去獲取這個內容的，其實也非（常）方便，這個也是比較通用的做法。

**（JoyContext 與 JoyAgent）：** 第二個就是我們的 **JoyContext** 以及 **JoyAgent**，這兩部分主要是給我們提供多模態的知識增強。它們的區（別）在於：JoyContext 是一個「知識檢索」，它僅提供檢索的能力——也就是我們把文檔也好、圖片也好、CSV、PDF 等這類（文件）（傳）上去之後，它提供一個檢索的結果，那我們內部 JoyCode 會跟它有一個知識庫的（掛）（接），這樣就可以起到一個知識增強的作用。而 **JoyAgent** 跟它的一個很大區別在於：它把這些知識變成「可以編排」的，也就是它是以「（工作流）」進行接入，所以它會相對於 JoyContext 更加豐富一些，然後用戶也可以去自定義自己的一些工作流、Skills、MCP 等等。這個就是我們 JoyAgent 的一個工作流編排的示例，這個是 JoyContext 整體提供的知識（能力）。

**（CodeWiki 代碼知識增強）：** 第三塊是我們做得比較重點的一塊，就是我們的 **CodeWiki**。CodeWiki 簡單理解它就是我們的「代碼知識」，它的（生）（成）方式就是通過 AI 在後台不停地讀取我們的代碼，然後去生成這種高層次的文檔，比如像設計文檔、架構文檔、核心模塊文檔、甚至我們的新手（引）導等。這類文檔對我們（智能體）也是有（幫）（助）的。大家可以簡單看一下這個演示：比如我們問它「當前系統架構是什麼」，我們的上下文（引擎）就會把它檢索回來，並且這個結果是跟我們的可（視）化（聯）動的——你可以直接通過這個上下文（檢索）的結果看到對應的文檔。並且這個知識是注入到我們的（上下文）的。在我們的左側是有這樣一個完整的 CodeWiki 目錄，大家不管是新人也好、還是日常有需求也好，都可以通過這個文檔去（找）自己想要的高階知識。

並且我們整個 Wiki 是在「空閒時」跑的——比方說我們後半夜、凌晨這種空閒的算力，我們自部署的模型會把它利用起來。另外在（企業）內部有一個非常大的好處：就是我們的項目往往都是「多人共用」的，也就是我們在空閒算力跑出來的這些知識，可以同時下發到多個同學。那有人會覺得「我們是不是會跑多個分支」？其實我們是有做一些增量的（更）（新）的——我們會默認基於它的一個默認分支（像倉庫的默認分支）去跑一個整體的（Wiki），然後不同的分支我們會再去做一個增量的更新，達到一個知識的復用。所以這可以極大程度上減少我們整個知識（生成）（成本）（的）（降低）。這是一個架構的示例。

接下來還有「新人上手」這一塊——我們面臨項目交接、或新（人）來了之後，之前我們都是要人工去維護這種項目的（新）人指導；那有了這個 Wiki 之後，我們就可以直接用它的能力去（交給）（新）（人），讓他快速地上手我們的項目。這裡面有一個非常大的好處，就是 CodeWiki 跟知識它是「動態實時更新」的——哪怕它是 T+1，它的時效性也是比較高的，相對於我們人工去自己維護，這個成本降（低）非常多。另外像我們還有 API 的架構（圖），這裡面解決的一些重點就是剛才提到的「新成員上手困難、（培訓）成（本）比較高」；另外就是一些技術債務類的——它不僅是架構知識，裡面還會有一些複雜的依賴關係也會給你呈現出來。代碼生成就是我們（剛才看的）。

**（D2C 設計稿到企業組件）：** 第四個就是我們的 **D2C**，也就是 Design to Code 的知識增強。這也是我們比較重點去推動的一個事情。我們企業內部有設計稿平台（**Relay**），也有企業內部的組件（**DongDesign**）。我們傳統的讓（AI）生成頁面的時候會面臨一個問題：生成的代碼往往是一個 HTML、或者是（通用）組件，它都是通用的；但對於企業內部而言，我們往往是有我們企業內部的組（件）。所以我們需要做的是「把設計稿跟我們企業的組件做一個關聯、綁定」。我們其實把整體的鏈路做了一個打通——也就是我們設計的 DSL 是可以跟企業內部的知識進行關聯的。這裡演示的就是它如何從一個設計稿的鏈接，過去再到解析、再到整個交易（頁面）代碼的生（成）的過程。這裡它生成的組件裡面其實有很多是我們 JoyCode 內置的這些企業（組件）——也就是說，在 D2C 這個領域，如果我們僅僅是一個 Vibe Coding 或者 SDD，它是做不到這種非常精（準）的（百）（分）（百）還原、並且跟我們企業知識去做企業內部（組件）（關）聯的。我們只有去做這種 DSL 的、真正的可（配）（置）的、可控的（方案），才能盡可能地既保證還原度、也能夠保證生成的組件是準確的。（JoyCode 通過 D2C MCP Server 實現企業級前端代碼生成。）

### 2.2 上下文工程管理

第二個就是我們的「上下文工程管理」，這也是我們重點去做的另外一件事。有別於其他大家見到的一些比較通用的做法，比如像「短期（記憶）的管理」——我們有各種各樣的壓縮機制；然後我們還有「長期（記憶）的管理」——有 AutoMemory、有（記憶機制）等等，它們都可以定期更新我們的記憶。但是我們覺得，我們的重點應該放在「**檢索**」上。為什麼呢？我們覺得「你檢索了主（動）（精）（準）地把東西讀進來、讀到上下文，這個才是最關鍵的」，而不是說「檢索到一個內容先交給大模型，大模型就一股腦地把所有內容都讀進來」——那樣會引起一系列的連鎖反（應）。

所以我們重點是做了檢索的工具：我們提供給大模型豐富的檢索工具，然後我們定義好它的（適）（用）（場景）之後，把選擇權交給大模型，讓模型自己去選擇。第二個原則就是「一定要先定位、再讀（取）」——這個定位我們是要定到「代碼函數」的：比方說我們一個 function 它在一個大的文件裡，我們需要知道它具體的開始跟結束的位置，我們才會把它注入，而不是說我們知道這個方（法）在某一個文件內、就全部把這個文件讀進來——那就會造成一個浪費，以及上下文窗口會快（速）（消）（耗）。第三個就是我們剛才提到的 CodeWiki 也好、還有後面會介紹的圖（索）（引）也好，我們提供「預處理的、倉庫級的理解知識」。這其實主要解決一個大家也經常會遇到的問題：就是我們會問大模型這類問題「幫我重構一下當前項目」、或者「幫我優化某一個類、我的項目裡哪一個類是最複雜的、哪一塊是最需要優化的」——這部分如果我們不提供這種倉庫級的知識，其實大模型是非常（難）的，它需要去讀你的 README、需要去讀你的 package.json、需要去讀你很多的項目配置來獲取這些知識，而這種知識往（往）是不足以準確地提供給大（模型）的。

那我們**多路檢索**——我們這裡面還有一個 graph（太長了就沒在這裡）——我們有 **grep search**（我們的精確（匹）配，這個是正（則），這個是我們非常（常）見的），第二是我們有**倒排索引**，第三是我們有**稀疏索引檢索**，第四個也是比較常（見）的 **Embedding**，然後我們還有 **Wiki search** 以及我們的 **Graph search**。下面我們就介紹一下這一些各類的檢索工具（的優劣）：

**grep_search：** grep 其實是最常見的（包括 Claude Code 它也是用的 grep 加 glob）。它的優勢就是「正則表達式、精確匹配」，另外就是它的響應速度其實還是比較快的（我說的是在中小（量）還是非常快）；另外就是它的靈活性比較強（正則嘛）；然後它不需要去建立索引、即（搜）（即）（用）；它也可以提供（上下文）。它不好的地方就在於：它不能夠理解查詢的語義，另外它對這種模糊的查詢是沒辦法做到精確的，另外就是在超大（代碼倉）中可能會慢。這個也是為什麼我們會重點去做檢索的一個關鍵——因為我們實際上遇到有這種大型代碼倉，不管是通過 glob/grep 先去定位到你各個文件夾裡面的內容也好、或者直接通過 grep 整個大型代碼倉也好，它會遇到幾個問題：第一，它的檢索工具調用會非常多（也就是說你會看到這個智能體它在不停地 glob、不停地 grep）；另一種，如果它不進行 glob（不去查看每一個文件夾中的內容）、只用 grep 去做這種（匹配），它也會有一個很大的性（能）問題——對於超大（代碼倉）一次檢索可能返（回）結果非常多、或者它執行能力會下降非常（多）。這個其實也非常依賴模型能力：即使你把它的邊界給（限）定好、告訴它「不要去給我查詢大量的這種工具」，但你會發現有的模型它就是會給你做很多大量的（調用）。所以我們為了解決這個（責任）問題，後面加了其他（檢索工具）。

**Embedding（向量／語義檢索）：** 這個也是比較常見的，就是「語義（檢索）」——它的一個好處就是這種模糊的（查詢），我們用比如「用戶（認）（證）流程」「錯誤處理機制」這種自然語言的檢索，它的優勢在這裡。但它有一個很不好的地方，就是它的（索）引的成本是比較高的：像我們是用在雲端、在遠程去做索引，它要 embedding（向量化），然後再去構建索引，它整體（耗）（時）是比較長的，所以它會有一段時間的（冷）啟動。如果這段時間我們沒有提供它其他的額外工具，那我們還是會陷入到 grep（這種）（模式）。

**倒排索引（InvertedIndexSearch）：** 重點講的（是）倒排索引。倒排索引簡單理解，它就是一個非常快速的、不會卡頓的一個（檢索）——但它是基於關鍵詞，速度非常快，但只能是非常簡單的「你這個關鍵詞匹配到了它就給你返（回）」。它能解決這種「（跟）（它）一次性請求返回多個結果」的時候的性能問題，因為它是基於（索引），所以它的速度是在（毫）秒（級）——不管你是多大的（倉庫）它都可以做到（毫）（秒）（級）。另外，它對這種（tokenization）技術的（支持）是比較好的。它不好就在於：它也是有（索）引的（成本）、也會佔用戶的一部分內存。但我們實際測下來它的（構建）速度還是非常快的，我們（以）30 萬行的這種代碼倉庫來講，它也就是大概不到一分鐘就可以構建好了。它也彌補了一個問題：像我們 Embedding（索引）如果沒有啟用，那它在（冷）啟動的階段也可以通過它去做一個（替）（代），起到類似效果。它的一個原理就是它會把函數、類名等這些關鍵詞去構建（索引），然後它可以返（回）於這些所有關鍵詞包含的代碼塊。

**稀疏索引檢索（TermSparseSearch，BM25）：** 主要也是另外一（種）關鍵詞的檢索，但它跟倒排索引會有一個區別在於：它返回的是「有相關性的」——也就是它會跟你當前檢索的語（義）（匹）（配）（度）更加匹配，它會把匹配高的放在前面、匹配不高的放在後面。它彌補了我們剛才倒排索引的一個問題（倒排索引只要（匹）到它就（返）回）。它主要是基於 **BM25** 算法，會把最相關的結果放在前面，同時也會返回包含多個查詢（詞）的（結果）；它比較適合找這種特定的詞組。它的缺點是它也需要這種（索）引，另外它也無法理解（詞）的實際含義。它的原理跟倒排索引其實類似，也是做（分）詞的構建、拆詞放入庫，然後（做）（打）分。

**圖檢索（GraphSearch／CodeGraph）：** 下面就給大家介紹一下圖這一路的（索引）。這個也是我們重點去建設的，就是為了我們超大代碼倉的理解——或者是為智能體提供這種倉庫的理解。CodeWiki 它是這種抽象的、高階的、自然語言類的知識，而 **CodeGraph** 它起到的是這種「（結構）類的倉庫知識」。它怎麼做到的呢？它其實是可以把所有的語法（樹）做（成）（節）點（觀點），我們會得到很多類、很多 function 以及它們的調用關係、（繼承）關係等，它會形成一個大的代碼知識圖。我們給它提供了一個豐富的可（視化）界面——這個的作用，其實因為我之前是搞圖的、我對這塊比較了解，就是我們在這種圖的（構）建的時候，其實會有一個「準確性」的問題，也就是我們不一定構建出來的這種 CodeGraph 是百分之百準（確）的；但如果它不准，它的影響性會非常大——它會給我們的模型、給我們的智能體提供一個不准確的結果，（下游）就會受到影響。所以我們需要給它提供一個可（視）化的界面來幫助用戶去進行分析：這個界面用戶可以做自己的圖的（檢）索、也可以去做一些交互。
