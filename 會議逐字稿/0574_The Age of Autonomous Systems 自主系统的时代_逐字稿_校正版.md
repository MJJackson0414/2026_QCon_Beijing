## 主持人開場

……《The Age of Autonomous Systems 自主系統的時代》。同時黃老師也是矽谷峰會的負責人。現場我們知道，今天也來到了非常多社群的會員。那接下來，讓我們把時間交給黃老師。

## 自我介紹

大家好。這個……我已經好幾個月沒有跟這麼多人說話了，大概是去年年底的時候吧。因為那一波 agent 的能力、包括編程（coding agent）能力的大幅度提升，我當時就做了一個決定：我在公司內部就不再開會了，所有的時間就在跟我的 agent 開會。這幾個月、這幾週算是「出關」了，所以今天可能會帶一些出關這幾個月的一些感受。

其實剛才那位講者的分享是一個非常宏觀、比較大的東西；今天我的分享可能更多是從我自己的一些思考，以及這段時間「燒」了可能上百億 token 得到的一些感受。

OK，我先介紹一下我自己。我叫東旭，是 PingCAP 的聯合創始人兼 CTO。首先我覺得我肯定還是一個工程師，現在因為……應該說，每天還在寫（代碼）嘛。現在大家介紹自己好像都要放一點這個「日均 token 消耗量」，對，所以我覺得這確實也是一個指標；但是大家不應該把這個當作一個目標，而是要看你一天完成了一些有意義的事情、回頭看在這個旅程中得到了什麼樣的 lesson。

我以前一直做技術、做軟件、做數據庫，但最近這幾個月，大家好像認識我的渠道都是從我最近開始寫的一些關於 agent coding 相關的思考。所以目前是這麼一個狀態，最近主要都在做 agent 相關的探索。

## 開場觀點：Coding 已死，但軟件會迎來大爆發

其實今天講這個還挺有意思的。以前我做這種大會分享，主辦方經常提前一個月就開始催：趕緊把 PPT 做好。但今天我們去聊 agent 或者 AI 的這個時代，我可以非常大方地說：不好意思，因為現在這個行業發展實在太快了，如果我一個月前就把 PPT 寫好，那說出來的這些話和內容肯定早就過時了。所以包括這個 PPT，其實是昨天晚上才寫好的，所以我可以理直氣壯。

首先我先拋出一個觀點：**Coding（人來寫代碼）這件事情，基本上已經死掉了。** 我今天早上來的時候還看了一下——哦，by the way，整個這個 PPT 百分之百是純人工手寫的，沒有任何 AI 含量，比較真誠對吧。可能以後我們會有 QCon 的 agent，到那時候再說；但至少今天是「人」的大會，我還堅持用人來寫 PPT。但是代碼，我已經完全不用人來寫了。所以 Coding 這個問題基本上已經被解決了。

這也回到我看到的：今天整個大會這兩天，其實已經沒有跟 agent 無關的內容了。這跟前幾年技術大會的感覺非常不一樣。但我覺得大家也不用悲觀，軟件這件事情其實反而會迎來一個後面會說到的「寒武紀大爆發」的狀態。

## 三個宏觀主題

今天我接下來的分享，會圍繞三個比較宏觀的主題來說。

第一，Agent 時代對於「軟件構建」的方向發生了什麼樣的變化，也就是生產觀。第二，軟件本身的形態——今天我們其實明顯有感覺，這是一個非常混亂的時期。比如舉個簡單例子，Claude Code 和 Cursor，這兩個大家天天用的編程工具，其實代表了兩種完全不同的編程理念。我不說誰最後會贏，但現在你看，這種「自主」的形態走在一個比較前面的位置——不過也不好說，因為現在整個東西迭代實在太快。這個階段我會從宏觀上說一說我的一些思考。第三，其實嘉賓也聊到了：Skill 是未來嗎？不好說。所以我可能在最後會聊一下 what's next——Skill 其實我認為並不是一個最終的狀態。大概就是這三個框架。

## 主題一：計算機史是一部「抽象」的歷史

第一個階段。當我回頭去看整個計算機的歷史，尤其在這種比較混沌的時間，我們其實可以從歷史裡面學到非常多的東西。反而我覺得今天有這樣新的東西的時候，大家千萬「別學」——就是「不學」，其實到最後才是最優的策略。比如當時 OpenClaw（小龍蝦）出來的時候，大家就瘋狂去學，結果最近這兩天我又把我整個 agent 切到那個 Slock 上面了。所以「不學」其實是最好的。這種時候你反過來，應該回到計算機的根源去看什麼東西容易（沉澱下來）。

左上角那張圖，其實是大家最早的計算機的樣子。你想要去讓它做點事情，你可能要去改變它的物理線路結構。在那個時代，每個人既是硬件工程師，又是軟件工程師，又可能是物理學家。慢慢地大家發現，對一個人的要求太高了，所以就開始慢慢抽象。所以今天，我相信不太會有人——比如大家穿越回 50 年前，跑到那個房間裡，你肯定不知道該怎麼辦。但今天我們每一個人看到的代碼，其實是我們跟計算機交互、思考的一個載體，這就是整個軟件行業。

所以本質上，我覺得計算機的發展史其實是一部關於「抽象」的歷史。我是這麼思考的：我們讓計算機完成一件事情，其實有兩個特別關鍵的媒介或者說載體。一個叫**執行載體**——就是你的思想、你的目標，怎麼在一個物理的基礎上被執行；另一個是**思考載體**——你想做的需求，怎麼透過一種抽象（語言也好、代碼也好）在你頭腦裡被思考出來。

回到剛才那張圖：計算機誕生之初，硬件既是執行載體，其實也是思考載體。但我覺得，讓計算機行業變成一個可以被稱之為「產業」的關鍵節點，就是編程語言的誕生——沒有編程語言，其實不會有軟件行業，這個道理大家非常好理解。編程語言的誕生，其實就是把執行載體跟思考載體分開了。

而整個計算機歷史，我覺得在大模型、coding agent 出來之前，其實沒有任何本質創新，只是我們不停地把硬件的能力變得更強，把編程語言翻來覆去變得更加友好——從機器語言到高級語言，再到現在。雖然整個過程你看行業發展得非常蓬勃，但它的本質沒有變化：都是硬件在做執行，然後大家用代碼來思考，只是思考的媒介從一些非常晦澀的 0 和 1，變成了現在的 Python、Node.js 之類的。

## 這一次為什麼不一樣：代碼從「思考載體」變成「執行載體」

但這一波，coding agent 這一波非常不一樣。這可能是從計算機誕生以來、編程語言發明以來，跟編程語言發明是同一個級別的事情。大家仔細想，今天我們去看待代碼的方式，已經跟幾個月前不一樣了。幾個月前，我們作為程序員還在用代碼去思考；但是今天，代碼反而——我已經完全不看代碼了，現在 AI 在寫什麼東西，我是完全不看的。那代碼變成了什麼？代碼變成了跟硬件一樣，變成了一個執行載體。所以我們作為思考代碼的人——架構師也好、程序員也好——我們這個歷史時期已經完成了。

當然，剛才我說軟件本身不會消失，但軟件的「生產」其實會變得非常平民化。想像一下：上一次這種級別的變革，也就是思考載體的變革，誕生了整個軟件行業，對吧？如果計算機一直停留在（真空管/晶體管）那麼原始的階段，是不會誕生軟件行業的；只有編程語言發明之後，才會誕生軟件行業。上一次這種載體級別的變革產生了軟件行業，那這一次它會產生什麼？這個我不知道，我把它作為一個問題留在這邊。

我這裡想放一個新聞。這個新聞大概是今年 2 月份的時候，Anthropic 的官方博客說：我們用 Claude Code 加上一個 agent team，完整地實現了一個 C 語言編譯器，中間沒有任何人工介入，完全是黑盒開發的。其實這個新聞發出來之前，我大概從去年 11 月份就開始獨立地嘗試類似的事情了，只是這篇文章把當時整個矽谷最前沿的一幫公司的實踐，變成了一個讓大家看見的東西。

為什麼我剛才一直反覆強調去年 11 月份這個時間點？因為那個時間正好是 GPT-5.2 和 Opus 4.5 發布的時間。在那個時間之前，你可以認為所有的 coding agent、或者說當時的模型，對於程序員、對於做複雜系統和複雜工程，只能做個輔助；但在那個時間點之後，它其實跨過了某一個極限、某一個閾值。跨過這個閾值以後，這個系統就可以完全自己去做那種長程的、複雜的軟件任務，而且它交付的結果已經可以用了。

你想想，雖然每一個 agent 在幹事情的時候，上下文窗口是有限的，但是軟件工程這件事情，任何一個軟件工程的項目，都可以被拆解成一些局部不那麼複雜的模塊。那這時候，如果你這個局部模塊的完成能力已經 ready 了，你會發現現在的模型和 agent 已經能夠完成任意複雜的軟件（工程）。所以當時在那個時間點，我就覺得這個世界已經徹底變了。對於程序員來說，AGI 已經實現了。而且我們現在其實沒有辦法去評估 coding agent 的能力邊界在哪裡——這是我一個切身的感受。

雖然今天其實有很多朋友說：哎呀，這個東西太蠢了，還是得（人來）編程才會更安心一點。但是我只能說：第一，你沒有給模型足夠多、正確的上下文；第二，你可能本身的需求描述就沒有那麼清楚。但模型本身一定是能（做到）的。這其實是我自己最近三個月一個人在做的一些東西——這個已經完全是在現實生產上上線、並且已經有客戶的一個現狀。就是一個人、三個月、幾百萬行代碼的項目，而且是一個純基礎軟件、有點像編譯器那樣的項目。包括現在我在演講的時候，我的 agent 還在不停地開工——人肯定是（累）就過來了，對吧？

## 新的思考媒介：Goal + Context + Constraints

所以我們回到剛才那個判斷：當代碼已經變成了一個執行載體以後，我們今天要去生產軟件、構建軟件的這一端，思考媒介是什麼？我其實覺得，雖然這個東西還沒有名字，但它大概只有三個東西的組合。就是大家今天看到，前一位 speaker 最後講的：未來大家可能想去的行業是「AI + 崗位」。嗯，我覺得這個還是太（籠統）了。當你去思考這件事情的本質以後——軟件到底是個什麼、我們應該去關注什麼——我覺得大概拆成三個東西：一個是 **Goal（目標工程）**，第二個是 **Context（上下文工程）**，第三個是 **Constraints（約束 / 環境管理）**。

其中人在裡面關注最多的，應該是 Goal 這一塊。而且其實現在大家對於「要做什麼」這件事情，我覺得還是沒有太思考清楚。人類我覺得有一點特別不好，就是人是不知道自己要什麼的，這個對於 AI 來說是會有麻煩的。所以我提出這個思考框架，是為了讓大家把今天所有的技術和流行的東西，放到這個大框架裡，大家就能看到整個 agent 行業現在到底是個什麼樣子。

比如說，我們今天搞得非常非常熱的聊天、比如 Skill、比如各種上層的應用生態、跟人的交互這一塊，我覺得可以放到 **Goal** 這一塊——就是怎麼讓人能夠更快地去跟 agent 交互、完成他要的目標。比如今天特別火的 Harness Engineering，包括之前比較局部的像 ReAct loop、memory 管理，這各種各樣的東西，其實都是在優化 **Context**。而 **Constraints** 其實是現在 Agent Infra 最火的一個賽道吧——你會看到今天無數的創業公司跑出來說「我做 sandbox」「我做測試環境 for agent」，或者做這些 runtime for agents，其實都是在 agent 生產軟件的過程中，去控制約束和邊界的東西。所以今天你會看到，任何我們在 agent 上做的事，都可以放到這個大框架裡面。那既然都能放進來，這個就是未來軟件的樣子和架構。

## 人與 Agent 的協同模型

其實關於軟件的生產，除了剛才那個大的思維框架，我覺得還有一個點挺重要，就是人和機器如何協同。大概從去年年中，我也經歷了一個思維的升級或者說轉變。我去年年中的時候非常激進，一直在嘗試讓它完全純粹地「黑盒」——就是人你別介入，任何 agent 在幹的事，就是 agent 自己做討論、自己去搭環境、自己去開發，消耗多少我覺得無所謂。「more tokens, more intelligence」我覺得今天仍然是成立的。

我其實做了一整套 agent infra，能夠讓無數的 agent 在裡面自己去組織成一個「社會」，去維護狀態、開啟 sandbox 然後去工作，人只能看、不能有任何干預操作。這個大家其實很好理解，因為我畢竟是開公司的，我有一個特別大的經驗教訓：當老闆開始去插手操作的時候，這個系統經常會出問題。所以我一開始的目標就是：我完全不關心這個 agent 怎麼做，你給我交結果就行，中間你消耗個 100 億（token）我無所謂，你給我目標（結果）就行。

但是後來慢慢發現，這個模式不太行，人還是要在流程裡面「點撥」一下。我自己跟我的 Agent Team 的工作模式大概是：我每天會在群裡讓大家簽到，然後讓大家總結一下昨天幹了什麼、誰表現得最好，如果誰表現最好，那就學習一下他為什麼表現得好（有點像做 HR / 復盤）；然後我會說「你看今天你表現得不太好，你要反思一下為什麼」。聽起來非常……嗯，這是一方面，就是這種 agent 的組織協同。

第二方面，是我作為一個老程序員的一些經驗，這些經驗我覺得特別重要。原來我犯的錯誤是：我沒有辦法明顯看到 agent 在犯錯，也沒有任何辦法進去說「你別這麼幹」。所以我現在的工作模式，更多是把我作為一個軟件公司、這種樸素軟件工程的 SOP 寫得非常好，然後透過一些產品化的方式，讓這些 Agent Team 能夠組織、學習。

這裡面有一個很有意思的點。昨天我有一個朋友說，他的 Harness Engineering 總是實踐得不太好，agent 幹著幹著要麼就「跑飛」了，要麼幹著幹著就停下來了。而我很多任務一跑，都是幾個 agent 跑個三五天不會停下來，而且交付的活明顯會比別人更好。他問我：是不是因為你的 agent 組織形態和 Harness Engineering 做得好？我說完全沒有。說白了，我覺得 Harness Engineering 就是把多個 agent 放在一個群裡讓大家自己聊天，沒有什麼神秘的東西。最關鍵的還是：你怎麼去定義「什麼是好的軟件工程」，怎麼樣讓大家在一個正確的方向上，讓軟件和代碼的質量不至於在人不監督的情況下「跑飛」。所以（定義好的工程標準）可能會比 Harness 本身更重要一些。

## 大力出奇蹟：模型智商是決定性要素

另外一個我變成紅字的點，其實挺有意思。我相信現在大多數用 coding（agent）的朋友，可能都只是開一個 Claude Code、或者開一個 Codex，把自己要的東西跟它討論討論，它就可以幹活了，幹完活驗收一下就結束。但我要這麼說：如果你今天還是這樣的模式，那基本上，第一，你會變成一個最大的瓶頸——你的生產速度取決於你自己吃飯、睡覺這些作為人的事情；第二個更嚴重的問題是，你其實沒有辦法判斷 agent 給你的這些建議是不是最好的。

所以我後來的一個實踐是：不管是任何需求，我都會強制要求可能數十個 agent 不停地一遍又一遍地從寫、刪掉、重寫、刪掉，在這個過程中互相討論。可以說 99% 的時間，這些 agent 產出的東西都是廢話、都是一些車軲轆話；但我要的就是那 1% 的時間，突然有一些靈光乍現的 idea——而且出現這種時刻，你會發現所有的 agent 馬上就會「越簽到」另外一個方向。

所以這就是為什麼我覺得今天大家對於這種頭部模型的理解和判斷是不對的。我們現在沒有辦法去評估這個模型到底為什麼會有這種 1% 的時刻，所以我只能透過「大力出奇蹟」的方式，去把 token 的消耗量給拉起來。所以今天如果大家說「我要做一個好軟件，但是我要省 token」——不好意思（做不到）。

第二，模型的智商是決定性的要素。很多朋友問我：哎，這個東西如果我用某些智商低一點的模型行不行？我說不行。你想，尤其像這種長時間、多輪、可能上千步的 agent 工程，你每一步的智商差一點，你可能跑一千步以後（誤差就非常大）。雖然我知道最近可能有些國外的（模型）、包括昨天的新聞（說性能接近），但我只能通過我自己的親身感受（說）：你想辦法真正用到像這位 speaker 的這種程度，才可以感受到（頂級）模型的（差距）。

還有一個迷思：到底是「三個臭皮匠」協同產出更好的結果，還是一個腦子特別厲害的單 agent 產生的結果更好？我覺得這個問題，如果是兩個月前可能還有爭論，但今天我覺得沒有爭論了。一個典型的例子：大家可能看新聞，昨天（Claude Code）出了一個新功能，這個功能很有意思，它其實是個小功能，但它代表著 Anthropic 一個思維的轉變——就是它自己也在做 Harness。如果你這個（功能）其實有點像一個 trigger，就是發生了什麼事件的時候，觸發另外一個 agent。通過這個機制，你才能讓你的 agent team 變成一個 proactive 的 flow。所以這其實意味著，Claude Code 已經不再覺得「在單一機器上去做 agent loop」是完成複雜任務的終極方式——它需要去構建一個 agent 的網絡，才能去幹一些多階段的事情。所以這個功能本身，大家玩玩就好，但它背後代表的意義是更重要的。

## 我們這代程序員留下的遺產

OK，軟件工程這個部分，我相信大家聽完以後會覺得：作為軟件公司（程序員）這個（角色）已經結束了。嗯，沒錯。但是我們這一群最後的程序員，其實還是給這個世界留下了一些寶貴的遺產。有一句話我很喜歡：其實今天大家說的 Harness Engineering 這些，說真的，我們這行業太愛發明（名詞）了——**Harness Engineering is still good engineering**，你翻過來看，它就是好的工程，沒有什麼特別的。

也許三年以後，Agent 自己的社會網絡形成了以後，它能找出一些自己的工程方式，但在那個時候，我們可能已經看不懂它們在（做什麼）了。所以至少今天，我們作為一個 bootstrap 階段的人類，能夠給 agent 最好的東西，就是我們在上一個時代積累下來的那些「樸素的軟件工程、複雜性管理、需求分析、項目管理」——把這些作為當前這種 baby agent 的一個 bootloader（引導）。

## 主題二：軟件的形態

好，第二部分：軟件的形態。剛剛講了很多關於軟件的「構建」，但我覺得軟件的形態本身也是一個很有意思的話題。以前，在大模型、AI agent 出來之前，軟件的形態是靜態的——就是產品經理跟程序員寫好的：UI 是固定的、功能是固定的、用戶動線也是被設計好的。這意味著什麼？這意味著這個軟件智商的上限，就是設計這個軟件的人的智商的上限。比如說我是一個特別糟糕的產品經理、也是個特別糟糕的程序員，我做出軟件給你用，你會覺得這個軟件特別傻——不是這個軟件傻，傻的是我。這其實是過去軟件最麻煩的一個問題。所以為什麼在過去的時代，好的設計、好的產品經理、好的程序員如此重要？因為他直接決定了這個軟件的體驗（上限）。

但現在，今天軟件沒有固定形態了。大家其實說了很多，包括 OpenClaw——外面我看一個大海報說「你今天 OpenClaw 了嗎？」OpenClaw 這個事情，它的意義其實不在於 OpenClaw 本身（包括今天我其實不用它，我用別的工具）。它給整個行業最大的意義在於：它定義了一個「60 分」的、agent 時代軟件的及格線。就是未來所有的軟件，如果你要做得比 OpenClaw（小龍蝦）還難用，那不好意思，你是屬於舊時代的東西。今天如果你要再做一個新軟件，如果你的體驗、使用的靈活性、形態和完成的事情，不能比 OpenClaw 做得更好，那你可能就死掉了；你只能比它做得更好。所以它是個很典型的例子。所以其實沒有什麼固定的 UI、沒有什麼固定的形態，這個（agent 交互）才是用戶未來操作軟件的接口。

### UNIX 哲學（CLI）的復興

這裡差不多還有一個小點。其實最近一直發現有一個被整個行業反覆在說的東西：怎麼現在 CLI、包括 UNIX philosophy 又復興了？這其實我特別高興。因為我自己本身就是一個 GNU/Linux 的忠實粉絲，其實在很早、還沒有 agent 的時候，我就特別相信這個——當然如果你是搞運維的，你肯定知道我在說什麼。

為什麼今天 UNIX 復興了呢？因為 UNIX 從來就不是一個「操作系統」。大家經常覺得它是一個特別難用的、黑白的、圖形界面（很弱）的操作系統，其實 UNIX 完全不是操作系統，它是一套思想、一個體系——一套生產軟件的體系。我舉個簡單例子，讓可能沒有用過 UNIX 的人有一個感受。比如下面這個東西，右邊是一個大家可能更熟悉的、有 GUI 的軟件，可能是一個做展示的儀表盤（dashboard）。人可能會更喜歡右邊這個，但我跟你說，右邊那個其實會有非常多的缺陷：缺陷在於你沒有辦法靈活地針對不同的需求去改變這個軟件的形態。比如你的 dashboard，如果今天有個新需求說「我要看另外一個指標」，那不好意思，你要麼開發一個新的界面，要麼（很麻煩），而且你也不能隨便把兩個 dashboard（拼起來）。

但是對於 UNIX philosophy 來說，這其實就是改一行的事。比如說我現在不想看 error，我想看 warning，我直接把這個 grep（的關鍵字）改成（warning）就結束了，你不需要從頭開始開發一個新軟件。你想想，這個事情是不是跟剛才我說的那種靈活性——跟 agent 的靈活性和意圖——就完美地結合在（一起）了？這就是生成新軟件的體系。所以對於大模型來說，它只要把 UNIX 哲學和常用的 UNIX 工具學會了，它就能排列組合出各種各樣的（軟件）。

### 軟件市場：從紡錘形走向兩極（沙漏）

所以未來的軟件產業……不說未來，我說今天。今天這個軟件的市場，我畫了一根軸：底下是貼近機器的這一端（比如編譯器、數據庫、大數據），上面是關注人類的這一端（比如我們用的什麼美團之類的）。現在我們的行業，其實是落在這根軸中間的某個位置。其實在 AI 誕生之前，整個生產軟件的產業鏈，我覺得會呈現一個「紡錘形」：靠近兩頭的公司或創新比較少，但靠近中間、尤其美國市場、美國的企業服務市場，你會發現有很多 SaaS、很多行業軟件，其實是落在這個軸的中間。所以整個軟件（市場）應該是一個紡錘形。

但是我覺得，在 agent 普及了以後、不遠的未來，這些中間的市場就會被嚴重壓縮，創新、資本和軟件公司都會往兩頭走：你要麼就做特別「向人」的，要麼就做特別「向機器」的，沒有中間的選項。所以之前（有人）說 SaaS 的股價可能還能再跌一點，大概就是這麼一個意思。

我兩端都說一說。**靠近人的這一端會發生什麼事情**——這都是我自己的一點想法，因為剛才說這個市場現在處於一個非常混亂的階段，我就說我自己的一個觀察。其實到今天，靠近人這一端我使用的軟件，從 Claude Code 開始，到 OpenClaw，到我現在用的 Slock——我特別喜歡這個軟件。這一條線，我覺得我用得比較舒適的軟件，今天都有兩個特徵。

第一個特徵叫做「情緒價值拉滿」：人可以在裡面發號施令，同時交互的體驗會覺得「I'm in control」，對吧。而好的交互、好的體驗能帶來傳播——比如 OpenClaw、包括「小龍蝦」為什麼宣傳這麼快？就是因為這個東西用起來太好用了，大家口口相傳，感覺「我好想給我的朋友分享一下」，而且它的（易用）性也非常好。所以好的交互決定了傳播，今天我覺得傳播是一個很重要的事情。

但是什麼決定傳播呢？結果。剛才其實上一位 speaker 說的：今天的軟件，我們是在用「結果」來評估的。比如說，我不會說我喜歡小龍蝦（OpenClaw），我是喜歡小龍蝦給我交付的結果；如果這個東西交付的結果不紮實，那對吧，你是沒有辦法留存的。所以為什麼今天我毫不猶豫地從 OpenClaw 切換到了 Slock？因為小龍蝦（OpenClaw）的交付結果就是不如 Slock 好。當然，這個也只是一個現象——因為我相信可能未來三個月之內，一定會出現比它們更（強）的，而且如果出現，到那個時候我也會毫不猶豫地遷移過去，沒有任何遷移成本可言。因為（我看的是）結果。

第二個大的判斷是：下一次計算機的革命，其實是發生在人機交互上。今天我們的人機交互，其實還是 agent 時代之前的交互——比如說為什麼我要去學習用鍵盤、為什麼我要去用觸控板？比如說你有小孩，這個小孩從來沒有接觸過計算機，你讓他完成一件事情，他可能更自然地說「我拿紙筆」，或者「我在牆上塗畫」。那為什麼以後的交互不能是「在牆上塗畫就出來」呢？對吧。所以一切的東西都會往「跟人更接近」的方向去發展，我覺得這個是會出現的。當然，任何交互改進的最終評價標準，就是：人的輸入（交互）是否能讓 agent 交付更好的結果——這個我覺得是一個根本性的東西。如果你這個東西只是給大家提供了很好的情緒價值，但它對於你的 input 其實是廢話，那肯定也不行。

**說完靠近人這一端，說靠近機器這一端。** 我覺得靠近機器這一端的趨勢已經非常明顯：現在的基礎軟件已經不再是給（人類）開發者用的了。以前我們還有什麼「基礎架構工程師、基礎工程師、Linux 工程師」，不好意思，現在所有這些工程師所使用的軟件（都交給 agent 了）。包括現在我的運維（工作）已經完全交給了（agent），我自己再也不用去（弄了）——終於不用再寫 Dockerfile 了，真是謝天謝地。所以給 agent 用，其實是解放了人類。

第二個很好玩的例子：其實在 TiDB Cloud，我們有個新的產品線叫 **Zero**。這個 Zero 什麼意思呢？就是在這條產品線裡面沒有「賬號體系」，就是沒有「人」。有賬號體系的意思是說：人要登錄、要去鑑權；但是對於 agent 來說，agent 的數量和需求是人的可能 100 倍、1000 倍、1 萬倍，這時候你再用人的賬號體系去限制 agent，其實是不明智的。所以你就應該把自己變成一個純粹的、隨叫隨用（disposable）的技術設施。我只是舉個例子，因為這是我自己做的，所以有點感覺；但更想讓大家知道的是，這背後代表著一種思維的變化。比如包括現在我的（產品）onboarding，其實已經完全不是「安裝一個什麼東西」，而是直接把一個 skill 貼到對話框裡，它自己就調起來了——沒有註冊、沒有 configuration，no everything。

### Agent 的「人因工程」

所以其實圍繞這個話題再往前走一步，我覺得馬上會有一個非常重要的行業或者說生態會誕生，這個方向就是「人因工程（ergonomics）」，或者說「Agent 的人因工程」。以前開發的體驗（developer experience），我覺得在中國其實沒有那麼多人關注，但我在美國這塊其實研究得非常多——就是從一個程序員的角度來看，一個軟件到底好不好用。明顯有些東西更好用，有些不好用，但你怎麼去系統地描述「什麼叫好用」，這件事情就叫 developer experience 的工程。我覺得馬上，agent 使用軟件也會有這個行業出現：怎麼去設計給 agent 用的、更好用的軟件？

我這裡有幾點。第一，是降低 time-to-use 的摩擦。比如說你發現這個結構化數據在數據庫裡、memory 在另外一個地方、日誌又在另外一個地方，對（agent）來說就很分裂，有點像一邊要看這個、一邊要看那個。如果你能給它提供一個 unified 的 platform，它其實是很爽的。所以為什麼今天的（產品）我都可以（統一），因為可以同時（給人和 agent 用）。第二，給 agent 看的（文檔）跟給人看的有一個很大區別：信息密度很高。第三點我覺得很重要，也是人類經常會犯的問題：不相信模型的能力，只相信自己設計的流程。但經常 99% 的情況，我們自己想出來的那些流程規範，在 agent 面前都是非常愚蠢的，反而限制了 agent 能力的發揮。

## 主題三：What's next

好，因為超時了，我快速講最後一節。其實回到剛才一開始那個問題：軟件的未來會發生什麼？上一次這種級別的變革，誕生了軟件行業；這一次，其實我覺得會帶來一種新形態的軟件。

這裡我給大家一個例子。我稍微調查一下：現在有在用 Gstack 的朋友嗎？呃，沒有。好吧。有用過的舉個手？呃，那還行，三分之一吧。我覺得類似的（產品）跟那個（前面說的）也還挺接近的。但我覺得它的核心價值在於：它定義了一種未來的軟件形態。說白了，這個軟件就是幾百個 Markdown 文檔，然後他把這幾百個 Markdown 文檔放在 Claude Code 上運行，用戶可以不用關心底下這一套。我覺得它最大的意義在於：這些軟件是在把 Claude Code、或者說這種 coding agent 當作「操作系統」在用——你看到的界面不是（重點），而是（背後的）stack 代表這個東西。

Gstack 這個東西，就是 YC 的現任 CEO（Garry Tan），把他自己思考問題的方式、以及幹這麼多年（創業）這個（YC）和公司 CEO 的一些經驗，變成了一系列有自己思考框架的 agent。這就挺好玩的，我覺得它代表了一種未來的軟件形態。

所以回到我一開始說的 Skill：Skill 核心的問題在於，它太簡單了、太粗糙了。我想到什麼呢？想到當年計算機剛被發明、軟件剛被發明出來的時候，當時在（早期的）計算機俱樂部裡面的一幫愛好者，互相分享自己的東西：「誒，我今天寫了個小程序很好玩，給你去玩一玩。」今天我們交換 Skill 的方式，就跟當年這些人交換那些奇奇怪怪的 recipe 的方式是一樣的。但很明顯，大家看到未來我們可能有 Photoshop、可能有 Office 這麼複雜龐大的軟件，是不可能通過一張（skill）去交換的。

所以我覺得，未來在 Skill 之後，一定會有更好的抽象。這個抽象是什麼呢？第一，它是一個更複雜的、能表達更多事情的（東西）；第二，它其實是通過自然語言描述的，但這個語言跟機器協同生成時，可以有一定的結構、能被解析、能被（版本化），然後會隨著環境分發。它核心的目標，就是保留人類專家的知識——這一點其實是非常（關鍵）的。

有了這樣一個（抽象）以後，我覺得會迎來軟件開發門檻的降低。有點像什麼呢？比如說我今天特別想把我的（手藝）變現，但以前受限於開發軟件的能力，我沒有辦法把我這個「廚師能力」變成一個「做菜的 app」；但今天完全可能——你跟你的（agent）聊個三天三夜，最後把你做菜的 know-how 沉澱出來，變成一個做飯的（skill/agent），這個你就可以變現了。這很有意思。

## 總結

好，最後一頁，一個總結。今天為什麼——我其實說到了 Coding 已經死了，但為什麼我還在討論這個事情？或者說為什麼今天（Coding）看起來「贏了」，為什麼今天這個計算機、這個編程這麼重要？不是因為我們發現了一個什麼新的科學，而是今天我們現在的這個狀態，是被 Anthropic 一步步實現的，或者說這是人家的公司戰略。也許 Google 贏了，那這個世界可能走向多模態的世界；但今天是 Anthropic（這條路）贏了，我們的世界變成了一個「用編程去表達、去改變世界」的通用手段的世界。因為現在大多數所有的資金和模型訓練，都是在往編程這個能力上加強，於是我們所有的通用（能力）都是構建在這個編程能力之上的。

所以這是最後一頁，讓大家理解一下。OK，謝謝。
