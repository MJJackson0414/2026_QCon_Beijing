## 一、為什麼要用 Spec Driven 解決 coding 問題

首先第一個話題：Spec Driven 是什麼？為什麼我們要用 Spec Driven 去解決 coding 的問題？

其實我們講到，在這兩三年——剛才百度的老師（鄭然）也講了——（AI coding）發展得非常快。在 23 年，我們可能還叫做 Copilot 的工具；24 年逐步出現了很多「編輯器重塑」，Cursor、Windsurf 都是其中的（代表性）標誌；25 年我們稱之為叫 AI coding，因為這個時候大部分的編輯器推出了「自主編程」或 planning 的能力，特別是代表性的就是 **Claude Code**。這種（自主編程）的編輯器，其實很大程度上改變了傳統軟件研發的一些格局。那反觀（低）（代）碼呢，感覺聽起來像 low-code，感覺是很（傳統/低端）的一個技術——這幾年這個「AI + 低代碼」的產品比較少，大部分還是在實踐探（索）。

但是其實我們要面對一個現實：在 2025 年的開發者調查報告裡發現，60% 多的人認為 AI coding 顯著提升了自己的生產力，但是真正能「信任」AI coding 代碼的只有 3%。我可以問大家一個問題：大家有多久沒有看過 AI 生成的代碼了？

所以其實 AI 生成代碼有幾個非常大的問題。在很多人看來，AI 就是一個大型的「屎山製造機」：表面上看起來是可以運行的，但生成的代碼風格非常（隨意/不統一）。而且像國外的代碼，它流行的都是以 Next.js、CSS 這種流行技術棧為主，跟國內的技術棧差距也比較大，所以它跟企業現有代碼倉庫的（兼容）性會比較低。另外一點就是「代碼可維護性差」——這裡我其實都不需要講，（大家都知道）就是差。現在很多人用 AI 寫的代碼只能用 AI 維護，debug 的話其實都沒有什麼很好的方式，只能不斷地去對話、對話。還有一點：AI coding 生成的代碼是缺少業務理解的。在我們看來，在一些比較複雜的系統裡面，業務的很微小的提示變化、或者業務知識的一點變化，都可能會造成（生成）的巨大偏移。

其實在（19）78 年，有一個算法大師 **Dijkstra（迪傑斯特拉）**——如果大家學過算法或數據結構都會知道 Dijkstra 算法——他在 78 年就講到：其實「用自然語言編程是一件非常愚蠢的事情」。為什麼呢？首先，比如我們講到數學，數學它的約束是「形式化的符號」，比如 1+2+3 這種——你在寫形式化符號、或者你在寫編程代碼的時候，你同時就做到了「思考」和「抽象」；但是你如果用自然語言編程，你可能想到什麼就寫什麼。所以其實「寫代碼」它並不代表就是深思熟（慮）——AI 其實寫得可以很快，但是它（缺少）思考。

另外，AI 其實總是「漏需求」：你以為你自己說清楚了，AI 也表現得像好像理解了——特別我們知道像 GPT-5（早期）、還有 DeepSeek 早年的版本，它特別喜歡「奉承」開發者。但其實本質上，你跟一個人做自然語言的對話，他可能覺得「哎呀我聽懂了」，其實在其中出現了非常大的歧義和（誤）（差）。還有一點也跟模型有關：我們講到人和人之間溝通，如果用比較（泛）（泛）的溝通方式，它不一定能減輕負擔，可能兩邊都更累——因為你一開始沒有澄清楚，你需要不斷地去返工。這點在大模型上面也表現得非常明顯：對大模型來講，我可以一股腦地把各種各樣的信息都餵給大模型的上下文，那上下文越長，整個開發會越來越（降）（智）。所以其實「對話式 AI 」（本身）反而會變成很大的問題。

那麼怎麼去解決這個問題呢？其實這個問題的本質是什麼？就是「自然語言非常模糊」——這是自然語言本身的模糊性帶來的。這個問題的核心是：我們無法去指望用戶去寫出非常高質量的提示詞。你快速迭（代）可以把需求一點點描述清楚，（但）它是非常缺乏文檔、（測）（試）和架構約束的，開發者也很難去理解這個代碼。

## 二、Spec Driven Development（SDD）

所以在去年 9 月份，正好那個亞馬遜的老師來（網易）（做）訪問，他帶來了一個新的產品叫做 **Kiro**。Kiro 帶來了一個新的理念，叫做 **Spec-Driven Development（SDD，規約驅動開發）**。它的理念為什麼認為可以解決 AI coding 的問題呢？就是我們講的 vibe coding 的過程是「prompt to code」，對吧？而 SDD 追（求）的是什麼？是「prompt 先到 requirements」——我先把需求進行標準化，然後再到 design（技術設計），再到任務拆解（task），最後才 to code。

在這個過程中有幾個很關鍵的點：第一，我先把我跟 AI 對話的需求澄清楚，我確保 AI 在理解上沒有歧義；第二，我可以把我需要的技術設計、技術架構通過 spec design 的方式去澄清楚，然後我希望能夠用我公司的技術棧、公司的技術要求、我的目錄結構去約束 AI 的生成；第三，我可以通過 plan 的約束有利於 AI 生成的穩定。這個其實大家如果深度用過 AI coding 工具都會感覺到：去年下半年幾乎所有的 AI 工具都上了 **plan mode**。其實 plan mode 是一個非常古老的智能體模式，在 23 年就已經出現了，當時的（代表）就是那個 **BabyAGI** 等等；它發揮到（極致）的（代表）就是 25 年的 **Manus**，它就是一個典型的 plan mode 產品。當然 SDD 還強調「我需要通過 TDD 去（測）（試）和驗證」。

這樣的方式，其實在很多場景下已經能夠解決我們剛才講到的問題。比如代碼質量（不好），你可以通過在 SDD 的過程中、通過技術架構約束，去保證代碼質量在你可（控）範圍之內，你還可以去注入這個項目的規範知識去約（束）（生成）。另外，可維護性差——SDD 的理念是「你就不要再（人工）維護了」：我們講到 TDD、什麼叫 RDD，就是「我結果說話」，我通過寫各種各樣的測試用（例），包括 E2E 測試、UI 測試，我保證結果對了就好了，所以就無所謂維護不了。第三，如果 AI 對業務理解和需求理解得不清楚，我們也可以通過不斷地去澄清產品、以及加入業務理解需求來解決這個問題。

其實在很多公司開始實施 SDD 以後，他們會發現它的 AI coding 提升了非常多。但是我們還要再回去看一個問題：**SDD 真的能解決所有問題嗎？**

很多人會理解 SDD 是不是「我（做）一個（大型）的提示工程，我把那個輸入到大模型的 prompt 寫得足夠詳細、足夠複雜，是不是就能解決問題了」？其實事實上不是的。首先第一點，spec 大模型能（讀懂）的前提是——大模型它要讀得懂你的 spec。其實我們在測試中發現，很多模型是讀不懂非常複雜的 spec 的，它做不了很好的上下文管理以及指令遵循，所以你把一大坨的 spec 餵給大模型，不同的模型表現都不一樣。這是為什麼呢？首先你要知道，spec 的編寫是有非常大的成本的——我們可能會用一些工具，包括 OpenSpec 這樣的工具去生成 spec。那你可以看一下生成的這個 spec，你是不是能看得懂、模型是不是能看得懂、或者說人跟人之間能不能看得懂。所以「寫 spec」是一個成本非常大的事情。

第二點，spec 給到模型以後，它不是說你把（spec/program）給它以後它就開始「哭哧哭哧幹一下」就出來了。事實上在很複雜的應用（裡），給到模型以後，模型會自動——就是我們剛才講到的 plan mode——進行任務的拆解。那當你的 spec 很多，模型就會把整個編碼任務變成一個非常複雜的 code agent 的長程任務。那在長程任務過程中，你（某個）節點出現了問題、或者某個節點生成的代碼不符合你的要求，它很容易就會出現「後面的代碼全部出現問題」，甚至你連不知道什麼時候出現問題都很難去排查。

## 三、Harness（馬具）工程

所以我們講到 Spec Driven 它只能解決「一部分約束」的問題。這個本質上（要引出）第二個概念，就是所謂的 **harness（馬具）工程**。

其實在 23 年，早年我們講約束叫做 **prompt engineering（提示工程）**，我們會學習怎麼去跟 AI 對話、怎麼去優（化）我們的（輸）入；在 25 年，我們講到 **Context Engineering（上下文工程）**，它會講到如何去給大模型提供相對應的知識；在 26 年，其實像 Anthropic 和 OpenAI 都會提出來「我需要構建一個舒適的環境讓大模型去跑」。本質上為什麼叫「馬具工程」呢？就是大模型是「一匹快馬」，如果你沒有很好的駕馭方案，它很容易就跑（飛）——它如果在一個比較複雜的任務上跑著跑著，可能就失控了。

所以我們講到所謂的 harness 工程，其實包含（幾個部分）。第一個叫做「規範」：我們可能會通過 spec、通過 **CLAUDE.md**、通過 **AGENTS.md**、比如 Spec Kit / Kiro 裡面的 **constitution** 等等，我們通過規範首先去約束大模型的行為，這叫做「形式化的規（範）」。但是我們在大模型的執行過程中，仍然要控制它執行的節奏和過程，所以我們需要像 **CI/CD** 這樣的流程性的東西去管控大模型整個執行過程。還有一點，就是大模型在執行複雜任務的時候，我們需要用一些「控制論」的方法去管理它穩定的任務執行——這個就是後面我會講到我們怎麼去做大規模應用的 **harness engineering**。

## 四、低代碼與 AI Coding 的發展歷史

那我們再回頭去看低代碼和 AI Coding 的發展歷史。早年我們剛才講到，AI Coding 最早的一個問題就是「技術棧不受控、維護成本高」。所以很多公司最早的做法——特別是 AI coding 公司——它最早的做法是引入「低代碼 / 可視化」。大家可能用過比較早的 Cursor 就知道，Cursor 之前做了一個 **Bolt**（可視化能力），它認為「我很難通過 TDD 的方式去維護這個前端生成的代碼、我也看不懂，那我通過一個（可視化）去看、可以去動態地（改），是不是也能夠解決」。但是這個能力它沒有具備整個（收斂）——它開放性太強了，沒有具備足夠的收（斂）能力，也很難跟代碼做二次關聯。所以它有沒有用？也有——它是適合於像「創作原型」這種場景，比如像 **Lovable** 就大規模使用（可視化/DSL）技術，來讓 AI coding 生成的工具更容易給設計師或產品使用。

接下來，比如 AI coding 開始引入 Spec Driven，這個時候我們保證了技術棧的受控，但是很難避免的問題就是「大規模任務上的（不）穩定」，而且維護成本仍然非常高。還有一點很重要：其實每個公司都有自己不同的角色——有產品經理、有設計師、有前後端、還有測試——你不可能指望所有的角色都跑到你的電腦上、用一個 IDE 去協作。所以這也是很多公司落地 AI coding 的一個困難：它只能給程序員（用），可能產品經理可以用一用，那其實很多都是「單點提效」、流程上串不起來。

但這個東西（不是）沒有用，也是非常有用的：目前出現了很多「超級開發者」，你可以通過各個角色的串聯，自己在你的本地就閉環起來。我們認識很多個人開發者用 spec 可能孵化的代碼——比如它一天可能（燒）過（上億）的 token——都能夠孵化非常（多的產出）。

那麼我們再回看低代碼。低代碼本身，早年大家都認為是一個非常簡單的場景，包括表單、報表、流程等等。很多公司為了解決低代碼的（能力上限）問題，引入了（DSL）語言，它可以通過複雜的 DSL 去讓低代碼的（能力上限）提升，也可以通過約束性的語言更好地讓 AI 去生成低代碼，還能夠通過（可視化）的方式去呈現資產。但是它最大的問題是什麼？低代碼平台也是軟件，它的學習也是要成（本）的，門檻是非常高的。所以很多公司開始嘗試——包括我們在去年和前年都在做——比如「我加上 AI 的功能，通過自然語言生成邏輯、自然語言生成頁面，能夠降低這個門檻」。事實上這個（治）（標）不（治）本，因為本質上自然語言的問題我們仍然沒有（解決）。

所以最後我們希望探索一條新的路線：通過「可控的語言體（系）」加上「可視化開發」加上「Spec Driven」，徹底解決低代碼產品的上手門檻問題，也能夠更好地通過 spec 的方式約束 AI 生產的代碼；同時我們也可以借助代碼本身的優勢——比如資產、比如企業級軟件開發的全流程控制、平台化的多人協作能力——去解決整個軟件開發的問題。這就是我們今天推出的新產品。

其實可視化開發本身會有一些（先天）優勢：比如像低代碼平台、可視化開發平台，它天然具備「統一的應用生命週期管理」，包括應用的創建、發布、協作，包括需求的（管理）等等，都會在一個平台上流轉，它天然是適合多角色協作的。另外一點，低代碼平台天然具備「統一的 DSL」——不管你這個平台做得多好，它一般都會有一個統一的 DSL 去（承載/記錄）。可能很多人都會問：AI Coding 時代 DSL 有沒有用？其實在我們的實驗中，DSL 對於「約束生成代碼」的效果是非常重要的。最後還有一個很簡單的場景：你至少還可以通過可視化的方式看看界面的效果、可以改一改，避免說「我只能讓（AI）改」。

## 五、產品：需求標準化的開發（Demo）

所以這個就是我們今天要介紹的產品，我們圍繞「需求標準化」的開發。大家快速看一個視頻——如何使用 SDD 模式完成企業級應用開發：

第一步，產品經理選擇一個企業中常見的需求文檔進來，文檔上傳後，通過（多）個階段智能分析處理，轉換成標準需求文檔。產品經理此時需要確認智能體（結構化）補充的文檔是否符合預期。第二步，架構師開始啟動技術設計工作，智能體將標準需求文檔拆解為架構設計和業務設計，架構設計包括應用架構、數據建模、UI 規範、領域服務設計等。架構師在這個階段需要 review 所有架構設計，並提出一些必要的修改。第三步，架構師可以將確認好的技術設計生成研發任務，並將任務（提交）執行。此時可以看到每個技術設計文檔下都有研發任務列表，可以人工檢查、補充文檔、重新生成。架構師會將架構相關的任務（提交）執行，此時看到的是（任務）執行、實體生成，執行完成後可以確認接受、修改或者取消。（每）次生成可以逐條執行或者批量執行，任務執行時智能體會自動檢測依賴任務並自動（觸）發。第四步，開發組可以（按）項目大小（進）行分工協作，將（各）模塊的研發任務（提交）執行；研發過程中仍然可以繼續補充需求和設計細節、重新生成任務，貼近真實開發場景。當任務階段性完成時，可以檢查生成內容、修改調整後發布預覽。當項目中的所有模塊和任務都被執行完成時，應用完成搭（建）。在我們的實踐中發現，SDD 模式極大地提升了 AI 生成的精準性，通過人機協作的方式實現企業級（開發）。

OK，這個產品介紹，就是我們基於 SDD 的理念加上可視化平台的底座，實現了一個「軟件開發自動化研發」的平台。

## 六、需求工程（EARS）

這裡面有一個非常關鍵的點，叫做「需求工程」。我們講到 SDD 關鍵的點就是——spec 到底怎麼寫？什麼樣的 spec 人能看懂、AI 也能看懂？這其實是一個非常古老的概念，就是「如何去標準化地描述需求」。在整個軟件研發的過程中，我們選擇了 **EARS**（需求語法）這樣一個標準的需求模式。它是一個非常輕量、結構化的方法，可以透過規範的自然語言去把需求描述清楚。（EARS）本來是用來做航天發動機控制的（Rolls-Royce 為航發控制系統提出），大家其實可能了解到像 **Kiro** 它也是使用這個 EARS 語（法）。它的結構其實比較清楚：「在什麼樣的條件下、當（可選的）什麼觸發條件時，系統必須怎麼樣」。

我給大家舉幾個例子。比如像「用戶登錄功能」，你的產品可能會寫「系統應該讓用戶登錄方便一點、出錯（有）提（示）」；那麼重（寫）之後會變成「當用戶輸入用戶名、密碼並點擊登錄時，系統應驗證（賬號密碼）是否匹配；若驗證失敗，應顯示『用戶名和密碼錯誤』」——這就是一個典型的「事件驅動型」的產品描述。比如像「用戶編輯內容時最好能自動保存」，那麼它會改成「（當）編輯停止輸入超過五秒，系統應（自）動保存」等等。

這些例子本質上——我們會對需求先去做標準化。因為你如果連需求都無法跟人和 AI 達成共識，你後面的東西全部是有問題的。所以你可能看到網上有很多「spec 專（家）」，他拿那個 OpenSpec，隨便丟一段需求，它好像寫得非常快，但後來發現其實寫的都是「答非所問」的東西。所以我們重點就是要做需求的（標準化）。這個點就是：第一，我會消除模糊詞，比如「最好、方便」什麼的，變成「應」和「必須」；然後明確觸發條件，把複合的需求拆分成多條描述；另外一點就是你的需求要「可量（化）」，比如你不能寫「太慢」，我們通常會（寫）「兩秒內」。這就是需求工程 / 需求標準化的過程。

其實在這個功能上我們也調研了很多方案，比如像 user story mapping、（各種）需求模式等等，最終還是選擇了 **EARS**——我們覺得它語法比較簡單、可測（試）性比較強，它是非常適合需求工程這個（場景）的。還有一點，就是我們在整個開發過程中，比如這是用戶的原始需求（是一個文檔），你轉換完了以後，你（會想）「我要看到我到底（生成）什麼東西、關聯了什麼東西」——我們還做了需求的管理，能夠把轉換出來的標準需求跟原始需求關聯上，便於去澄清和關聯（問題）。

接下來還有一個很大的問題：比如我們有很多老（代）（碼），每個公司都有自己的（歷史遺留系統），可能這個叫做「主權代碼」，每個人（都不敢）改動，甚至有很多老（系統沒有）記錄。因為我們整個客戶是做 ToB 為主，那麼「（存量系統）改不動」其實是 ToB 客戶一個非常大的痛（點）。所以通過 Spec Driven、或者說需求工程，我們也可以把這個事情變成一個可解的方案：我們提供了一個編輯器插件，叫做「倉庫（理解）插件」，你可以在這裡面直接跟它對話去生成對應的 spec，這個 spec 也是基於我們標準需求進行優化和生成的。然後你可以把這個 spec 直接丟到開發平台裡面——比如我們先做一個（研）（發）（解讀），然後再生成 spec；上（傳）spec 以後，你可以把這個 spec 直接導入到（低碼）開發平台裡面去，然後它就會做相關的開發。還有一點比較重要的：很多老系統的 API 是要保持一致的，比如你這個 API 變了以後，別人依賴的服務就掛了。所以你在重（構）的過程中還要保持 API 的一致（性）。所以這個地方不僅會把需求放到 spec 上面，還會把技術設計（比如 API 接口）也放到我們的 spec 裡面去。最終我們可能就把原來的老系統「翻譯」成了一個新系統。

## 七、大規模 SDD 任務的 Harness Engineering

下面就開始講整個方案到底用到什麼樣的技術，我們稱這個叫做「大規模 SDD 任務的 harness engineering」。

首先，低代碼本身的底座是什麼樣的？我們平台本身有一個很天然的優勢：它所有的（可視化）本質上都是我們一個「（可視化）（DSL）」——我們叫做 **NASL** 語言——的一部分，包括頁面、邏輯、數據定義、數據查詢，都是生成 NASL 語言對應的一個 DSL。所以它天然是一個非常受限、約束性非常強的（開發）平台。所以其實它的 AI（化）也要非常簡單，就是我們可能把一些可視化的方式進行 AI 交互、輸入（生成）（DSL）就好了。

然後整個產品本身，我們還是需要一個「代碼智能體」。這裡面，其實在執行（過程）中你會想到：我是不是用 Claude Code 也能夠去做這個 spec 生成、或者代碼生成等等？這裡面其實我們做了一個自（研）的 AI coding 工具，叫做（CodeWave Agent），這個是開源的。為什麼要做這個事？不是說要造輪子——這個項目是完全 spec 開發的，如果大家（有）興趣訪問一下這個 GitHub，可以看到裡面沒有任何一行人寫的（代碼），全部都是 Spec Driven 自己開發的（就這個平台是「自己開發自己」）。所以我們希望能夠證明：spec + constitution 是能夠完成比較複雜的項目開發的——這個 Agent 有 12 萬行代碼、有 72 個 spec，整個過程都是用 spec 開發的。

下面其實我們也對比了像 Claude Code 的一些功能，我們會發現在 Claude Code 基礎（上）我們還增強了很多功能。這個點呢，我們還是希望做一些公司特定的、或者說我們自己實踐下比較有用的（增強）。比如 Claude Code 在 **LSP（Language Server）** 支持上其實糾結了很久，包括它去年 12 月份可能才（提）（供）（支持）、後面又下線了——讓我覺得單純的 grep 其實是比較難以滿足需求的，特別是 Java 的應用，所以我們也引入了 LSP 的工具，等等，包括 spec 的工作流和 constitution 等。

那為什麼我（做）這個事呢？其實本質上來講就是叫做 **dogfooding**——你在 AI 時代一定要做 dogfooding，就是「自己的狗糧自己要吃」。我們要真實去感受到整個 spec 的（痛點）是哪裡的，然後 spec 的過程中哪些步驟是要有人工介入的；工具好不好用，是做工具的人最清楚的。

下面就是整個的流程——我們稱之為「圍繞 NASL 生成的 SDD 流程」，整個跑在 **CodeWave 可視化編輯器** 之上，從下到上分四層：

**第一層「需求標準化」：** 文檔上傳 → 文檔解析 → 多模態處理 → 大綱抽取 → EARS 轉換 / 需求澄清。就是我會把文檔進行上傳和解析；因為文檔裡面都會有很多圖片，我們會做多模態的處理，然後抽取大綱；再通過 EARS 做需求轉換與澄清。

**第二層「技術設計」：** 領域模型設計 → 領域服務設計 → 外部依賴（組件、中間件、API）設計 → 頁面設計、UI 風格注入、依賴組件選擇和召回。在這個過程中，我們還設計了一個功能：如果你的資產或者組件不夠用，我還會（喚）起「資產快速接入」，用（pull）的方式給你生成一個組件。

**第三層「NASL 生成」：** 數據模型開發 → 服務端邏輯開發 → 前端頁面開發 → 開發清單檢查、NASL 代碼生成、可視化渲染。也就是我們去生成整個的 NASL 語言，包括數據模型、服務端邏輯、前端頁面。

**第四層「驗證」：** NASL LS 檢查（通過 Language Server 檢查語言的合法性）→ NASL Fixer（對特殊場景進行工程修復）→ UI E2E TDD（通過 Spec 生成的用例測試）。開發完了以後，比較重要的就是我們會做「代碼的檢查和運行」——這裡會有一個沙箱的環境，通過 NASL Language Server 去驗證語言的合法性，對於一些特殊場景用 NASL Fixer（做）工程修復，最後再通過 Spec 生成的用例做 UI E2E TDD 測試。

這個過程其實非常複雜，它都是在一個智能體裡面去完成的，所以就會面臨一個問題：**大規模的任務怎麼樣去保證穩定性？**

### 智能體架構選型

這裡我們就講到一個叫做「智能體架構選型」的問題。市面上已經有三類大規模的智能體（架構）：

最早我們叫做 **Manus（類）**——剛才講到其實是在 23 年就提出來的一個非常有意思的智能體方式，叫做 **plan-and-execute** 以及 **ReAct** 的思路：你來了一個任務以後，大模型會自動把任務給你做拆解，然後每個步驟進行一個觀察（observe），去判斷自己的任務執行到什麼程度。它的優點是「開放性非常非常強」，最大限度地借助大模型本身的任務規劃和任務處理能力；缺點很明顯——當你真的跑出來問題以後，你 debug 都沒法 debug。所以在 Manus 早期上線的時候，很多人會發現它這個任務比如跑一天、或者跑到（中）（途）斷掉，都不知道什麼情況。

第二類架構，我們叫做「中等靈活性」的：這個情況下，我把下游的實現轉成一個 **skill** 驅動的（模式）。因為 skill 本身是一個天然叫做「漸進式披露（progressive disclosure）」的方案，它會把很多場景的實現固化下來——比如我要畫一張圖、我要寫一個代碼，我可能通過一個 skill 把整個流程固化下來。但因為任務本身比較複雜，我們可能還需要交給智能體本身去做自主的規劃，然後每個 skill 會結合 Agent 去做執行。這個時候其實就不需要（主動）地去管理整個任務的過程了，由 spec 的上下文（去）驅動每個 skill 去執行。這個場景下，在特定的 skill 場景下表現是非常好的，因為它上下文比較隔離，而且 skill 打磨得比較好的話，它任務的穩定性是非常強的——比如我們的代碼（生成）（流程）、比如畫圖這樣的場景，對於這種架構是比較（合適/靈活）的。

第三個場景，我們叫做 **Workflow**。Workflow 其實也是一個非常古老的詞語，說白了就是「（一）個流程引擎」。其實在 AI 時代，還是（有一派）叫做（Workflow）智能體，就像 **Dify** 或者說 **Coze**、**n8n** 這種產品，其實都是典型的 Workflow 智能體——它不相信 AI 自己的編排和 plan 的能力，它認為「我所有的東西、我的任務一旦固化了，我就是一個 Workflow，我不需要你去發揮」。所以在固定的場景裡面，我們其實是非常建議使用 Workflow 智能體的：比如很多企業裡面做 AI agent 的落地，它其實也是會去使用 Workflow。它的好處就是「消耗比較少、固定的流程執行非常準確」，壞處就是「開放性非常差」。（打個比方）第一個（plan-execute）我們可能叫做「龍蝦」（OpenClaw 式），最後一個可能叫做「Dify」——這其實代表了兩類智能體技術的（分野）。

### 知識工程

其實我們講到 harness 工程，除了智能體架構的選擇，它還有一個叫做「知識工程」：就是你開發過程中如果引入了新的知識以後，你怎麼去加載進來。我們一開始可能覺得「把所有的知識塞到上下文裡是不是就好了」？（但）大部分模型在上下文超過 80K 的時候都會出現大規模的幻覺。所以我們一定需要去參考像 skill 一樣做一些「漸進式（披露）」，比如我們用「片段知識召回」的方式（後面我會詳細介紹）。

還有一個關鍵的點，就是我要「驗證這個模型的結果」——你 harness 工程每一步跑出來的東西，你要（保證）可信或者對的。所以我們在早期會有一個 **fixer** 或 **checker**，在文件生成（時做）檢查；後期我們覺得這個也不穩定，我們也改成了 **hooks**——hooks 其實是一個「被動檢查」的（機制），就是我每次跑完了代碼以後會檢查（結果）。這就是所謂的「harness（馬具）工程」的三個要素：第一個叫智能體架構、第二叫知識工程、第三叫驗證可（信）性，也就是「駕馭大模型這批快馬」的功能架構。

### 需求標準化（大綱階段）

下面我會展開。比如第一個過程叫做「需求標準化」：如果用戶上傳了 100 頁的需求到你的平台裡面，你怎麼把它變成一個標準的 spec 需求？你是不是讓大模型直接拆一拆就好了？其實也不是這樣的——我們會發現，不管是給 Claude Code、Spec Kit 或者 Kiro 都非常難以處理，因為它上下文就（爆）了。那我們怎麼辦呢？我們一開始會做一個「需求大綱階段」，其實也是借助了「漸進式披露」的思想：我先把目錄、關聯關係以及數（據）（表）分析出來——這是我把一個完整需求拆成各種子模塊，通過這種方式去串聯模（塊）。對於下游原始需求的拆分，我會去開始一點點地遍歷，遍歷的過程中我們會記錄每個模塊對原始需求的位置，然後在上面去做關聯和目錄；非需求的內容我們會流轉到後續環節（比如如果用戶在 PRD 裡面放了一張圖片你應該怎麼處理，後面也會講）。這裡我們也會通過（並發）去做——因為需求（量）非常大，你必須要使用（並發）去做。

### 技術設計（依賴分析 / API Contract）

下一個階段是「技術設計」。技術設計有一個非常關鍵的點叫做「依賴關係處（理）」。大家都知道，我們在正常開發過程中都有一個很關鍵的（東西）叫「對接口」：前端你的界面雖然可以隨便（改），（但）接口肯定是不能亂（改）的，你不能說後端返（回）（讓）它自己去改一改、改成別的樣子。所以在技術設計架構階段，我們做了一個非常關鍵的點，叫做 **API Contract（接口契約）** 層：不管前端和後端，我們定義的是一個「協議層」——我一旦確定了數據庫（數據庫肯定是基本的、都不能動的），數據庫確定了以後，我會設（計）一個叫 API Contract 層，這一層定義所有接口的入參和出參，我所有的前端和後端的接口設計都需要嚴格依賴這個文檔。然後後端生成和前端生成了以後，（它）作為前後端生成頁面的（回）（歸）的輸入來源——前端就不需要去猜「我的接口到底什麼樣」，我直接按照這個 API Contract 契約生成。

當然，在技術設計階段還有一些很複雜的東西，比如「模塊實（體）間（的）依賴」：比如我的商品表依賴一個用戶表、商品（庫存）表依賴商品表等等，我們都會在這個過程中做依賴分析。還有一個可能就是「循環依賴」，我們會做特殊的處理（當然這個一般會直接返給用戶（人工）處理）。比如還有像「跨（模塊）共享的數據」，比如一個物流表可能在物流和配送都需要使用，那這些我們可能要統一的命（名）。這個就是所謂的技術設計的「依賴分析階段」。

### 代碼生成（原子任務 / 增量模型）

下面就是我們叫做「代碼生成階段」。代碼生成階段我們是用大模型去生成 NASL。這裡面有兩個比較重要的點。第一點，我們怎麼去做複雜的代碼（生成）任務。在這裡面我們會發現，比如有 40 家（張）數據庫表、接口（可能）150 家（個）服務端和 60 家（個）頁面，完全是不可（能一次搞定）的。所以我們做了一個事情：一開始我們把 Manus 的方式拋棄了，就是所謂的 execute 和 ReAct 的方式，我們把所有的開發任務變成了「原子任務」，把（一把梭）式的開發變成了一個「增量模型」。其實很多的 AI 開發是一個（一把梭）模型，它很容易——它是開發完以後再去驗證結果；我們是「增量模型」，就是我一開始就把我開發的任務確定好，然後通過工作拆分的方式一步一步地去開（發）。這個缺點就是它可能會比較慢，優點是它可以非常好地去判斷你所有任務的依賴關係以及任務執行，會保證非常穩定。

同時還有一個關鍵點：在 AI 生成的過程中，你能夠通過任務的拆分保證「上下文的乾淨」。因為你如果所有的任務都放到 Agent 裡面去做，你的上下文會塞滿各種各樣的需求和知識；我們拆成小上下文以後，就把任務變得非常乾淨，甚至你可以基於這個去做測試——你可以把整個的（sample）都取出來、重現出來，這個就是「隔離性」。這其實都是（上下文管理）的一些很好的理論。

還有一點，就是我的 NASL 是有很多私有知識的，我是不是一定要去訓練我的（模）型？所以這裡我們還是參考了 skill 的「漸進式披露」的原則：我首先會做一個「摘要（層）」，我會告訴模型我有哪些（DSL）語言、每個資源什麼領域；然後詳細的召回，我提供了一個 **MCP** 的工具，當模型自己去決定「我在這個頁面比如要生成一個（CRUD）頁面，它可能需要表格、需要數據實體、需要 CRUD 邏輯」，我就用這個（MCP knowledge）去自己召回。然後我還會把所有的文檔變成「文檔化」的獨立知識塊，每個知識塊不超過 1500（字）——這其實是避免上下文（爆）（炸/暴露）；然後我們還通過（query）這個方法去（做）（檢）（索），同時我們在文檔裡面還要加上（few-shot）去補足例子，這也是傳統的大模型提示工程的（做法）。

### 複利工程（經驗自進化）

最後一步，其實我們會講到——我們在跑 Spec Driven 的過程中，它其實要不斷去總結知識。它最大的問題就是「它不知道原來做的這個知識是什麼樣子」：比如你原來頁面裡面有些（概念/約定），它不是個代碼層面的（約定），它肯定是需求層面的（約定）。其實像 Claude Code 等，他們其實會嘗試通過 grep 的方式去找相關的邏輯；那如果你代碼層面找不到這樣的需求層面的邏輯，它需要去顯式地（沉澱）。所以我們也引入了一個新的概念，叫做（複利工程）：就是你每次跑完了以後，我會去總結一些經驗，把解決的問題進行記錄，形成一個團隊的資產。我們希望我們的智能體是一個「自進化」的開發——當然我們會發現最近很多（工具）也實現了這樣一個功能，就是「我自己總結自己」。

還有一點，因為我本身是負責（文檔智能 /）知識工程的負責人，那麼我們本身會有「文檔解析」的能力，我們也最大限度地復用了我們文檔解析的能力（這個平台就是（我們的文檔智能平台），大家感興趣可以看一下）。我們還是會去做相關的文檔解析的對比，比如像 MinerU、Vision 等等。在現在的技術，其實逐步都不需要（傳統 OCR/版面）算法了，逐步開始出現「多模態大模型（直接）解析」的方法。這裡面我簡單也列了一下不同方案的對比，這裡因為時間有限我就不展（開）。

### 圖片處理

下面有個比較有意思的東西：如果你的需求裡面有圖片怎麼辦？首先我要去判斷一下它到底是個「原型圖」還是「示意圖」，我需要去接入一個智能體。原型圖其實有兩種概念：第一，它可能是「描述一個需求」——就是我可能話說不清楚、用圖示一（下），這裡面我會轉成需求描述；第二，它也是個「視覺參考」，比如一個「確認、取消」的按鈕，它其實是一個視覺描述。所以我們也設計了一套叫做「視覺和交互描述的 DSL」，比如你的頁面的左右是怎麼樣的、（布局）是怎麼樣的、分幾塊等等。這裡可以同時傳入文字和圖片的信息去（增強）理解。當然像架構圖什麼的，我們是直接轉換需求放到 PRD 裡面；視覺就比較好處理了，我們直接轉成（視覺）DSL 去加入到上下文裡面去生成這個頁（面）。

### 沙箱（Sandbox）

最後一個講到的基礎建設就是沙箱。沙箱在 AI（編碼/上手）的過程中是非常重要的：因為傳統的後端服務是比較可控的、行為模式比較可預測、權限是有限的；但是 AI agent 的複雜行為非常多，我們會遇到很多情況，比如「我的 AI 把自己的代碼刪掉、清掉庫」什麼的，所以必須要有一個很強的沙箱能力去管理整個 AI 的執行環境。

這裡面我們也對比了很多方案。最早是使用 **E2B**，E2B 做到了一個非常好的低資源佔用和高的隔離（性），但是它的部署和（私有化）成本非常高——如果用過 E2B 的同學會發現它（幾乎）做不了私有化。然後我們又對比了像 Docker、虛擬機等等，最後還是參考 Claude Code 選擇了 **Claude Code 的 sandbox 模式**——就是它使用的（輕量級）（sandbox）。我們這個方案非常適合於（我們的場景）：它不需要很強的權限，但是它啟動非常非常快，命令（執行）也很快。

這是整個的架（構）圖，快速講一下：我們會有一個 **sandbox manager** 會去（喚）起沙箱，然後在每個服務器（集）群上我們有一個 **sandbox proxy**，它會去創建和銷毀沙箱；然後在每個機器上面，我們會有一個叫 **sandbox instance**，這裡面有個 **sidecar** 去管理沙箱的狀態、還有（喚）起（實例）等等（這（都）是在沙箱集群裡面的）。如果沙箱出現了問題，我們會（由）sandbox proxy 收集，然後由 sandbox manager 去管理——這就是一個沙箱的集群。這樣其實能夠有效做到整個代碼生成（的隔離與穩定）。

### Harness 工程小結

總結一下怎麼去設計一個很好的 harness 工程：一定是「每個 skill 對應一個（乾淨的）上下文」是非常重要的，然後（主）（Agent）只負責調度，甚至我都不需要（主 Agent）、我用 Workflow 的方式，那每個 skill 只幹自己的東西，一切的狀態共享都（走）文件。這裡我們也應用了叫 **context offload** 的技術，就是我要把上下文卸（載）（到）文件，保證整個任務裡面可以在（中間）去介入和修（改）。然後每個結果都是要可驗證的，一定要通過 valid（ate），一旦生（成）了錯誤，後（面）（校）驗都會失敗。所以這裡面也是我們所謂 harness 工程的三要素：第一個是智能體的選擇，第二個是任務的管理，第三是結果的驗證。

## 八、度量與模型訓練

下面就是我們講到——為了優化整個產品，我們也設計了很多的 benchmark，這裡因為時間有限我就講快一點。我們很多的東西，包括需求解析、AI 對話修改等，我們都建立了不同的 benchmark。因為叫做「**no benchmark, no（optimization）**」——你沒有 benchmark，你是不知道你產品的邊界、模型的能力等等的。包括像需求解析、圖片識別、需求標準（化）、技術設計、或者擴展組件、外部依賴（接入），我們都會有必要的測試（集）保證，然後保證產品的質量是穩定的。如果出現 bad case，會回（流）到裡面。

接下來，其實我們也做了「單一功能的 AI（提效）度量」以及「復合功能的 AI 提效度量」。單一功能這個我就直接（展示）一下就好了，其實比較簡單，就是 AI 功能的平均提效率，就是「手工開發（耗）時 減去 AI 功能的（耗）時」除以「（手）工開發（耗）時」。那提效率是從開發效率、需求還原度、代碼質量幾個維度去看的。

然後為了去做我們自己的大模型，我們其實也會去做代碼生成的 benchmark，我們會採用像（權威）網站的、業內的標準。（比如）前年可能只有 54%，基於我們在工程修復和模型微調，得到 80% 的（通過）（率）。這裡我們也講到怎麼去選擇一個代碼模型的「模型底座」訓練：我們會考察代碼生成能力、（評）測及補全能力、推理能力——這裡其實有個重點是「推理能力」，其實很多 benchmark（沒有）考慮，因為其實代碼生成它不只是文本（生成），你要讓大模型知道這個代碼到底是什麼意思。這裡其實也不是給阿里打廣（告），其實 **Qwen2.5-Coder** 當年（作）為模型基座確實是非常好。

整個訓練過程，就是我們會去開源社區收集一些（代）碼，然後轉成 NASL，這個叫做「指（令）（構）造」；然後我們會建立一個（NASL）語言運行的沙（箱），通過（拒絕採樣 / rejection sampling）合成很多訓練的（樣本），構造用來訓練的數據（集）；然後再做數據的後處理。同時我們在 SFT 的過程中去構建這個「採樣代碼」的方案，然後去使用 **RL** 方案去做數據的回流和提升。最後我們其實也會做一個叫「偏好對齊」，因為我們會發現訓練情況中「bad case 可能比 good case 更有效」，所以我們會使用 **DPO** 的「三元組」策略：我會構造一個「問題 / 正確代碼 / 錯誤代碼」的三元組去強化整個訓練。

整個過程我們會建立到我們的 AI 工程化平台上，它其實就是一個「回流」的過程：首先 benchmark 用來去識別產品的邊界，也就是我們所謂的（product-model fit）——我要知道我的（模）型做到什麼程度才能支持整個產品的（落地）。另外，上線以後觀測到（的問題）我們也會回流到我們的 benchmark（平台）；然後產品 AI 功能升級、或者說大模型廠商（發新模型）——大半夜發（布）模型以後，我們也可以快速地去回歸測試，發現這個是不是要升級了。比如昨天升了這個 **Claude 4.7**，我們就第一時間進行了一個評測，結果發現（提升多少）。

## 九、總結

下面就做一個總結：本質是什麼？就是回歸到最開始——它是一個「（熵/混）（亂）」的問題。什麼叫「（熵）」？就是混亂程度。你跟人跟人之間對話、或者說產品裡給你一個 PRD、你說「你給我看一看、開始幹」，這個時候其實「混亂度」是非常非常高的，叫做「混沌階段」，它其實是（不可控）的。那第一次，我們（EARS/標準）化以後、標準化以後，我們可能叫做「原始需求（的混亂度）」就下降了；第二，如果我們把交互稿和設計稿都準備好以後，設計和交互的（不確定性）都下降；那麼我們通過代碼約束，我們把整個的「有序」——整個的（輸入）和輸出——變得可觀測。所以 Spec Driven 的本質，並不是什麼非常高深的理念，它只是一個「通過形式化的方式來降低混亂度（熵）」的（方法）。

這裡簡單做個產品對比：我們其實相比於（一般 AI coding）來講，本身會有像「（研發全）（流程）」、資產（沉澱）、應用生命週期管理、以及像（低碼的）（可視化）等這種部分（優勢）。（產品）（廣告）就不（展）（開）了，大家如果感興趣的話可以體驗一下——因為我們目前還是在公測階段，是一個「邀測」情況，因為 spec 實在是太（貴）了。如果大家感興趣的話，可以在我們的官網去聯繫我們的同學去預（約）、試用一下。我們現在可能有 230 家（客戶），可能一個月光 token 就燒大幾十萬，所以還是比較「肉（痛）」的。

然後下面其實我們也會做一些未來規劃：比如 spec 跟 NASL 的「雙向（同步）」——比如你改了代碼以後，你要（同）步到 spec，這個其實是非常重要的。因為我們會發現很多代碼用 spec 開發的時候，這個 spec 逐（漸）就失效了——比如你（手）改代碼以後，（原來的）spec 就變成一個（屎）（了），所以你既有代碼（屎山）又有 spec（屎山），這很不對了。另外，我們會（優）化生成速度，然後（適）（配）國產的模型——因為 Claude 實在是太「綁架」（我們）了，我們其實這幾個月一直在（跟它）做鬥爭，動不動有封號、然後限流等等，然後還打（關稅）（仗）。然後後面我們還會跟低代碼平台去做結合。

好了，今天的分享就到此，謝謝，非常感謝老師。
