## 一、AI 時代架構範式躍遷的四大變量

### 變量一：軟件工程正從「確定性」進入「非確定性」

第一個，我認為是軟件工程在從「確定性」向「非確定性」（演進）。這個觀點不同人的表達邏輯會不一樣，但大家可以有一個共識。如果我們回溯一下：**從 2014 年的微服務架構（Micro Services），到 2019 年的雲原生架構（Cloud Native），到 2026 年的 Agent Engineering**（時間前後這是一個區間）。2019 年的雲原生架構——從微服務到容器、到 Service Mesh、還有整個雲的進步——2019 年的時候，其實我和小兵在一起，在阿里巴巴的「全面上雲」戰役中，當時轟轟烈烈地感受到了技術進步的巨大躍遷。而讓我再次有這個感覺的，就是今年，所以這也是為什麼我特意跑到北京再和大家做一個交流。我認為它是一個「巨大創新誕生」的世紀：就像圍繞 Agent 的整個（開發）（工具）鏈、甚至中間件都會被重寫，甚至整個的（運行時/中間件）也會重寫——因為我等會會展開，現在的（運行時）其實是為移動互聯網設計的，而不是為 Agent 或 AI 時代設計的。

大家可以看我左邊這張圖，叫「確定性的系統」。什麼是確定性的系統呢？如果我們在微服務時代，大家都知道我們按照 Service 去做劃分（Service A/B/C）。其實微服務的架構——不管是領域驅動、還是面向服務的設計、還是延伸出來的 API 到 SPI——它都有很強的確定性。然後我們整個計算的底層設施，就是為（服務）提供保障，保障整個的高可用和一定的彈性。

我印象特別深的一個場景：我做國際化電商的時候，我們做雙 11——2020 年的時候，我們在牆上打印了一個像 100 寸電視機那樣大的一張紙。打印了什麼呢？就是從商品（詳情）、到交易下（單）、到下單渲染、下單提交、支付……每一個環節、每一個接口的調用，涉及到緩存、數據庫，然後對應的 QPS、對應的 QPS 放大比例、對應的數據庫實例數、線上應用的容器數。大家可以想像，我貼在牆上，就是為了在做（大促）緊急（決策）的時候可以有一個快速的決策。但大家想想，它這個（場景）為什麼高度確定呢？因為每個接口調用背後的邏輯都是非常確定的——調用庫存就是庫存，扣庫存可能失敗、可能成功。這個邏輯上有它的複雜性、可（能有）挑戰（比如整個高可用邏輯），但那是「上一個時代」。

對於這個時代來講，「非確定性」的典型體現：第一個，我認為在模型的 **planning**（規劃）環節其實是不確定的。大家都知道，早期大家都會談 AI 的「幻覺」問題——我現在其實（是這樣看的）：如果有 AI 用戶給我提「（怎麼）解決幻覺問題」，我就覺得他沒有用好 AI。為什麼呢？我覺得這是 AI 一個典型的「創造力」的體現。我們可以用一定的方法來規避一定的（幻覺），但它仍然是「第一次、第二次、第三次執行結果不一樣」。另外，我們延伸出來的 Context Engineering 裡面，大家耳熟（能詳）的像 Memory、像 RAG——Memory 其實是一個特別有意思的技術機制，它可以讓我們的軟件「越用越智能」成為可能。我們屋子裡的同學做系統多少年了，以前我們做的相對是「規則驅動」和「靜態系統」，一直有一個願望或夢想：我們的系統是否能夠越用越智能？在當時的基礎（設施）上是實現不了的，但現在我覺得完全可以，而 Memory 是裡面非常重要的一個機制。所以 Memory 其實是有一個「自進化」的機制，而進化之後就會導致它的執行結果會有差異。

然後現在來講，我相信大家都在玩 OpenClaw（小龍蝦），它裡面甚至都有 Skill 的「自進化」——所謂 Skill 自進化，是說用戶輸入的錯誤信息，它可以自動基於錯誤信息去 verify、生成一個新的 Skill，而這裡面又是一個不確定性的體現。另外，關於 **Model Engineering**——我認為現在的（後訓練）可能還集中在少數算法同學手裡，但後續，尤其是 RL，我認為像 **Agent RL** 會是每一個工程技術團隊的標配。為什麼呢？因為我覺得它也是相對有效的。當然大家可能有一些「普遍的（教）訓」：就是大模型的（本身）能力在快速提升，那我做的後訓練的模型是否（還有價值）？我認為在「一定窗口」之下 post-training 仍然有效果，而這整個也是自進化的典型體現，這又給 Agent 帶來了新的一層不確定性。

所以我認為，如果從發展歷程來講：微服務、雲原生其實都是在工程時代、相對一定標準之下追求「確定性」；而 Agent 呢，它的「不確定性」會越來越高。

### 變量二：從「WorkLoad」的視角看 Agent 的長週期與不確定性

第二個，我們從 **WorkLoad** 的視角（來看）。大家可以看我左邊這張圖：如果我們今天把互聯網的架構範式做一個最頂層的抽象——我在 2019 年到 2023 年畫了大量的架構圖，每年其實超百張架構圖——畫出來最後的效果，就是我腦海中天然會形成一張「（雲）（的）形態」的圖。如果我們把互聯網架構的模式做一個抽象：不管是以服務化為核心的 request-response 模式（RPC）、還是以消息為核心的 Pub/Sub 模式、還是以 Scheduled Task 為核心的 TimerTask 模式、還是 Streaming 模式，然後上層可能是 Web UI、可能是 Mobile UI。（然後）排除大數據的離線計算，絕大多數場景下都是「短平快」——大家感覺一下：一次請求 500 毫秒，一個下單的 RT 一秒以內。我們之前一直追求的都是這些，而這裡面的特點就是「短平快」：調用鏈路沒那麼長，給到用戶快速返回，且成功和失敗是非常確定的。如果把這邊的架構來（歸類），這基本上就是非常典型的互聯網架構的特點。不管是 API、還是 Event、還是 Task，我認為它都是相對「中短期」——短和長的界限我認為沒有一個明確的界限，大家姑且可以按「一分鐘以內和一分鐘以上」來劃分，但以前我們在互聯網的在線業務上，幾乎沒有超級（長的）（任務）。

那對於 AI 時代的變化是什麼？我認為有四個不同：

**第一，生命週期。** 以前是毫秒（級），現在可能到分鐘了；以前是「請求完即釋放」，現在可能是有一個長週期的（駐留）。我們自己內部的 Agent 現在跑個五分鐘、十分鐘我覺得已經是比較長了；而現在最新的（Agent）跑到 30 分鐘、45 分鐘。剛剛的 Opus 4.7 跑（多長）時間我還沒看，但我春節期間有一個「暴論」的預判：我覺得 2026 年，甚至我們 Agent 跑三小時、六小時可以成為常（態）。大家想想，一個 Agent 一個任務跑三小時、六小時，對於整個 WorkLoad 是一個巨大的衝擊。就像今天早上我還跟我們 sandbox 開源的同學在做交流：以前我們是「一個微服務對應的容器數是相對確定的」，大家具備一定彈性；但大家想，這個在「長中期」的情況下已經（不適用）了。就是說，我們未來是否是一個 **agent runtime + agent sandbox** 結合的方式：在確定性的容器裡面去做推理，然後它（需要）（大）（算）（力）計算的時候，由「無限擴」的 sandbox 去做執行——例如有幾個或者幾十個 sandbox 去做它的規模化任務執行。那未來這個對於在線架構就會發生巨大變化：我們以前是說 n 個容器，我認為未來是「**n 個 container + m 個 sandbox**」的一個標準架構，而這裡面 sandbox 的整個體系剛剛才開始。

**第二，執行路徑。** 之前的執行定義是「預先定義」的，我們可以叫它 Hard Code、或者叫它 DAG（有向）流的編排；而現在是「運行時」的——這個規則會隨著上下文（涌現）有一些變化。

**第三，狀態管理。** 之前的狀態可以稱之為「外置」——我們做的微服務架構更多是「無狀態」，把東西存在數據庫、存在（緩）存裡面，也是一種外置的方式，這種架構已經相對標準了。因為「有狀態」它天然彈性不好：就像如果我們在容器裡面有大量的計算，它的擴容和縮容必然面臨問題。甚至我以前在做整個架構（時發現）：應用啟動時間過長也是一種「有狀態」的體現，因為你的 scaling 時間、或者你應對故（障）去做重啟的時間就會大大延長。所以現在來講，「上下文」其實可能成為一個更加有意思的話題：上下文的壓縮、上下文的（間）（歇）（性）（總）結、以 Memory 更加結構化的方式把它存儲出來、甚至通過 RAG 的「知識庫外置增強」的方式、或者通過 graph 的「更加多維的知識庫連接」——而上下文（管理）非常典型地已經成了一個（顯學）。我去年 10 月份在內部提了一個理念，叫「**紮根微服務架構，擁抱（AI）原（生）**」。因為微服務架構的技術成（熟）度已經非常高了：我之前有一張圖推演過去 20 年和未來五年的工程技術架構——從底下的雲原生、到中間的大數據、數據庫、微服務、和端側，大家感覺一下，過去五年整個所有的變量都在 AI。那對於微服務，成熟度已經很高了，作為工程技術來講，我認為就是要「紮根微服務」，然後不停地去再推進、學習一些基本的邏輯。

**第四，結果反饋。** 以前的成功和失敗其實是非常確定的（失敗之後也可以重試，這個錯誤都是經過嚴謹設計的），但現在（結果是模糊的）：你運行一次和運行第二次，結果還有可能不一樣，而且有的時候還需要 Human（人）介入去做結果正確性的校驗。所以你會發現軟件也在發生變化——之前的軟件是「給人用的」，現在的軟件可能一部分給人用、一部分給 Agent 用，可能走著走著，Agent 用得越來越多。春節期間我相信大家都在觀測 SaaS 的股票，我現在覺得可能 SaaS（會有拐點），這個拐點可能就在 2027 年。當然好多廠商也在做對應的應對策略。我也認為，如果我們現在——尤其我們做內部運營系統——一旦我們的消費者使用 App 的日活（DAU）超過（一半）、超過 5 億的時候，我相信我們內部的運營系統如果沒有 AI 化、如果沒有大力擁抱 AI，會被嫌棄、會被（淘汰）。這是稍微延伸了一點，對於 SaaS、對於未來的變化——因為 SaaS 的下一個可能是 **Agent Service** 或者 **Result Service**。

所以這是從 WorkLoad 的角度。如果我們從一個更加深入和全局的視角看的話，大家可以想，我們「運行態」的架構都會發生非常大的變化，而這個變化我認為才剛開始——就像剛才我舉的 sandbox 的例子，可能就是一個非常典型的實現。

另外，不僅是（運行態），研發也在發生變化。我相信大家可能會去思考什麼是 **AI friendly**。就像以前我們追求什麼？我們追求的是「前後端分離」、前端代碼和後端代碼分開，追求的是「運行時配置和代碼分開」——因為運行時配置相對（易）改。大家想，這肯定就是「AI 不友好」的，那是「human friendly」的。那 AI friendly 是什麼呢？我的代碼（都）（放）在一起、然後 AI 都能讀懂，其實是非常方便 AI 做 coding、去做各種邏輯的。所以其實這是一個非常典型的體現。另外像 MCP——大家都知道，以前我們的服務化接口都是為「系統」去做設計的，它的入參和出參都是（複雜）（的）（數據對象 DAO）；而現在大家都知道 MCP 裡面如果參數相對比較精簡，AI 可能會處理得更好。當然現在也有 **CLI** 了，我等會也會展開 CLI 的一些邏輯。所以以此來推斷整個的架構範式躍遷，大家心中可能會有一張大圖，在工作開展的時候會（有幫助）。

### 變量三：從傳統分層架構到「穩定態 + 敏捷態」雙態架構

第三個叫什麼呢？叫「從傳統分層到雙態架構」。這個結論很簡單，但我思考了好幾週的時間。以前我們的分層架構是一個六層或者五層的架構，典型（範式）——幾乎所有的 CTO 和技術平台的負責人都會說「我這是多少層的」，而那個分層架構是「按照技術的邏輯」在展開。為什麼？因為技術在有巨大的變量和不確定性，所以大家就會有這樣的趨勢：（編程）語言在變化、大數據在變化，然後微服務相對穩定但仍然可以更成熟，包括端側現在幾乎所有的大廠都在推「全棧化」——而菜鳥其實在兩年前已經完成了全棧化的變革，我們現在的（研發側）跟測試、前端的比（例）都已經是極高了。這裡面我認為這是「上一代」的傳統分層範式。

那下一代是什麼呢？AI 時代的下一代是什麼呢？我琢磨了很長時間，結論是：我們的傳統系統仍然有效、仍然有用，但是它會「退化」——退化成 **System of Record**（記錄型系統），成為一個技術型的系統。記錄型系統負責什麼呢？負責「穩健」——也就是我們整個的 **Clean Core Service**（為什麼是 Clean/Core 呢？因為我們的商業是嚴肅的、運行是嚴謹的，它一定要通過更加結構化的方法來做設計、做體現）。而這裡面我覺得它承載的（是）核心商業，同時可能會是「**本體論**」（Ontology）。本體論——我相信在座大家都有關注 **Palantir** 這家公司，它成立 20 年，前段時間說它「終於等到了時代」，它的 **Ontology**（本體）架構設計又再一次拔到了新的高度。它的 CEO（Alex）Karp 是「哲學存在主義」的一個人。但我研究了很長時間，我覺得可能在我們國內落地本體論，因為它需要真的還是持續、高階的領域專家不停地去做研究設計——這和我們早年的「領域架構」很像，領域架構如果沒有一個穩健的團隊、持續懂的（架構）師群體，其實很難做。但我覺得不妨礙——這一層一定是要經過嚴謹設計的。

再往上是什麼呢？往上是我們的 **Invocation Service**、或者說叫 **Agent Service**，因為整個創新會圍繞 Agent 來展開。這一層負責什麼呢？負責「敏捷、彈（性）」。大家想，我認為每一個 CTO 或技術（負責人）都會被挑戰——敏捷啊、效率啊、能不能更快一點、能不能做得更多一點。而我認為，假如有了這個「分（層）」之後，下場（好處）就是：傳統的微服務架構它可以改造成「AI 更友好」的，然後它負責「穩健」，上一層的 Agent 負責「創新」。甚至我覺得以現在的形態——假如一個公司內部的 Agent 有個很好的框架，產品經理也可以是「Agent 的工程師」。我在內部講：我們內部「冷（coding）」要從古法（編程）躍遷到「AI 編程」，我的產品經理要從「古典 PD」躍遷到「**AI PD**」，躍遷不過去的就被淘汰——這個時代我覺得是很殘忍的，淘汰你的不是（別人），是時代。而 AI PD 的典型體現，我們內部現在運（作）下來：第一，PRD 能不能通過（低代碼/LLM）的方式去做「對焦」？大家都知道一個 PRD 上接十個技術、十個業務，下接十個開發，它如果更加高效了，整個效率會更（高）。那 PRD 是否可以直接（生成）？第二，我現在鼓勵我的 PD 去寫 SD（spec）、「搶開發的活」，然後讓開發去幹更加高深、更加底層、更加深入的 Agent 的（構）建。現在實驗下來我覺得這個效果非常好，甚至我們現在在鼓勵我們業務同學去寫（spec），把他們的經驗能夠（沉澱/推）出來。我認為這些是從架構延伸出來的「組織的變化」。而「雙態架構」，我現在的預判：它有可能真的會成為一個很核心的架構。

（這個當然是剛拋出來的——就像我春節期間十天時間、每天三四個小時在家裡看，幾乎沒出門，每天寫兩篇文章，激發了我大量的表達（欲）。我寫的第一篇文章叫「token 經濟（學）」，然後沒人看、也沒人（理），因為這個畢竟影響也有限；當（某家）發布了「token 經濟學」之後大家都去看。實際上我覺得早在一個月前，我覺得已經開始有這個觀點邏輯了。所以我現在對於雙態架構的（篤）定性還是比較強的。）

### 變量四：Agent 產品形態演進——從「Chatbot → Reasoning」到「硅基員工」

第四個變量，就是 Agent 的產品形態，從 **Chatbot** 到 **Reasoning**、再到「**硅基員工**」（傳統軟件「響應操作」→ Chatbot「響應問題」→ Copilot「輔助處置」→ Agent / 硅基員工「交付結果」）。我右下角這個「二維象限」其實是非常認真（畫）的一張圖。我們現在的概念很多，那我們用一種什麼樣的框架來理解現在的邏輯呢？我覺得就是通過「**Context 密度 × 智能（Agency）高度**」——有一個二維象限。

第一象限（低）的，就是 Embedding、Copilot 和一定的 Agent，我們可以把它稱之為 **AI-Powered**——它仍然有效、仍然有用，但它創造的智能上限是有限的。第二個是什麼？就是 Agent，或者 Agent 往上是 **Agentic System**——我認為 Agentic System 和它的區別就是「雙態架構」的典型（體現）。再往上，什麼是「**超級自動化**」？我認為 AI 最大的魅力就是讓我們的「超級業務自運（轉）」成為可能了。就像傳統的規則時代、傳統的服務化架構情況下，我的客服自動化可能做到 60%、70% 就是（上限）；而現在 AI 來到，我整個自動化可以幹到 80%、90%，甚至有些場景可以（接近）百（分之百）automation。而這裡面，右邊的這部分我認為是 **AI-Native** 的。

我認為 AI-native 的產品有四個特點：第一，它是「主動」的——就是 OpenClaw 有一個 wake on（主動喚起）的機制，讓你感覺有一個「積極主動的員工」在（旁邊）；第二是「自我進化」，我覺得這是軟件裡面非常有魅力的、也是 AI-native 裡面非常鮮明的一個特點；第三個是 **intent**（意圖）——就是我們現在不管是任務驅動還是目標驅動，它可以去做快速執行；第四個特點我認為叫 **long-horizon**（長程）。（如果大家在思考 AI 的 2B 類產品的特點，我覺得剛才的四個，也可能是當前這種（理解）——因為我現在表達都特別謹慎，以前在（雲計算）時代都很篤定，現在在 AI 時代這個不確定性太強了。就像我這個文檔也是——以前基本上四週之前就成稿了，現在可能真的是一週左右才成稿，因為東西變化太快了。以前一個圖用兩三年，現在一個圖有效期可能真的就兩三個月的時間。因為我定期會給總經理和 CEO 報告，說我這一周約不上、下週再約，我那個稿子可能就要再改（一）點了。）

這裡我延伸一點「生產力（Agent）的幾個特徵」。第一個是 **Skills（托管執行）**——如果大家去翻它（OpenClaw）的代碼，我認為 Skills 從 2025 年 10 月 18 號出現，到 2025 年 12 月成為（普遍）標準之後，OpenClaw（小龍蝦）其實大量激發了它，它的曲線就是這樣一個（陡峭）曲線。Skill 我認為是非常好用的，它可以成為我們業務的「技能經驗」的一個很好的承載，但是它整體偏簡單，處理不了特別複雜的事情——我認為未來可能還會有新的形態，但當前的 Skill 也足以讓我們（把）Agent 從「信息工具」躍遷到「生產工具」。這是一個很大的不同：所謂生產工具，就是可以「調用工具」——那 Skill 很明顯肯定是一個很不錯的方式，我們現在在鼓勵（大家）去寫（Skill），去（沉澱）大量的 Skill。

第二個是 **Memory**——Memory 我認為是特別值得研究的一個領域，我認為一直在被低估。我自己（買了）一個（AI 錄音掛墜，類似 Plaud / Limitless）——就是在這裡拍照的那個、每五分鐘錄一個 15 秒視頻的那個。我問了它們一個問題：「根據你對我的了解，測一下我的 MBTI」，然後測出來我覺得還挺準的，而且它倆基本上一致。這背後源於它們可能有的時候是對於「我的記憶」的一些（提）取。我認為記憶其實是一個非常值得研究的（方向）。2026 年在 Agent 裡面，假如要投入一個大的（賭）注，我認為就是 **long-horizon**——就是「長程智能體」。為什麼呢？我們做的產品不能「出生即（落）後、上線即淘汰」，一定要為「六個月之後的模型能力」去做設計。現在有一個確定性的信息：六七個月後模型（本身）整體的能力會越（強）。所以如果大家現在還是「low-context」的設計、（低）agency 的設計，那你最終出來的效果肯定不好；如果你現在就在規劃和設計「長程」的東西，那你上線的時候就可以天然享受「模型成長帶來的紅利」。這也就是新時代的「（SRE/56？）」。我想說，如果大家想「我是否有場景能夠去做長程智能體」，把整個機制做一個更加不一樣的（拔）（高）。

（三個案例——其實我們內部的案例，我覺得幾十個完全有。我們剛剛做完了 Q4 整個項目的復盤，我覺得效果是遠超最開始預期的。）

### 案例一：AI SRE —— 從人類經驗到 Agent 自動診斷與托管處置

第一個。我自己的電話是「從來不接別人電話」的，為什麼呢？因為以前做 SRE 做了四五年時間，接電話有陰影——因為一接電話就是（故障/告警）。所以現在我那個電話幾乎不接的，除了快遞外賣，（陌生的）都不接。這個場景其實已經有很深的意義了：因為大家都知道 SRE 真的是一個（苦）（力），晚上要（值班），有大量的預警任務，而且是（即時性/突擊性）的，它會不停地干擾你日常的研發任務。而這裡面，假如團隊比較小、負擔比較大，大家又沒有很長的時間去做（治）理（怎麼辦）？

我們這裡經歷了三版演進，我這裡只寫了兩版，第三版我口述。**第一版**是我們整個的 **ReAct 模式**（大家反正都聽過 ReAct 模式——Google 這個很早的時候，差不多去年 9、10 月份發布了它的（那篇 paper）。我覺得 Google 特別擅長「提得比較早，但不一定很好」，就像 **SRE** 這本書大家肯定都看過——是 Google 最先寫的一本書，我覺得那本書寫得（不算特別好），但它很有里程碑意義，因為它足夠早地提出了 SRE 的理念。而我也認為它當時提的 planning（規劃）、Skill 模式、ReAct 模式等等——我認為那些不足以稱之為「架構模式」，頂多是一個局部設計的小（範式）而已。真正的 Agent 架構模式，我認為還需要很長時間，雖然 Anthropic 最新發布了它的五個設計模式，但我也認為現在才剛開始。）

這是 ReAct。ReAct 上線之後，大家肯定都熟悉這個過程：我的大模型和 MCP 工具、和（外部）環境之間有一個調用。但是這裡有一些邏輯——看起來是挺合理的，但是我們線上整個的採納率成果只有 40%，它的效果其實沒那麼好。這裡有兩個核心問題：第一個是「沒有評測能力」。大家都知道，評測肯定是一個很核心的問題——當時我們做評測，如果是 offline 的評測它效果也不一定好，那麼是否可以基於線上真實的數據去做一些（評測/策略）？第二個問題是「沒有系統化引入專家經驗」——它用的只是大模型的通用經驗，那沒有專家經驗它效果肯定是一般的。

所以我們後來又做了一個升級，要把這兩個問題去解決。正好那時間 **Skill** 越來越成熟了（Skill 當時也並不成熟），成熟之後我們發現它是一個很好的「（提）取人類經驗」的方法。現在其實大家都在（提）取這部分，甚至（流程/工作流）大家也都在做這些邏輯。這個搞了之後，我們整個效果有一個很鮮明的變化：大家可以看，我的**採納率 40% → 80%**，然後我的**（夜間預警時效）達標率達到 96.53%**（從 70.55% → 96.53%），然後**處理時長下降 95%**。所以這是 SRE 架構的變遷。

但如果我們把 SRE 的任務做一個抽象：它其實就是「我這裡有一個預警，我去檢索大量的日誌，再基於我的經驗去做一個匹配」。這個場景就是一個「**規則極度密集**」的場景。什麼樣的場景特別適合被 AI（接管）？我認為就是「規則密集」的——不管規則是複雜還是簡單，主要規則夠密集。我印象特別深的：我做（大促）的穩定性（保障）的時候，我列了一個 23 條的 check list，那足夠（全）（面）——那也就意味著在以前全都是靠人執行的，而現在可以是 AI 來執行。

這是我們的第二版（用了 Skill）。我們最近在做我們的**第三版**，也開始在做推廣了：我們想能不能給每一個團隊配置一個 OpenClaw，成為他的「組員」、成為他們組裡面的 **AI SRE 成員**——就是「擬人化」的設計，晚上幫他做值班。因為菜鳥是一家全球化的企業，我們現在海外營收佔比超過 50% 了，所以其實我們有大量的「跨時區/夜間」的工作。如果大家基於責任感偶爾一兩天熬個夜還沒問題，但如果一直持續就是不可長久的。而我給每一個團隊、基於團隊維度（配一個 AI 值班）——大家想，以前擬人化設計的時候，一個團隊十個人，今天 A 值班、明天 B 值班、後天 C 值班；那 OK，我是否有一個「AI 員工」一直在旁邊值班呢？然後把人類員工釋放一部分（也不用釋放全部）。這個對於團隊的體感、對於我們自己用新技術去做改變，我認為肯定會有不一樣（的（效果））。就像 OpenClaw——我給每個團隊配一台電腦，大家都知道我最近的電腦基本上白天都發燙、電池用得很快，因為一直運行各種（Agent）應用。所以未來我們白領的「標（配）」可能是「一台電腦 + N 台（Agent）」去做處理。所以這是 AI SRE 的架構躍遷——從最開始的 ReAct，到 Skill，到現在 OpenClaw 的這種形態去做擬人化設計。

### 案例二：AI 銷售 —— 從 Leads 到 Cash

第二個是我們整個的 **AI 銷售**。銷售這個環節我認為是一個「AI（密度）極大且非常合適」的場景。大家想，從銷售的外呼、到銷售外期的（拜）訪、到客戶入駐之後的整個環節、再到持續的回款環節——這裡面不管是「線索轉化率提升、客戶轉化率提升、客戶流失率下降、還是銷售的人均產（能）」都是非常好的價值。

之前我定義了「五大價值」：一個企業裡面做 AI，第一個是**提效**（這是絕大多數公司內部在做的）；第二個是**降本**（當然提效、降本是一體兩面）；第三個是**提升體驗**；第四個是**促進增長**；第五個是**控制風險**。這裡面，能夠找到「促進增長」的場景，我認為是作為技術負責人或 CTO 來講、大家為數不多的（機會）——因為「提效」大家每個公司都在做，無非是領先三個月到六個月的問題；那 AI 是否可以帶來一些新的能力、新的競爭力、新的長期壁壘？我認為可能是（值得）大家去思考的。

所以我們當時做了一件事，就是 **AI 外呼**。我們有一個外呼團隊十幾個人，但他每天只能打（幾百通）電話；而我們用了 AI 外呼之後可以每天打幾（千/萬）通，把我們積壓了好多年的近百萬條線索很快就消化了。大家想，以前是人的時候，我就想這個東西要多長時間才能消化呀——這個其實都很頭大，因為人打電話這個（有）（情緒）（成本），其實有好多無效的工作在（消耗）。而我們找到了這個場景——我們打電話的最長時間是 **3 分 03 秒**。效果我認為還沒有打到預期，有一定的擬人化（空間），這裡面對於 **ASR、TTS** 的技術都是有非常高的要求的。我最近來到飛機上，我打印了一個資料，我在學什麼呢？我在學**聲學**——我覺得如果我們要把 ASR、TTS 做好，真的可能要去從聲學、從（信號）的這些底層機制去研究得更深，才有可能把這套機制做得更好。

我們的「人均清洗（效率）」、包括呼叫有效（數）、還有意向判斷的準確率都有一個大幅提升（**5x 日均清洗效率、98.99% 意向判斷準確率**）。它這個技術我們現在做的沒有什麼高深的技術，基本上 Context Engineering 就可以完成、就可以達到這個效果了——所以我們這個時候使用的 AI 能力可能只使用了它的一（部分），甚至（十）分（之）一（都）不（到）。所以其實這也是我覺得未來 AI 的魅力和上限還是很高的：具體的 ASR 容錯率、甚至 TTS 進一步的容錯、甚至「打斷」的更加精（準）處理。（AI 銷售，其實就是圍繞客戶建立一套「持續更新的 Memory 系統」：商機線索智能預處理 → 全息客戶畫像（建立全方位客戶級 Memory）→ 智能外呼（通過互動持續更新 Memory）→ 智能運營。而這套 Memory 的核心是四塊拼圖：**Who（這個客戶是誰）、State（客戶現在狀態）、History（客戶歷史事件）、Action（下一步動作）**。）

### 案例三：AI 質控 —— 長程任務 Agent 的關鍵探索突破

第三個場景是「**質控**」。作為物流行業，其實「時效、成本、質量」是一個三角形。質量控制對於「準時送達」——大家作為消費者感受到的是準時送達，但在我們內部是一個「質量控制」。傳統的、數字原生的做質控系統的「三板斧」是什麼呢？第一，大家搞幾百個指標；第二，大家搞一個「一筆訂單或多筆訂單的（工）單機制」；第三，大家搞一個「異常的（處理/罰）（單）」。基本上傳統三板斧——現在我只要在內部看這個質控方案，是「三板斧」的，我就把它定成「古典 PD」；而 **AI PD** 呢，我覺得要基於 AI 的思路來去做質控的設計。人為什麼要去盯「幾百個指標」，而不是盯「幾百萬筆訂單」？因為（人）盯不過來，那 AI 可以盯過來啊——AI 可以盯住每一筆訂單的每一個（節點/場（景））。所以我認為這是 AI 給質控這個領域帶來的最大想像力：以前是（抽樣），現在可以「一筆一筆盯」。（跨境物流時效 SLA 達成率是核心考核指標，傳統人工質檢存在「異常主動感知難、異常歸因難、協同低效、時效慢」等痛點。Agent 驅動的質檢流程分五個 Phase：Phase 1 對業務提單之後的狀態變化自動持續追蹤；Phase 2 檢查關鍵節點時效、自動識別是否存在風險；Phase 3 爬取航司網站、訂單狀態、運輸進展；Phase 4 監聽採集釘釘文檔、圖片、郵件等補充上下文；Phase 5 Agent 協同業務側處理、推動問題關閉。）

以消費者（企業）的折損來想，大家肯定有這個（切）感——如果大家做 2B 行業的話，這個肯定有更深的（切）感。以前我在內部提「一筆 QPS 的折損是一個用戶（體驗折損），一筆（工）單是一個巨大的用戶（期間）折損」。所以這裡面包含我整個質控的指標定義、追蹤，甚至質控的報告，我們都會有一些完全 AI 化的提升：之前是我們有質控專員每週會發一個質控報告，那現在我們已經做到說「AI 發起」（AI 生成），效果很好。讓我驚奇的是：我們最好的那個 prompt 不是我們的同學調出來的，是我們一個「業務總經理」調出來的——為啥呢？因為他還是很懂（業務）。

### 為什麼會有 BPO 級別的操作 —— BPO 領域特別適合被 Agent 取代

那我想（說什麼呢）？是 **BPO 領域特別適合被 Agent 取代**。這個觀點其實不是新觀點，但我為什麼要再次講呢？因為我認為它在（這個）時代的重要性還是比較大的。所謂 BPO（Business Process Outsourcing）領域，大家在傳統的客服和結算裡面有大量的 outsourcing（外包）。這些場景它是什麼呢？它有一個非常（現）（實）的工作，它為什麼會存在呢？我認為有兩個原因：第一，傳統軟件其實有（局限）——它無法對於結構化、無法對於非結構化的數據有很好的處理，所以需要「人去做業務和軟件的縫合」；正式員工大家捨不得讓他去做這麼（標）（準化）的工作，找個外包來做。而我認為現在 AI 時代顯然是更好的：因為 AI 處理多模態的能力越（來越）強了。不管你是上傳圖片去處理——我們現在有一個下單的環節，用戶可以去一個訂單（截）（圖）直接上傳下單。我們在消費者（寄）（件）的時候，他從各個平台的截圖直接上來——以前可能需要 14 個步驟、操作三分鐘才可以，因為有了我們這個多模態的能力，現在只要一分鐘以內就可以完成。這點從三分鐘到一分鐘，這就是消費者體驗的一個巨大變化。所以不管是多模態能力、還是推理能力、還是生產能力、還是對於工具調用——其實都某種（程度）（拓寬了）（傳統軟件的能力邊界）。（Long-horizon 場景下 Agent 遇到的挑戰：任務鏈路長、狀態容易丟失；Agent 判斷穩定性不足；多源數據質量不穩定；閉環學習能力仍需加強；自動協同動作存在風險。所以要靠：統一創建托管任務 → MCP 暴露標準能力 → 按狀態驅動流轉 → 檢查點與冪等 → 狀態與過程持久化 → 異常場景人工接管。）

我認為「重複性的工作、鼠標鍵盤密集的、數據密集的、知識密集的、（多方）協作密集的」都是 AI 非常擅長的場景。

## 三、企業級 Agent 落地的關鍵問題

### 問題一：存量系統如何升級？ —— CLI 是最佳橋樑

第一個就是「存量系統如何升級」。我們有大量的存量系統，它到底是「資產」還是「負債」呢？我覺得如果我們把它當成負債，我們會背了一個巨大的包袱；我認為它是「資產」。為什麼呢？如果我們的傳統系統做（適）量的 **MCP** 改造、或者 **CLI** 改造，就會更加不一樣。CLI 的效果我認為是非常好的：大家都知道前幾週有一個（週末），（釘）釘發布了它的 CLI——我第一時間去看在哪，然後（下）（載），（代碼）還是 5 萬（行）。（釘釘）非常（激進），開源它的能力，它連週一都不等了——大家想，連週一都不等就去發布它的開源代碼能力。那也就意味著，我認為 **CLI 是一個「人類不友好但 AI 很友好」、尤其是對於 Skill 非常友好的方式**。

（過多的我就不展開了。）從最開始的（GUI）、到（TUI）、到 JUI、到 LUI、再到現在的「CLI 崛起」——CLI 我認為是特別適合這個 AI（時代）的。然後昨天第一場的時候，黃東旭也講的是「UI 的設計哲學再次（被）學習」——裡面不管是 CLI 的（管道/pipe），還是（Unix 哲學）進一步的（復興），一切都可以（用一句話帶過）……都帶來了一些（啟發）。所以這裡我認為 CLI 是非常典型的一個設計。

（頭部企業正在重寫 Agent 執行面：**釘釘**——從 API 集成轉向 Agent 可調用的 CLI 命令面，把 CLI 作為 AI-native workspace 底座的一部分；**飛書**——從開發者工具式 CLI 走向 humans and AI Agents 的執行面，在命令之外把 Skills 也做成一等對象。CLI 正在成為越來越多企業的共識。GUI 適合人類、對 Agent 不友好；API 能力最全但不適合直接暴露給 Agent；MCP 是協議層、適合 Agent 標準化接入工具；CLI 適合 AI 和 Agent 共同使用、解決動作執行的問題。）

這裡對應來講，我認為 **Skill 我把它定義成 min agent（最小 agent）**，它還是偏小的；上層還是可以通過 **Workflow** 或者 Skill 等等更加不一樣的方式來展開。這裡形成一個金字塔：**CLI 層**（把業務能力暴露為 Agent 可調用命令）→ **Skill 層**（把 SOP 和最佳實踐封裝為可複用 Skills）→ **Workflow 層**（把跨 Skills 的長程任務編排成可追蹤的流程：需求交付、工單質檢、大促值班）→ **控制層**（觀測、評測、審計、安全管控）。但這裡來講，傳統系統退化成 **System of Record**，上層是 Agent 系統負責創新——傳統系統仍然有用、仍然可以在 AI 時代發揮作用，它不是要去下線的。

同時我認為 AI coding 也帶來了一個巨大的躍遷：以前我特別怕存量系統的「一兩個核心人員離職」，現在我一點也不怕。為什麼呢？AI coding 來了——我 AI coding 可以快速地去做「翻新和刷新」，那我們老舊系統可以有一個很好的、藉助 AI coding 去做翻新（的路徑）。我們試了好幾個場景，我覺得是非常好的。今天其實我春節（就）給我團隊同學做了兩個實驗（兩個幾十人的實驗），我說「這兩個項目能不能 AI coding 貢獻率 90%」——剛開始這兩組同學還以為（難）（做不到），然後春節之後他們就給我交答（卷），各自幹到 95% 了，然後我覺得我要給他們發（獎）。

### 問題二：什麼是好的 Agent？ —— 從 Claude Code 學習到的三大設計範式

第二個，什麼是一個好的 Agent？如果我們現在要學一個「好的業務 Agent」，從哪裡學呢？我認為就是「從編程的 IDE 裡來學」。我自己現在工作很多，但實際上我就一個工作，就是 AI coding——用 AI coding 去改變研發（結構）甚至產研流程，然後用「AI coding 裡面學習到的 IDE 設計」來推進我們（業務）Agent 的設計。如果我們要學的話，我認為作為技術來講，就從 **coding agent** 的設計哲學開始學，就學 Claude Code。現在好多 Agent 還沒有一個「被大量用戶使用」的，而編程已經被廣泛使用了——全球 3000 萬程序員，現在大量的程序員開始每天在使用、在消耗（token）。我今年花了 2000 美金來做大量的 token 消耗。

那學什麼呢？我這裡學三個點（企業 Agent 要落地，要補齊「經驗復用、過程治理和組織協作」；前提是「給 Agent 一台電腦——核心 File、Web 以及本地操作等，有一個基礎運行環境」；Agent 從『AI Coding IDE』架構參考，主要是 Claude Code）：

**第一個，Agent Teams 模式。** Anthropic 這家公司一直在定義工程能力的標準——大家想，MCP 是「兩個 PM/工程師在一個週末搞出來的」，Skill 是「發布之後半年時間爆（發）」。而它最近提出來的，我認為就是一個「**Teams 模式**」，現在幾個地方都有實現，我認為 Teams 接下來就是整個 Agent 架構裡面的標配——因為它要「組隊」，組隊之後去做更加複雜的任務。（Agent Teams：Team lead、Teammates、Task list、Mailbox。）

**第二個，Plugins 機制。** 就是（Anthropic）發布的 Plugins，讓 SaaS 的股價暴跌。我第一時間把它幾十個 Plugin 的源碼（下載了）——源碼其實是 MD（Markdown）文件（就）足夠（了）。我看了一下，我覺得設計得還是非常（強）的。所以我覺得，如果我們（業）務系統有合適（的），你不管是 Command 的方式、還是 Skill 的擴展方式、還是把 MCP 的工具放在裡面，其實都是「擴展」。（Plugins：Commands（Bash and Scripts）、Skills；plugin.json 是 Manifest，commands 是「你顯式調用的 slash commands」，skills 是「Claude 自動取用的領域知識」，SKILL.md 需要 YAML frontmatter（name/description）、Markdown 指令、可選的 Bundled Resources（scripts/references）。經驗復用對應 Commands / Skills：高頻任務不應該每次從零規劃和推理，把高頻動作、通用流程和領域經驗沉澱為可複用的單元；典型企業任務：慢 SQL 排查、變更影響面分析、生成週報、審批流處理。）

**第三個，Agentic Loop。** 這是它的一篇文章，我認為沒有什麼特別新鮮的觀點，包括 Agentic（Search）、SubAgent（並行 + 隔離）、還有 Compaction（壓縮）。（Agentic Loop 分三步：一、Gather Context 上下文（Agentic Search、SubAgent、Compaction 壓縮）；二、Take Action 採取行動（MCP、Software System of Record）；三、Verify Work 驗證工作（Defining rules、Visual feedback、LLM as a judge）。過程治理對應 **Hooks**：解決生產環境中確定性執行的問題，在執行鏈路關鍵節點插入控制點，讓校驗、限制、通知和審計自動發生；典型企業任務：敏感信息檢查、代碼規範校驗、工具回填、日誌留痕。組織協作對應 **Teams / Subagents**：複雜任務不能只靠單 Agent，先按角色拆分任務，再組織協同完成。）它有 Command 模式（我 AI 生成代碼）、也有 Skill 模式（我執行預製的代碼）。所以其實這是一個非常典型的 Agent 架構。

我認為 Claude Code 的 50 萬行代碼都洩漏了，大家肯定都在看。有的時候我現在看到一個特別（好）的代碼，我會把它下載下來，然後用我幾個 coding 工具同時去「組隊分析」，然後各自給我交付一個報告，我看看之後——像讀代碼的時間也大幅縮短了。以前要弄懂一個 5 萬行的代碼真的需要兩三個小時，而現在有了 AI coding 之後，可能真的十幾分鐘、或者幾十分鐘時間就可以了解它的分層架構、核心設計、核心的接口和關鍵邏輯。

所以（Anthropic）的成功也不是機緣巧合：春節期間，Claude Code 的負責人、（Anthropic）的 CEO，和 Codex 的負責人都非常活躍，他們在很好地佈局自己的 AI coding 工具，然後都同時表達了一個觀點——「編程（是 Agent 的核心/一切構建的基礎）」。我也認為，我們這個行業程序員這個（工種）（不會）（消）（失）。那未來大家是什麼？可能每個人都是「架構師」，每個人手底下（帶）著 10 個 Agent、或者 10 個 Agent 手下有 100 個 Agent 去幹活。而我也認為，未來頂級程序員每天消耗 1 億或 10 億 token 成為可能。根據我內部的觀察，程序員這個群體的「28 效應」很明顯：**22% 的程序員消耗了 80% 的 token**。所以我也覺得，coding 工具值得研究，但我們的研究不僅僅局限於「如何用好 coding」，而可以把它延伸到 Agent 的架構和產品設計。

### 問題三：建設企業級 Agent，目標是更懂業務，同時更有「生產力」

第三個，就是我們建設（企業）級的 Agent 如何更懂業務。剛才我那個銷售的場景其實我們比較（初）（級）——我們的電話其實是「傻傻的、不懂銷售」，因為金牌銷售還是很會聊天的，同時銷售要懂產品知識才可以和用戶有更好的互動。所以這是我們下一步要（突破）的。

我這裡就講一個觀點，叫「**硅基員工**」。為什麼叫硅基員工？我認為有三個邏輯。第一，如果我們把 AI 當成「工具」，你（管理）的就是一（堆）工具；如果我們把 AI 當成「人」，你（管理）的是一個「團（隊）」——這裡面背後的邏輯，如果大家去追溯的話，其實從大模型的 MoE、再往底層（（神經元）），全部都是「擬人化的設計」。而擬人化設計來講，它天生是一個「（博學的通才/外行）博士」，它如何（進）（入）千行百業？我覺得「按照崗位、按照工種去做設計」是完全可以的。而「硅基員工」是一個非常好的（形態）——或者叫「硅基勞動力」，它是 AI（進）入一個「產業互聯網組織」的一個很好的（載體），（否則）（純技術）其實不太好走進（去）的。

所以這裡來講，我的（基礎 Agent）其實是一個「low-context + 低（智）能」的（形態）；而硅基員工是一個「**high-context + 高級智能**」的體現，它可以處理更加複雜的（任務）。我們現在在做的、內部花了大量時間在做的（探索），就是「如何把（Agent）用（日常運營的工作方式）來去執行」——這個我們花了很（多）（精）力，我覺得它可以讓我們的 AI 更加有生產力。就像我們發布的「悟空」、還有大家所用的桌面工具，我認為它更多的是一種「助理」的形態——通過（互動）、還是「以人為主」；但是「員工」不一樣，員工是說他可以「自主」，人是在裡面去「處理異常」，從而可以有一些更加不一樣的智能出現。

（從 Context 和 Agency 兩個維度看企業級 Agent 演進：**高風險執行體**（很能幹但容易幹錯，工具調用和自動執行強、但業務上下文不足）；**Chatbot / 問答助手**（會說一點、不太會做）；**超級顧問**（很懂你、但還要你自己動手，建議判斷強、執行依賴人工）；**硅基員工**（既懂業務、也能把事情做完，理解、執行、協作、閉環同時到位）。優化 **Agency**：CLI、Skills、Workflow、Hooks、Teams；優化 **Context**：Memory、上下文（及時清理/壓縮）、中間過程產物（外部持久化，避免佔用上下文資源）。）

那這裡來講，企業內部落地，其實可以「先挑一些高頻、重複、低風險的（任務）去落地」——就是大家想，「AI 的主菜還沒上之前，先上個甜點」，讓大家都可以拿到這個效果。我在內部去推進 AI，做了大量的「布道」——每兩個月和總經理講最新（進展），然後在全員直播群裡面講 AI。其實我們一個大型組織去推進 AI 要花很長的時間，且裡面我認為「思想的轉變」是一個巨大的（品）（質）（阻力）。（落地策略三條：策略 1 先挑高頻、重複、低風險任務打透（不要一上來就做全場景萬能 Agent）；策略 2 能力沿 Context 和 Agency 發展（會說不會做，優先補 Agency；常做錯，優先補 Context）；策略 3 優先建設觀測與評測體系（沒有觀測和評測閉環，Agent 看起來能跑，但很難持續優化）。）第二個是關於 Context 和 Agentic 的這些（能力），第三是「觀測和評測」。

而我也認為，整個過程中會有大量的工具鏈會重複誕生——會像微服務和（編程）語言（誕）（生）時代有大量新工具出現，整個甚至（運行時/中間件）都會被重寫。現在的（運行時）是給互聯（網設計的），它不是為「非確定性」去設計的，也不是為「長週期」設計的，所以我覺得有可能（運行時/中間件）的形態也會發生巨大的（變化）。

## 結尾

因為時間問題，可能我們也來不及（了）。這是我的公眾號的二維碼。我就覺得說，AI 時代激發了好多人的表達（欲），我自己的表達欲也再一次被激發了——然後春節期間每天寫兩篇文章，但一開工就沒有時間去寫了。未來一些交流我們也可以在公眾號裡面（進行）。

最後是我一個標題：我認為 **AI 開啟了新一次的工業革命**。我也非常期待——我春節期間寫的文章的最後一篇叫什麼呢？叫「**工程師開啟工程師的黃金時代**」。我也認為，AI 的海嘯（到）來，工程師是最先被海嘯席捲的一個群體，我們可以在工業革命的這個浪潮裡面去有更大的能量釋放。
