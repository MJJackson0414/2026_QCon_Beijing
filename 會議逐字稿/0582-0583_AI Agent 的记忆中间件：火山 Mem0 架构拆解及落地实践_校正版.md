## 一、背景與痛點

（我）來跟大家做一個分享。首先按照套路來，我們先切一下情況。左邊這張圖是說：我們現在模型的能力越來越強。這個（座標）AI 化的（標註）並不準——因為按照 scaling law 來說，我們模型的能力是（近似）線性的。這個數值大家都看（過）了，反正這裡表達的意思就是：我們的模型現在隨著 scaling law 不斷地在線性增長。

但是在模型能力不斷變強的時候，其實「記憶」還是蠻重要的。包括之前鳥窩老師也提到了，現在在（記憶）方面還是有所欠缺的。它有一些點需要我們（去解決），具體的點是什麼呢？

**第一個痛點，其實就是「任務信息斷裂」。** 還原一些簡單的場景：比如我們經常在給一個任務的時候，第一天可能給了五個 task，這些 task 可能有些（進展）我們推動（了）；然後第二天，我們又要去解釋一遍上下文。其實真正的（瓶頸）可能就在於：我今天「輸出上下文的能力」成為了一個瓶頸，而不是 AI（本身）的（瓶頸）。所以這個事就很煩——就像我上學的時候導師對我一樣：「這個（人）怎麼（記性）（這麼差），什麼都記不住，怎麼會？」那我們其實就需要「記憶」來幫我們解決這個問題。本質上，我們還是要在（跨）session（的場景）去把我們之前想讓 AI（做）的一些事情、還有一些「解釋上下文的成本」給它消滅掉。所以這就是我們的第一個（訴求）：我們想通過我們這個（記憶）產品，幫大家去解決類似這樣的問題。

**第二個（痛點），其實跟卢老師剛才講的那個（DeepResearch）有點像**，更多的是我們一些「經驗」是（一次性）的。就個人而言，我們的工作可能更多在編碼、還有一些日常事務處理、還有一些（研）發設計上的（工作）。我們在真實的工作場景中會有各種各樣的上下文、跟不同人的對話；然後我把 bug 修完了，過兩天我就忘了這個 bug 是怎麼修的，我需要翻、需要去想、需要花很多時間再把我之前（積累）的知識重新（梳理）一遍。所以這些東西一般都放到了各個不同的地方，有的在（聊天記）錄裡（散落著）。然後我經常要做的事就是：一個新（同事）過來了，問我「之前這事怎麼做」，我做的第一件事就要翻各種聊天記錄，按照我原文（的關鍵詞）去搜；如果有時候搜不到了，那可能這個東西就（丟）了，我也不知道我（記在哪）了。但現在，我們通過「記憶」或者 RAG 這種方式，就可以把這些之前已經沉澱、或者知道的信息，想辦法推到我們的記憶系統，（讓它幫我們）承載記憶。所以記憶系統幫我們解決的第二個重點，就是「經驗（的沉澱）」。

**第三個（痛點），可能跟我們目前這種 Agent 的工作稍微有點差距**，但比如說對於陪伴類的機器人——比如我們用豆（包）做個陪聊，其實很多，像我父（母）輩或者爺爺奶奶經常會這麼做——像這種陪伴類的 AI，經常需要的一個事就是：我需要把我用戶的偏好沉澱下來、記錄下來。包括類似於 ChatGPT 的 Memory 其實也是這個道理：我需要去真正理解我這個用戶是什麼樣的背景、他之前有什麼樣的偏好。比如我可以記錄「對於我的標籤，可能是一個程序員、工作者，現在在做記憶系統」，那它可能在解釋一些技術類東西的時候，就不需要（那麼）（贅述），它可以默認「我都知道」，那就會（節省）（不）（少）的閱讀成本。諸如此類的，其實對我們來說還是有不少好處的。

## 二、火山引擎 Mem0 介紹

### Mem0（社區）的歷史

社區最開始的（記憶）方案其實更多的是 **Mem0**。據我們所知，Mem0 應該是社區最早——不能說最早——最早知名的一個記憶方案。回顧一下它的歷史：它最開始 2023 年其實就開始搞了，當時有那麼兩三個人成立了公司，做這個（記憶）。它其實也是一個流行的方向：利用像（向量）庫去做一些（檢）索，然後返回一些相關的內容。然後在 2024 年夏天的時候，他們看到了一個機會，同時也（拿）到了（YC 之類）的孵化計劃，就大概出來做了 Mem0 這套東西。所以當時在業界來說，這個東西還是比較新、他們也比較早，所以相當於這是最早（火）起來的一個記憶系統。然後在 2025 年，他們完成了一個 A（輪），大概拿了 2400 萬美金。這是簡單回顧一下 Mem0 的歷史。

### Mem0 的架構

它的架構說實話非常簡單，可能在做的各位同學，把代碼放（進去），兩個小時就（能看完）；用 AI 看可能五分鐘就知道這個東西大概是什麼（原理）了。它的架構是：上層是一個「接口層」，有一套自己的 Memory 相關的協議，主要就是 add（從 message 裡面抽取記憶）、然後 query（查詢）——本質上主要的接口就這（兩個）。下面是一個「記憶層」，記憶層主要是支持同步記憶：我在用戶輸入 message 以後，通過用 LLM、通過用一些（原生）模型或（開源）模型，去把記憶相關的記憶點抽出來，最後存到向量數據庫。（圖存儲）其實也是經過抽取的。

這張圖說明一下它的整個流程，大家可能會更清楚一點。最左邊是我們最開始的過程：我們通過對話、通過 bot 這種方式，把 message 給到我們整個 Mem0 系統。然後它有一個「提取」的過程（Extraction Phase），會先把知識提取出來，變成一個 item。舉個例子：我今天可能說「我今天中午吃了一碗（拉）麵，然後這個味道（不錯）」，它就會提取一個知識點，比如「在 2026 年 4 月 16 號（吃）了一碗拉麵」，變成這麼一個知識點。然後它會經歷第二個階段，有一個叫 update 的階段（Update Phase）：它會首先去從記憶庫裡面搜相關的（記憶）。比如採取剛才那個例子——「我吃了一碗拉麵，我還挺喜歡它的」，它可能就會提取出來「我喜歡吃（這家）拉麵」；但是之前我可能某一天說「今天這個東西太難吃了、我不喜歡吃（這家）拉麵」，這種記憶也是（衝突）的。那麼它其實就需要這種 update 的機制，把之前已經過時的記憶拿出來做一個刪除操作，然後再把新的記憶更新出來（ADD / UPDATE / DELETE / NOOP）。因為記憶也不是一成不變的——人總是會變的，我們的偏好也（隨）時間不斷變化。所以他們其實也抓住了這麼一個（點），Mem0 比較早地提出了這種「update base」的概念。所以在 2024 年，相當於是（做了）一個比較成功的系統。

### Mem0 的問題

但是我們看到，整個 Mem0 做得還比較簡單，包括從 2024 年到現在，整個社區的進化相對來說也不是那麼快——不像我們（想的）「一天一個（版本）」——它完全是屬於一個比較（初級）的開源設施。它有很多問題，我們稍微總結一下：

第一，**記憶提取、管理（分層）的問題**。因為最近包括從 25 年 10 月份開始，我們有一個很大的變化，就是我們一直在提 **Skill**：Skill 有一個很重要的東西，就是「我的信息是按階段給到大模型的」——最開始可能是一個非常抽象的（描述），然後後面一層是更詳細地告訴你這個東西到底應該怎麼用，最後一層才是我實際的用法。但是之前的記憶——Mem0 這套是不支持（分層）的，它對於所有的記憶都是（扁平/一視同仁）的。這就有點像你做一個存儲的類：我們所有的知識都是一個「平的結構」，沒有「樹狀的結構」。而現在更多的是說，我們其實需要一個（分層）的結構，我們需要在（模型）最需要的時候，再去給它足夠的（信息）——記憶其實也應該是這樣。

第二，我們剛才可以看到 Mem0 是有「圖能力」的，但是它的圖能力其實相對比較弱，它對整個圖的提取和檢索的過程（都比較簡單）；而我們就是在（ByteGraph）上做了深（入）研究的，所以我們可能就在有限的（空間）存了更多的（信息）。

第三，我們發現 Mem0 是沒有一個「自進化」機制的，它對於經驗的抽取比較弱——它只能記住之前比較簡單的那種記憶關係，就是我剛才舉的例子（拉麵）；但是對於長程的任務，比如我真正寫了一段（代碼），然後發現這個東西有 bug、我去怎麼樣 fix 這個 bug，我（能不能）從這裡面總結、（提）煉出一條相應的經驗——這塊它是沒有任何能力的（後面我們會有一個例子來講）。

第四，可能是一個老生（常談）：一般任何的開源社區都是沒有「企業級」能力的，它只是把數據（管）得好，然後包括你任何的（權限）控制邏輯、企業級（部署）的能力，往往都需要自己來建設。

最後一個，它的策略是比較單一的：它（用的是）這種列表的（召回）策略，比較弱。它在返回的結果裡面會把「向量」和「圖」（分開）看——圖是圖、向量是向量；如果圖和向量有衝突，那對不起，你需要（自己）去解決這些問題。

### 火山引擎 Mem0（Mem0 Pro）：我們做了什麼

所以其實我們發現了 Mem0 有非常多的問題。所以這兩個月我們做了一個事：相當於我們完全把 Mem0 這套（重寫）了，我們只是保留了協議的兼容——就是我們對 Mem0 的協議是完全兼容的——然後在此基礎上提供了各種各樣不同的新（能力）。這一套其實我們也是最近比較火的 **vibe coding**（做出來的），完全是 vibe coding 出來的：從大概開發到實際的 PoC 跑通、到內部客戶用，大概只花了兩到三週的時間。所以可以見到，現在這個軟件開發週期、整個流程的變化（有多大）。

那具體我們從（開源的）Mem0 到火山（引擎）的 Mem0，都具體做了什麼呢？還是剛才那幾點：

我們改變了數據結構，我們從一個「扁平化、沒有分層的組織」變成了一種「三層的（結構）」。另外，我們把檢索能力也提升了，我們做這種向量、（關鍵詞）列表、（圖）的融合召回和排序（rerank）。第四個，我們支持了圖能力——因為我們構建在 **ByteGraph** 上，我們運用了很多 ByteGraph（的能力），這（是內部）一個比較好的（圖庫）。第五點，就是「自進化」、「企業級」（權限）和（可）監督性，這個事比較簡單，我就在這（略過）。

然後這個是（架構）加的一些優化和（設計）。首先，我們從（接口）形式上支持了一些其他協議：我們對整個架構上做了一層更多的封裝，然後在（原生）協議上更好地擴展、接入其他協議——未來我們就（可以）說，有些屬於（有向）的（比如）MCP，或者在這個上面，用戶要（接入）比較（容易）地去支持他們一個接口。另外一個是：我們在普通記憶的（基礎上），相當於增加了一些「異步」（能力）——未來我們會增加一套異步的接（口）。然後具體到下面那個記憶層，其實就是我們會增加一個 **AgentLoop**（的能力）——這也涉及到我們一些對未來的思考，就是說我們（記憶）組件要不要（有）原生的一些（Agent 能力）。這裡面的一個好處是：我們在面對客戶的時候，有時候會看到各種各樣奇（怪）的需求。按照傳統的軟件開發（週期），我們接了需求就需要去開發。舉個例子：比如我們在 graph 查詢的時候，用戶在一個（初始）節點，想知道這個節點的所有鄰居（一跳）——那麼接口上沒有這個東西，那用戶就（沒法做），那我們就（得）開發、需要去測試、然後到上線……從你接到用戶這個請求，到最後用戶真正拿到這個東西，一（段時間）就過去了。但是如果一個軟件內置了一個 Agent，那麼我們內部的 Agent 會把你（底）下所有的存儲、它的 schema、它的數據格式、任何東西，都可以做成一個 **skill**。那在這一層，其實我們就多了一層（能力）：你可以把這種低（頻）的查詢類、（使用）類的請求就（交）給這個（Agent）。那對於（用戶）來說，我只需要通過自然語言告訴它「你去查一下這個人所有的朋友、就是一跳的信息是什麼」，就可以拿到這個信息。除此（之外），我們更多地支持了一個異步的任務——更多用戶有一些（異）步的請求、想同時處理多任務。另外一個就是支持「經驗的（沉澱）」，後面就有一個（自進化的部分）。

### 三層記憶 / 三層查詢

然後這個就是我們 Memory（火山 Mem0）的一個記憶（組織）。其實我們把它分成了三（層）。最開始那層（Layer 0）就是「原始結果」，包括我們（給的）所有（原文）——比如我們使用一個 Agent，我們給了它所有情況、一個工具，你最終（說）了什麼話，這（是第一層）。第二層是「（提）取後的（記憶）」，它更多可能放在一個向量（庫）：比如我之前的例子，「我的個人用戶編號是什麼」，它會提取出來；「你之前做過一個什麼事、在某一個時間點做了些什麼事」。第三層就（是圖譜）。那我們有了這三（層）數據，你就需要對用戶做一個相（應）的查詢優化。我們其實就做了一種「短期記憶（元數據過濾）、向量查詢、圖查詢」這三層的聯合召回優化，然後同時給到（應）用層。

## 三、核心優勢

前面介紹了一些我們簡單的架構，相對來說（可能）（不夠具體），我們可能用一些例子來講一下我們核心的優勢——火山（Mem0）在記憶系統裡到底有什麼不一樣的東西。

### 優勢一：精準記憶注入，節省 Token

我們第一個核心優勢，還是說我們的（Token）（節）省上其實還是蠻（顯著的）。這個是我們記憶三種（做法）的一個對比：

最開始最原始的、大家用的方式——「我記憶找到、或者我需要這個東西」，包括對於之前的記憶、郵件，我很多都需要原封不動地全部塞給模型，然後利用模型這種海量的上下文能力，來把我相關的東西找到。這種方式呢，就會非常消耗我們的 token（Prompt）。第二種是傳統的 RAG 方式，更多的是對原文切片：我可能按照某（幾）句話切成一片，然後對每（片）算一個向量，把這個向量和我們原文的信息都存到向量數據庫裡；然後在我們（檢索）的時候，通過向量（檢）索把最相似、最相關的請求全部召回，再放到我們的 Prompt 裡面，最後完成這個相關的（推理）。而在我們的方案裡，我們其實做了更多在「抽取」上的工作，然後我們在圖、向量、原文，都只給用戶返回那種「最（精）（準）、最（貼合）請求」的一些信息，然後把這個東西（餵）（給模型）核心，來完成這個用戶記憶的（召回）。

我們相當於用這個做了一個 evaluation——我們如何評測這個效果呢？我們用了一個業界比較典型的（基準），叫 **LoCoMo**。這個東西其實首先它是一個面向多輪繪畫（對話）的（基準），本質上還是停在這個（描述）用戶（對話）的（邏輯）。它有四個不一樣的（維度）：

### 優勢二：記憶自進化

第二個優勢是「自進化」。這個能力反而是我認為現在的記憶系統最有價值的一個地方。我們核心的理念不是讓（模型死記硬背），而是說讓它在（學習的軌）跡中，通過之前失敗的經驗（去學習）——因為「失敗乃成功之母」嘛，我們需要把這些「母親」都記住，然後去變成一個（可複用經驗）的「兒子」，（讓 Agent）不斷地（成功）努力。

這裡面我們用的一個 benchmark 其實是 **OfficeQA**。這個東西我們也困擾了比較久：我們到底怎麼樣（衡量）這個東西能帶來什麼——每個人都是一套個人的經驗，我之前做了一個任務、靠某個經驗成功了，這個東西到底怎麼樣去量化呢？最後我們還是回到了模型的（評測），發現其實在它們的任務裡面是有一些相似的 benchmark（可用）。所以我們這裡舉的一個例子就是 **OfficeQA**。OfficeQA 本來是用於整個模型的一個 benchmark，它覆蓋的場景跟我們日常的工作比較像：（除了）編碼，還包括郵件、我們去總結會議記（要）、去分析文檔、做表（格）操作，然後去理解書、（音）（頻）（視頻）上的各種各樣信息，然後去做相應的回复。用了 OfficeQA 以後，我們最終（達到）的（效果）——我們可以看到有 13.3（%）的（提升）（OpenClaw + built-in memory 39.0% → OpenClaw + mem0 42.3% → OpenClaw + 火山引擎 Mem0 52.3%），這個效果還是驚人的。
